## 1. Design Decision: Paired Cooperative Destinations

The fusion kernel carries **TWO cooperative F32 destinations simultaneously** — one for gate, one for up — accumulated in parallel across the K-loop using the same staged activation tile.

This mirrors the existing simdgroup pair kernel (`kernel_mul_mm_id_pair_swiglu_f16_impl`) which already carries two sets of `simdgroup_float8x8` accumulators (`mc_gate[8]`, `mc_up[8]`).

### Why paired (not sequential):

| Approach | Pros | Cons |
|----------|------|------|
| **Paired** (both live simultaneously) | Single activation staging per K-step; fewer barriers; mirrors existing kernel structure | 2× accumulator register pressure |
| **Sequential** (finish gate, store, then do up) | Half the accumulator registers at any time | 2× activation staging passes (full second K-loop); 2× barrier cost; more complex control flow |

The paired approach was chosen because:
1. The simdgroup version already carries both accumulators without occupancy issues
2. Cooperative F32 destinations from `execution_simdgroups<4>` have a fixed per-thread capacity (typically 8–16 elements per cooperative tensor) — carrying two doesn't necessarily halve occupancy since the register allocation depends on overall kernel complexity
3. The single activation staging pass is a significant memory-traffic saving (sb[] is staged once instead of twice over the entire K dimension)
4. It produces the simplest code that can be compared directly against the simdgroup kernel

## 2. Design §8.6 Experimental Questions — Answers

### Q1: Can two cooperative destination tensors from matching descriptors be indexed with a compatible per-thread mapping?

**YES.** Both `cT_gate` and `cT_up` are created from the same `matmul2d` descriptor via `get_destination_cooperative_tensor`. They have identical `get_capacity()` and `is_valid_element()` behavior. Each is independently zeroed and accumulated. The cooperative store (`cT_gate.store(tC_gate)`) resolves the per-thread mapping identically for both — the underlying thread-to-element mapping is a property of the matmul descriptor and execution configuration, not of the operand content.

### Q2: Can gate and up be run back-to-back while the shared activation stays hot?

**YES.** Within a single K-iteration:
```metal
mm.run(sB, sA_gate, cT_gate);
mm.run(sB, sA_up,   cT_up);
```

The activation tensor view (`sB` over `sb[]`) remains valid between both calls because:
- `mm.run()` only reads threadgroup memory through tensor views; it does not write to threadgroup
- It accumulates into cooperative destination registers (per-thread state)
- No barrier is needed between the two `mm.run()` calls
- The threadgroup data is protected by the existing K-loop barriers (before staging writes and after matmul reads)

### Q3: Is storing only `mid` valid for the production graph, or are gate/up values needed elsewhere?

**YES — only `mid` is needed.** The existing simdgroup kernel already writes only `mid` to device memory. The `ds4_metal_dsv4_moe_swiglu_weight_args` struct provides `mid_row_stride` for the output. Gate and up intermediate values are not consumed downstream in normal inference.

A diagnostic path that materializes gate/up separately already exists (controlled by `write_clamped` in the non-fused kernel path) and is outside the scope of this fusion kernel.

### Q4: Does fusing route weight here preserve the existing arithmetic order closely enough?

**YES — exactly.** The epilogue performs:
```metal
float g = Cg[i];
float u = Cu[i];
if (c > 1.0e-6f) { g = min(g, c); u = clamp(u, -c, c); }
const float silu = g / (1.0f + exp(-g));
D[i] = (half)(silu * u * route_weight);
```

This is **identical** to the existing simdgroup kernel's epilogue (same clamp logic, same SiLU formula, same multiply order). The only arithmetic difference upstream is the matmul reduction order (matmul2d vs manual simdgroup_multiply_accumulate), which is the standard TensorOps vs simdgroup tradeoff already accepted for the staged-dequant pattern.

### Q5: Is register pressure lower/higher than writing gate/up to device memory?

**Higher per-thread register cost** due to two cooperative accumulators, but:
- The alternative (sequential: finish gate → store to device → do up) would require a full second K-loop pass over the activation, doubling activation memory traffic
- Writing gate/up to device memory is the worst option — it was the original unfused path that this kernel replaces
- The existing simdgroup kernel carries `mc_gate[8]` + `mc_up[8]` (16 simdgroup_float8x8 matrices) without issues
- Each cooperative destination's per-thread capacity is bounded by the tile geometry and execution configuration; the Metal compiler should handle the allocation

If register pressure proves problematic on actual hardware (manifesting as occupancy loss measurable via profiling), the fallback is the **sequential approach**: finish the gate matmul entirely (all K iterations), store cT_gate to threadgroup, then re-stage the activation for the up matmul. This trades memory traffic for register savings.

## 3. Threadgroup Memory Analysis

```
Staging phase (during K-loop):
  sa_gate: half[64 × 32] = 4096 bytes   (offset 0)
  sa_up:   half[64 × 32] = 4096 bytes   (offset 4096)
  sb:      half[32 × 32] = 2048 bytes   (offset 8192)
  Total staging: 10240 bytes

Epilogue phase (after K-loop, reuses shmem):
  sc_gate: float[64 × 32] = 8192 bytes  (offset 0)
  sc_up:   float[64 × 32] = 8192 bytes  (offset 8192)
  Total epilogue: 16384 bytes

Required threadgroup allocation: max(10240, 16384) = 16384 bytes
```

Compare with existing simdgroup pair kernel: sa_gate 4096 + sa_up 4096 + sb 2048 = 10240 during K-loop; temp_gate 8192 + temp_up 8192 = 16384 for epilogue. **Identical threadgroup footprint.**

### Relationship to task 7.2 specialized kernel

Task 7.2 implemented `kernel_mul_mm_id_mxfp4_pair_swiglu_f16_mpp` — a hand-specialized
MXFP4 version of the same fused pattern. The task 7.4 generic template
(`kernel_mul_mm_id_mpp_pair_swiglu_f16_impl`) generalizes this for ALL quant formats
using the same dequantize function pointer pattern as the existing `kernel_mul_mm_id_mpp`.

Minor design differences between the two:
- Task 7.2 uses two matmul2d instances (`mm_gate`, `mm_up`); task 7.4 shares one
- Task 7.2 hardcodes MXFP4 pointer advancement; task 7.4 uses generic `nl` template param
- Task 7.4 includes a TP ownership check (defensive); task 7.2 does not

Both produce identical results for MXFP4 inputs. The template version enables
IQ2_XXS and Q4_K fusion without code duplication.

## 5. Differences from the Simdgroup Pair Kernel

| Aspect | Simdgroup pair | TensorOps fusion (this) |
|--------|---------------|------------------------|
| Matmul engine | `simdgroup_multiply_accumulate` | `matmul2d` (M5 Neural Accelerator) |
| Execution | 4 simdgroups, manual MMA loops | `execution_simdgroups<4>`, hardware matmul2d |
| Accumulator type | `simdgroup_float8x8 mc_gate[8], mc_up[8]` | Cooperative F32 tensors `cT_gate`, `cT_up` |
| Activation reuse | Shared `sb[]`, manual `simdgroup_load` | Shared tensor view `tB` over `sb[]` |
| Epilogue | Identical (clamp + SiLU + mul + route weight) | Identical |
| Output format | `half` via `dst_mid` | `half` via `dst_mid` |
| Threadgroup bytes | 16384 | 16384 |
| Tail cull variant | Yes (`CULL_TAIL_SIMDGROUPS`) | Not yet (add if prototype wins) |
| Compact-tail variant | Yes (32×32 tile) | Not yet (add if justified) |

## 6. What To Benchmark (Task 7.8 prerequisite)

When benchmarking this kernel against the simdgroup baseline:

1. **Match dispatch geometry exactly** — same work buffer, same threadgroup count, same expert bucketing
2. **Measure at representative expert bucket sizes** — full tiles (32 tokens) and short tails (1–16 tokens)
3. **Check register pressure** — if the Metal compiler reports higher register usage, profile occupancy
4. **Thermal parity** — same binary, ABBA ordering, matched thermals
5. **Correctness first** — verify bit-for-bit (or calibrated-envelope) match against simdgroup kernel output on the same inputs

## 7. Sequential Fallback (if register pressure wins)

If profiling reveals that carrying two cooperative destinations hurts occupancy enough to negate the matmul2d speedup, the sequential fallback would be:

```metal
// Phase 1: full K-loop for gate only
for (loop_k = 0; loop_k < args.ne00; loop_k += NK) {
    stage sa_gate[], sb[];
    mm.run(sB, sA_gate, cT_gate);
}
cT_gate.store(tC_gate);

// Phase 2: full K-loop for up (re-stages activation)
for (loop_k = 0; loop_k < args.ne00; loop_k += NK) {
    stage sa_up[], sb[];  // sb re-staged from device memory
    mm.run(sB, sA_up, cT_up);
}
cT_up.store(tC_up);

// Phase 3: epilogue (same as paired)
```

This halves accumulator registers but doubles activation staging memory traffic. Only implement if profiling proves it necessary — the paired approach is the stronger hypothesis.

## 8. Requirement Traceability

### R6 (Routed-MoE TensorOps lift)

> WHEN gate and up projections use the same activation tile  
> THE SYSTEM SHALL evaluate a fused TensorOps design that reuses the activation and applies SwiGLU and route weighting before unnecessary device-memory round trips.

**Satisfied.** This kernel reuses a single staged activation tile for both projections and applies the full SwiGLU+route-weight epilogue before the single device store of `mid`.

> WHEN a cooperative-tensor result can be consumed by the next operation without an intermediate device-memory store  
> THE SYSTEM SHALL evaluate that fusion and retain it only if correctness and end-to-end benchmarks pass.

**Evaluated.** The cooperative results are consumed entirely within the kernel's epilogue (threadgroup materialization → fused arithmetic → device store). No intermediate device-memory materialization of gate or up occurs.
