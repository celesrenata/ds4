# Task 9.2 — IQ2_XXS Format Documentation

_Requirements: R7_

Source: `cuda/mmq/ggml-common.h`, `metal/moe.metal`, `rocm/ds4_rocm_moe.cuh`, `cuda/mmq/test/iq2_host_tables.h`

---

## 1. Overview

IQ2_XXS is an "information-optimal" 2-bit quantization format from the GGML/llama.cpp lineage. Unlike standard linear quantizers (Q2_K), IQ2_XXS uses a **codebook-based** approach: each group of 8 weight values is represented by a single 8-bit index into a precomputed codebook of 256 allowed 8-element patterns, plus a 7-bit sign pattern index into a 128-entry sign table. This achieves **2.0625 bits per weight** (2 + 16/(256) = 2.0625 bpw overhead from the block-level f16 scale).

---

## 2. Block Structure

### 2.1 C Struct Definition

```c
// QK_K = 256 (values per super-block)
typedef struct {
    ggml_half d;            // f16 super-block scale (2 bytes)
    uint16_t qs[QK_K/8];   // packed grid indices + sign/scale data (32 × uint16 = 64 bytes)
} block_iq2_xxs;
// sizeof(block_iq2_xxs) = 2 + 64 = 66 bytes
```

### 2.2 Block Parameters

| Parameter | Value |
|-----------|-------|
| Elements per block | 256 (QK_K) |
| Block size in bytes | 66 |
| Bits per weight | 2.0625 (256×2 bits data + 16 bits scale = 528 bits / 256 values) |
| Sub-groups per block | 8 (each covering 32 values) |
| Quads per sub-group | 4 (each covering 8 values) |
| Natural alignment | **2-byte** (uint16_t array; 66 is not power-of-two) |

### 2.3 Memory Layout (66 bytes)

```
Offset  Size   Field
------  ----   -----
0       2      d           — f16 super-block scale
2       64     qs[0..31]   — 32 × uint16_t, interpreted as 8 groups of 4 uint16_t
```

The `qs` array is consumed in groups of 4 consecutive uint16_t values (8 bytes) per 32-element sub-group. Within each 8-byte sub-group:

```
qs[4*ib32 + 0], qs[4*ib32 + 1]  →  aux32_g (grid word): 4 × 8-bit codebook indices
qs[4*ib32 + 2], qs[4*ib32 + 3]  →  aux32_s (sign/scale word): sign indices + sub-group scale
```

---

## 3. Sub-group Encoding (32 values → 8 bytes)

Each of the 8 sub-groups (ib32 = 0..7) encodes 32 weight values in exactly 8 bytes (two uint32 words when reassembled):

### 3.1 Grid Word (`aux32_g`)

```
aux32_g = qs[4*ib32 + 0] | (qs[4*ib32 + 1] << 16)
```

Contains 4 × 8-bit codebook indices packed in little-endian order:

```
aux8[0] = aux32_g[7:0]    → codebook index for values [0..7]
aux8[1] = aux32_g[15:8]   → codebook index for values [8..15]
aux8[2] = aux32_g[23:16]  → codebook index for values [16..23]
aux8[3] = aux32_g[31:24]  → codebook index for values [24..31]
```

Each index selects one of 256 entries from `iq2xxs_grid`.

### 3.2 Sign/Scale Word (`aux32_s`)

```
aux32_s = qs[4*ib32 + 2] | (qs[4*ib32 + 3] << 16)
```

Bit layout:

```
Bits [6:0]    → sign index for quad 0 (values [0..7])     — 7 bits
Bits [13:7]   → sign index for quad 1 (values [8..15])    — 7 bits
Bits [20:14]  → sign index for quad 2 (values [16..23])   — 7 bits
Bits [27:21]  → sign index for quad 3 (values [24..31])   — 7 bits
Bits [31:28]  → sub-group scale factor (4 bits)           — value 0..15
```

Total: 4×7 + 4 = 32 bits ✓

---

## 4. Codebook: `iq2xxs_grid[256]`

### 4.1 Structure

The codebook is a constant lookup table of 256 entries, each a `uint64_t` (8 bytes). Each entry encodes 8 unsigned magnitude values packed as 8 × uint8_t within the 64-bit word.

```c
GGML_TABLE_BEGIN(uint64_t, iq2xxs_grid, 256)
    0x0808080808080808, // entry 0: all values = 0x08 = 8
    0x080808080808082b, // entry 1: seven 8s, one 0x2b = 43
    ...
GGML_TABLE_END()
```

### 4.2 Value Alphabet

The codebook values use only 3 distinct magnitudes:

| Byte value | Decimal | Meaning |
|-----------|---------|---------|
| `0x08` | 8 | Low magnitude |
| `0x19` | 25 | Medium magnitude |
| `0x2b` | 43 | High magnitude |

Each 8-element codebook entry is a permutation/combination of these 3 values. The 256 selected patterns are the information-theoretically optimal subset (minimizing expected quantization error for normally distributed weights).

### 4.3 Lookup Mechanics

Given codebook index `idx` (8-bit, from aux8):
```c
uint64_t grid_word = iq2xxs_grid[idx];
uint8_t magnitude[8];
for (int i = 0; i < 8; i++) {
    magnitude[i] = (grid_word >> (8*i)) & 0xFF;  // extract byte i
}
```

The magnitudes are always positive (8, 25, or 43). Signs are applied separately.

---

## 5. Sign Encoding: `ksigns_iq2xs[128]`

### 5.1 Structure

A 128-entry table of `uint8_t` values. Each entry encodes sign bits for 8 values, addressed by a 7-bit index extracted from `aux32_s`.

### 5.2 Even-Parity Encoding

The sign table uses **even-parity** encoding: only 7 bits are stored (the index), and the 8th sign bit is reconstructed to maintain even parity (even number of set bits in the full 8-bit sign pattern).

```c
GGML_TABLE_BEGIN(uint8_t, ksigns_iq2xs, 128)
    0,   129, 130, 3,   132, 5,   6,   135, ...
GGML_TABLE_END()
```

For the Metal/GPU dequant path, the sign byte is used directly with bitmask testing:
```c
uint8_t signs = ksigns_iq2xs[sign_index];  // sign_index is 7 bits
// bit i of signs: 0 = positive, 1 = negative (for value position i)
```

### 5.3 Bitmask Application

```c
static constant uchar kmask_iq2xs[8] = {1, 2, 4, 8, 16, 32, 64, 128};

// For each position i in the 8-element quad:
float sign = (signs & kmask_iq2xs[i]) ? -1.0f : +1.0f;
```

### 5.4 CUDA Integer-Arithmetic Path

On CUDA, the sign is unpacked for dp4a (int8 dot product) via:
```c
uint32_t dev_unpack_iq2_signs(uint32_t v) {
    uint32_t p = __popc(v) & 1;     // parity bit
    uint32_t s = v ^ (p << 7);      // reconstruct 8th bit
    return s * 0x01010101;           // broadcast byte to all 4 lanes
}
```

This broadcasts the sign byte into 4 identical lanes for vectorized sign comparison with `__vcmpne4`.

## 6. Scale Semantics

### 6.1 Two-Level Scale

IQ2_XXS has a **two-level** scale hierarchy:

1. **Super-block scale** (`d`): A single f16 value per 256-element block. Stored at offset 0.
2. **Sub-group scale factor**: A 4-bit integer (0–15) stored in bits [31:28] of `aux32_s`, shared across all 32 values in the sub-group.

### 6.2 Combined Scale Formula

The effective per-value scale (`dl`) is:

```
dl = d × (0.5 + sub_group_scale) × 0.25
   = d × (0.5 + (aux32_s >> 28)) × 0.25
```

Where:
- `d` = f16 super-block scale (float after conversion)
- `sub_group_scale` = 4-bit integer from bits [31:28] of aux32_s (range 0..15)

This gives an effective sub-group scale range of `d × [0.125, 3.875]` (i.e., `d × 0.25 × [0.5, 15.5]`).

### 6.3 Alternative Integer Form (CUDA vec_dot)

The CUDA dot-product path uses an integer-scaled variant for dp4a accumulation:
```c
int ls = aux32 >> 27 | 1;   // = (sub_group_scale * 2 + 1), range 1..31 (odd)
sumi = sumi * ls / 8;       // equivalent to multiply then divide
```

This is algebraically equivalent: `ls/8 = (2*scale+1)/8 = (0.5+scale)*0.25`.

## 7. Dequantization Arithmetic

### 7.1 Complete Scalar Formula

For element `i` within value-position `j` of sub-group `ib32` in block `blk`:

```
value[i] = d × (0.5 + (aux32_s >> 28)) × 0.25 × grid_magnitude[j] × sign[j]
```

Where:
- `d` = `float(blk->d)` (f16 → f32)
- `aux32_s` = reassembled from `qs[4*ib32 + 2..3]`
- `grid_magnitude[j]` = byte `j` of `iq2xxs_grid[grid_index]` (value ∈ {8, 25, 43})
- `sign[j]` = `(ksigns_iq2xs[sign_index] & (1 << j)) ? -1 : +1`

### 7.2 Metal Shader Dequant (Reference)

```metal
template <typename type4x4>
void dequantize_iq2_xxs(device const block_iq2_xxs * xb, short il, thread type4x4 & reg) {
    const float d = xb->d;
    const int ib32 = il/2;
    il = il%2;
    device const uint16_t * q2 = xb->qs + 4*ib32;
    const uint32_t aux32_g = q2[0] | (q2[1] << 16);
    const uint32_t aux32_s = q2[2] | (q2[3] << 16);
    thread const uint8_t * aux8 = (thread const uint8_t *)&aux32_g;
    const float dl = d * (0.5f + (aux32_s >> 28)) * 0.25f;

    // First 8 values (quad 0 or 2)
    constant uint8_t * grid = (constant uint8_t *)(iq2xxs_grid + aux8[2*il+0]);
    uint8_t signs = ksigns_iq2xs[(aux32_s >> 14*il) & 127];
    for (int i = 0; i < 8; ++i) {
        reg[i/4][i%4] = dl * grid[i] * (signs & kmask_iq2xs[i] ? -1.f : 1.f);
    }

    // Second 8 values (quad 1 or 3)
    grid = (constant uint8_t *)(iq2xxs_grid + aux8[2*il+1]);
    signs = ksigns_iq2xs[(aux32_s >> (14*il+7)) & 127];
    for (int i = 0; i < 8; ++i) {
        reg[2+i/4][i%4] = dl * grid[i] * (signs & kmask_iq2xs[i] ? -1.f : 1.f);
    }
}
```

Each call to `dequantize_iq2_xxs` produces 16 float values (stored in a 4×4 register tile). The `il` parameter selects which half (0 or 1) of the 32-element sub-group to decode.

### 7.3 Decoding Order Summary

```
Block (256 values)
 └── 8 × Sub-group (32 values each, 8 bytes encoded)
      ├── aux32_g: 4 codebook indices (4 × 8-bit)
      ├── aux32_s[27:0]: 4 sign indices (4 × 7-bit)
      ├── aux32_s[31:28]: sub-group scale (4-bit)
      └── 4 × Quad (8 values each)
           ├── grid lookup: iq2xxs_grid[index] → 8 magnitudes
           └── sign lookup: ksigns_iq2xs[sign_idx] → 8 sign bits
```

## 8. Row Stride and Alignment

### 8.1 Row Stride

For a row of `K` elements:
```
blocks_per_row = K / QK_K = K / 256
row_bytes = blocks_per_row × 66
```

Example: K=4096 → 16 blocks × 66 = 1056 bytes per row.

### 8.2 Alignment Problem

`sizeof(block_iq2_xxs) = 66` — this is **not** a power of two and not even 4-byte aligned. The `qs` array starts at offset 2 within the struct, meaning uint32_t code words within `qs` require two uint16_t loads on architectures requiring natural alignment.

This is documented in DS4 as a known performance limiter:

> "block_iq2_xxs is 66 bytes, so the code stream is only 2-byte aligned and every 32-bit weight word costs two 16-bit loads (get_int_b2)." — `proto_iq2_aligned.cu`

DS4's CUDA path addresses this with an **aligned SoA repack** (`repack_iq2_xxs_aligned_kernel`): block scales are separated from code words, and the code stream is 64-byte aligned per block.

## 9. Contrast with Q2_K

| Property | Q2_K | IQ2_XXS |
|----------|------|---------|
| **Encoding** | Linear: `x = d×scale×q + d×min` | Codebook: `x = d×sub_scale×grid[idx]×sign` |
| **Weight representation** | Raw 2-bit integer per value (4 values/byte) | 8-bit codebook index per 8 values |
| **Scale granularity** | Per 16 values (4-bit scale + 4-bit min in `scales[]`) | Per 32 values (4-bit sub-group scale) |
| **Block structure** | `scales[16] + qs[64] + d + dmin` = 84 bytes | `d + qs[32×uint16]` = 66 bytes |
| **Bits per weight** | 2.625 bpw | 2.0625 bpw |
| **Decode complexity** | Shift/mask, linear multiply-add | Table lookup + sign expansion |
| **Value space** | 4 levels (0,1,2,3) + offset/scale | 3 magnitudes (8,25,43) × ±1 from codebook |
| **GPU decode** | Shift-extract → linear transform | LUT read → sign XOR → scale multiply |
| **Native int2 compatible** | Partially (weights are raw 2-bit; scales are not) | **No** (weights are codebook indices, not raw 2-bit values) |

### Key difference

Q2_K stores the actual 2-bit quantized weight value inline — you can extract it with bitwise operations and apply a linear dequantization formula. IQ2_XXS stores a **codebook index** that requires a memory-indirect lookup to recover the original weight magnitudes. The codebook is a non-trivial 256×8-byte constant table.

## 10. Native Metal int2 Tensor Compatibility Assessment

### 10.1 Fundamental Incompatibility

**Native Metal `int2` tensors cannot represent IQ2_XXS data.**

Metal's `int2` tensor type assumes each 2-bit value IS the (linearly-scaled) weight. IQ2_XXS's 2-bit fields are NOT weights — they are:
- Codebook indices (8 bits per 8 values → effectively 1 bit per value in the index sense, but packed as 8-bit per quad)
- Sign pattern indices (7 bits per 8 values)
- Sub-group scale factors (4 bits per 32 values)

There is no way to:
1. Map the codebook lookup to a linear scale/zero-point that `int2` tensors assume
2. Represent the 3-valued magnitude alphabet {8, 25, 43} as a 2-bit linear quantization
3. Encode the sign separately from the magnitude in `int2` semantics

### 10.2 What Would Be Needed

To use TensorOps/`matmul2d` with IQ2_XXS, the code must:
1. **Custom-dequantize** into a cooperative tensor (f16/f32) before matmul — this is exactly what the existing `kernel_mul_mm_id_mpp` path does
2. Stage dequantized tiles into threadgroup memory (`tgmem`)
3. Feed the f16 result to `matmul2d`

This is the **only** viable path. The existing DS4 MPP kernels (`kernel_mul_mm_id_iq2_xxs_f32_mpp`, `kernel_mul_mm_id_iq2_xxs_f16_mpp`) already implement this pattern: staged dequant → tgmem → matmul2d with NR0=64, NR1=32, NK=32 tiles.

### 10.3 Conclusion for Task 9.3

Native int2 tensor representation is **fundamentally impossible** for IQ2_XXS. The codebook-based nature means:
- No zero-copy tensor view is possible
- No "reinterpret cast" to int2 is meaningful
- The only viable TensorOps path is custom dequant → cooperative f16 tensor → matmul2d
- This path already exists in production (the MPP kernels)

The question for task 9.4 is whether the existing cooperative dequant path can be made faster on M5 (larger tiles, better staging, overlapped dequant with matmul), not whether a native int2 bypass is possible.

## 11. Threadgroup Staging in Production

The existing Metal MPP kernel loads the codebook into threadgroup memory at kernel start:

```metal
// Each thread loads 4 grid entries (128 threads × 4 = 512 > 256 needed)
int nval = 4;
int pos = (32*sgitg + tiisg)*nval;
for (int i = 0; i < nval; ++i)
    svalues[pos + i] = ds4_metal_iq2xxs_grid[pos + i];

// Similarly for sign table (128 entries)
nval = 2;
pos = (32*sgitg + tiisg)*nval;
for (int i = 0; i < nval; ++i)
    ssigns[pos + i] = ds4_metal_ksigns_iq2xs[pos + i];
```

This amortizes constant-memory traffic across all tiles processed by the threadgroup. The decode matvec kernels use the same pattern.

---

## 12. Summary

IQ2_XXS achieves excellent compression (2.0625 bpw) through information-theoretic codebook design rather than linear quantization. The tradeoff is decode complexity: every 8 values require a 256-entry codebook lookup plus sign table lookup, making it fundamentally incompatible with native low-bit tensor types that assume linear dequantization. DS4 already handles this correctly via staged custom dequant into TensorOps cooperative tiles.
