# 5.6 Native-MX Decision

## Status: DEFERRED — Pending macOS 27 SDK

**Validates:** R7  
**Prerequisites:** 5.1, 5.2, 5.3, 5.4, 5.5  
**Active path:** Custom dequant to cooperative tensor (Candidate B, tasks 6.2–6.5)

---

## 1. Decision

**Native-MX is neither proven nor rejected — it is blocked by SDK availability.**

The installed macOS 26.5 SDK (Xcode 26.6, Metal compiler 32023.883) provides no FP4/E2M1 tensor element type, no E8M0 scale-plane type, no multi-plane tensor constructors, and no block-factor mechanism. Tier 4 (native low-bit floating MX) is entirely absent. The native-MX path cannot be implemented, benchmarked, or accepted/rejected until Apple ships a macOS 27 SDK containing these types.

**Mark: none of {direct view / resident-cache layout / bounded repack / reject} can be selected.** The decision is deferred with custom dequant as the active implementation path.

---

## 2. What Was Proven

### 2.1 DS4's MXFP4 values match OCP E2M1 standard

All 16 E2M1 codes were verified against an independent bit-field decode implementation across 10 representative E8M0 scales (0, 1, 64, 100, 126, 127, 128, 150, 200, 254). The DS4 value table `{0, 0.5, 1, 1.5, 2, 3, 4, 6} × {+, −}` matches the OCP MX E2M1 specification exactly.

**Evidence:** `tests/test_mxfp4_native_mx_probe.c` — test 1 (256 probes), test 2 (256 probes), test 3 (1024 probes). All pass.

### 2.2 DS4's E8M0 semantics match standard power-of-2 scaling

The scale conversion `e8m0_to_f32()` produces `2^(e−127)` for e ∈ [1, 254], matching the IEEE 754 exponent-bias convention used in OCP MX. Special case: e=0 maps to 2^(−127) (smallest positive subnormal), not zero. This is a minor variation that must be verified against Metal's convention when available.

**Evidence:** `tests/test_mxfp4_native_mx_probe.c` — scale variation tests confirm correct decode at minimum, unity, and maximum scales.

### 2.3 DS4's block layout is structurally incompatible with zero-copy

The interleaved [scale][data] 17-byte block structure cannot be expressed as a native MX tensor view:

| Structural barrier | Explanation |
|-------------------|-------------|
| Interleaved scale/data | Metal MX expects separate contiguous data and scale planes; DS4 interleaves 1 scale byte every 17 bytes |
| Non-power-of-2 block stride | 17-byte block period is incompatible with element-unit stride descriptors |
| No byte-granularity stride | Inline tensor strides operate in element units, not bytes; extracting 1-of-17 or 16-of-17 bytes is not expressible |
| Split-half nibble ordering | DS4 uses `low=elements 0–15, high=elements 16–31`; Metal's convention is unknown and may require an additional shuffle |

**Conclusion:** Zero-copy native MX from the mmap-backed GGUF layout is structurally impossible regardless of future SDK additions. Any native-MX use requires a repack step.

**Evidence:** Task 5.4 analysis, confirmed by Metal tensor inline constructor semantics from SDK header inspection (task 5.2).

### 2.4 Custom dequant to cooperative tensors IS available now

The macOS 26.5 SDK supports:
- Cooperative tensors as matmul2d inputs (Tier 2)
- `half × half → f32` and `bfloat × bfloat → f32` matmul2d
- Inline tensor construction from existing device pointers
- Custom shader code producing cooperative tensor values

This enables Candidate B (design §8.4):
```
MXFP4 interleaved blocks (device memory, mmap-backed)
  → custom shader E2M1 dequant + E8M0 scale apply
  → cooperative tensor (half/bfloat values)
  → matmul2d on M5 Neural Accelerator
  → cooperative output
  → post-matmul fusion (SiLU, route weight, etc.)
```

No layout change, no model copy, no format conversion. R3 fully satisfied.

**Evidence:** Task 5.2 SDK inspection confirms cooperative tensor input support; task 6.2–6.3 implement this path.

## 3. What Remains Unknown (Requires macOS 27 SDK)

### 3.1 Metal's FP4 nibble ordering convention

DS4 uses split-half ordering: `qs[j] & 0x0F → element j`, `qs[j] >> 4 → element j+16`. Metal may use sequential ordering: `qs[j] & 0x0F → element 2j`, `qs[j] >> 4 → element 2j+1`. If conventions differ, any native-MX repack must include a nibble shuffle.

**Impact:** Determines whether a resident-cache repack is a simple plane separation or a plane separation plus nibble reorder.

### 3.2 Whether stride descriptors can express sub-block interleaving

Even with native MX types, DS4's interleaved layout requires either:
- A stride descriptor that can skip 1 byte per 17-byte block for scale extraction, OR
- A gather mechanism that selects non-contiguous byte ranges

Current SDK stride semantics make this unlikely, but the question is formally unanswered for macOS 27's multi-plane constructors.

### 3.3 Performance of native MX matmul vs custom dequant to half cooperative tensor

The key benchmark: does hardware-accelerated MX decode (feeding native MXFP4 directly to the tensor core) outperform shader-based dequant into a half cooperative tensor that feeds the same matmul2d?

Factors:
- Native MX avoids the shader ALU cost of E2M1 LUT + E8M0 scale multiply
- Native MX may achieve higher effective bandwidth via hardware nibble decode
- But native MX requires a prior repack step whose cost must be amortized
- Custom dequant has zero repack cost and reads directly from mmap

**This is the central performance question for the native-MX decision.**

### 3.4 Resident-cache repack cost/benefit at realistic expert cache hit rates

Task 5.5 was deferred because there is no native MX type to repack INTO. When available, the evaluation must answer:

| Question | Method |
|----------|--------|
| Repack time per expert | Benchmark: separate planes + optional nibble shuffle for one expert at gate/up (128 blocks → 128 scale bytes + 2048 data bytes) and down (64 blocks → 64 + 1024) dimensions |
| Break-even hit count | `repack_cost / (native_savings_per_matmul)` = minimum token routes to amortize |
| Memory overhead | Dual-layout entries vs single-layout: bounded by existing cache budget? |
| Interaction with SSD streaming | Can streaming experts skip native layout? Fallback path needed for cold experts |

## 4. Active Path: Custom Dequant to Cooperative Tensor (Candidate B)

The implementation proceeds with Candidate B (design §8.4, tasks 6.2–6.5):

```
┌─────────────────────────────────────┐
│  MXFP4 blocks (mmap device buffer)  │
│  [e₀][qs₀] [e₁][qs₁] ...           │
└───────────────┬─────────────────────┘
                │ shader reads
                ▼
┌─────────────────────────────────────┐
│  Custom dequant (per-thread)         │
│  E8M0 → float scale                 │
│  nibble → LUT/half_lut → half       │
│  scale × value → half element       │
└───────────────┬─────────────────────┘
                │ store to cooperative tensor
                ▼
┌─────────────────────────────────────┐
│  cooperative tensor (half)           │
│  matmul2d input                      │
└───────────────┬─────────────────────┘
                │ hardware matmul (M5 Neural Accelerator)
                ▼
┌─────────────────────────────────────┐
│  cooperative output (f32)            │
│  → SiLU / route weight / fuse       │
│  → final store to device memory     │
└─────────────────────────────────────┘
```

**Advantages over waiting for native MX:**
- Available immediately (macOS 26.3+, verified on macOS 26.5)
- No model format change or repack required
- Preserves mmap/SSD-streaming/resident-cache semantics (R3, R19)
- M5 Neural Accelerator is exercised via matmul2d regardless of input source
- Proven mechanism: task 6.2 (staged control) and 6.3 (cooperative input) implemented

**Correctness:** Dequant uses the same LUT/decode logic as the existing MXFP4 kernel. All 16 codes verified against CPU reference (task 5.3).

## 5. Future Work: Re-evaluate When macOS 27 SDK Ships

When Apple ships macOS 27 with native FP4/E8M0/MX tensor types:

### 5A. Immediate conformance check
1. Compile the native-MX probe stub in `tests/test_mxfp4_native_mx_probe.c` (currently `#ifdef DS4_METAL_SDK_NATIVE_LOWBIT`)
2. Verify nibble ordering: does Metal use split-half or sequential?
3. Verify E8M0 scale=0 convention: 2^(−127) or zero?
4. Run basis-vector matmul and compare against CPU reference

### 5B. Resident-cache repack prototype
1. Implement plane-separation repack (+ nibble shuffle if needed) for one expert
2. Benchmark repack latency at gate/up and down dimensions
3. Create native MX tensor from repacked layout
4. Benchmark native MX matmul2d vs custom dequant matmul2d at matched dimensions

### 5C. Decision gate
- If native MX matmul is >1.25× faster than custom dequant AND repack amortizes within typical expert hit counts (≥10 token routes per hot expert) → adopt resident-cache repack for hot experts, keep custom dequant for cold/streaming
- If native MX is faster but repack does not amortize → keep custom dequant everywhere
- If native MX is not significantly faster → reject native MX path, custom dequant becomes permanent

### 5D. Integration
If adopted, the resident-cache repack would add an optional native-MX layout alongside the existing layout in the expert cache entry (design §14.2):
```c
struct expert_cache_entry {
    // existing:
    void *gate_weights;  // mmap pointer, interleaved blocks
    void *up_weights;
    void *down_weights;
    // optional native-MX (bounded budget):
    void *gate_mx_data;   // separated data plane
    void *gate_mx_scale;  // separated scale plane
    // ... (only for hot experts within budget)
};
```

## 6. Requirement Traceability (R7)

> **R7:** WHEN adding a native quantized TensorOps path THE SYSTEM SHALL first produce a byte-level compatibility result covering data encoding, scale encoding, block size, row stride, alignment, and transpose semantics.

| R7 sub-requirement | Status | Evidence |
|-------------------|--------|----------|
| Data encoding (E2M1) | ✓ Verified compatible | Task 5.1 value table, task 5.3 all-codes test |
| Scale encoding (E8M0) | ✓ Verified compatible (minor e=0 question) | Task 5.1 §3, task 5.3 scale tests |
| Block size (32 elements) | ✓ Matches OCP MX standard | Task 5.1 §1 |
| Row stride | ✓ Documented, 17×blocks/row | Task 5.1 §5 |
| Alignment | ✗ Incompatible (non-power-of-2, interleaved) | Task 5.2 §3, task 5.4 §2 |
| Transpose semantics | — Cannot test without native types | Deferred |
| Nibble ordering | ? Unknown Metal convention | Task 5.3 §4, deferred |
| Layout compatibility | ✗ Zero-copy impossible | Task 5.4 (rejected) |

> **R7:** WHEN direct native representation is not compatible THE SYSTEM SHALL evaluate custom DS4 dequantization into a cooperative tensor before falling back to threadgroup-memory staging.

**Status:** Custom dequant to cooperative tensor (Candidate B) is the selected active path. Implemented in tasks 6.2–6.3. Threadgroup staging (Candidate C) serves as the compatibility fallback.

## 7. Summary

| Candidate | Status | Reason |
|-----------|--------|--------|
| Direct view (zero-copy native MX from mmap) | **REJECTED** | Structural layout incompatibility (interleaved, non-aligned, non-power-of-2) |
| Resident-cache repack to native MX | **DEFERRED** | No native MX types in SDK to repack into; cannot benchmark |
| Bounded per-tile repack | **DEFERRED** | Same — no target format available |
| Custom dequant to cooperative tensor | **ACTIVE** | Available now, verified, no layout change, R3-compliant |
| Reject native MX entirely | **NOT YET** | Cannot reject a path that hasn't been benchmarked |

**The decision is DEFERRED, not rejected.** Native MX may prove valuable via resident-cache repack once macOS 27 provides the types and benchmarks can be run. Until then, custom dequant (Candidate B) is the production path.
