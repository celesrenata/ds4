# 6.3 Cooperative-Input Dequant — BLOCKED by SDK Constraint

## Finding

Metal SDK enforces: **"Input cooperative tensors require a single SIMD group"**

The error occurs at shader compilation:
```
static_assert failed due to requirement
'__tensor_ops_detail::__is_same_v<metal::execution_simdgroups<4>,
 metal::execution_simdgroups<1>>'
"Input cooperative tensors require a single SIMD group"
```

## Impact

The task 6.3 cooperative-input kernel uses `execution_simdgroups<4>` (128 threads)
to match the existing routed-expert tile geometry (NR0=64, NR1=32, NK=32). This is
the same configuration used by all other production TensorOps kernels in DS4.

Cooperative tensor inputs are only permitted with `execution_simdgroups<1>` (32 threads
= 1 SIMD group). This constraint means:

1. **The matmul tile must shrink dramatically** — a 1-simdgroup matmul produces a much
   smaller output tile, requiring proportionally more dispatches.
2. **Throughput loss** — 4× fewer threads per threadgroup means worse occupancy hiding
   and 4× more dispatched threadgroups to cover the same work.
3. **The staged-dequant control (task 6.2) remains superior** — it uses 4 simdgroups
   with full tile geometry and is unaffected by this constraint.

## Why This Constraint Exists

Cooperative tensor inputs distribute data across threads within a SIMD group. The
matmul hardware reads from the cooperative tensor's per-thread register state. With
multiple SIMD groups, the cooperative tensor would need cross-simdgroup communication,
which the hardware does not support for input operands.

Cooperative tensor *destinations* work with multiple simdgroups because each simdgroup
independently accumulates its portion and the final store merges them.

## Decision

**The cooperative-input dequant path (Candidate B from design §8.4) is NOT viable
for the multi-simdgroup tile geometry used in DS4's MoE dispatch.**

The winning mechanism for task 6.5 is:
- **Staged dequant to threadgroup → tensor view → matmul2d** (task 6.2 pattern)
- This is exactly what the existing `kernel_mul_mm_id_mpp` already does for Q2_K/IQ2_XXS

The theoretical advantage of cooperative inputs (eliminating threadgroup staging) is
real but cannot overcome the 4× simdgroup penalty at DS4's production tile sizes.

## Implication for MoE TensorOps (Sections 7–8)

The routed-MoE TensorOps implementation will use the staged-both-operands pattern:
```
weights (device, quantized)
  → dequant to threadgroup half tile
  → tensor view from threadgroup
activations (device, scattered per-token)
  → gather to threadgroup half tile  
  → tensor view from threadgroup
both views → matmul2d with execution_simdgroups<4>
  → cooperative F32 destination
  → store and scatter
```

This is proven by the existing `kernel_mul_mm_id_mpp` (Q2_K/IQ2_XXS) and the
task 6.2 control kernel (Q8_0). The matmul still runs on the M5 Neural Accelerator
— the cooperative input bypass was an optimization ON TOP of TensorOps, not a
requirement for using TensorOps.

## Code Status

The kernel `kernel_mul_mm_id_q8_0_coop_input_candidate` is retained in `moe.metal`
behind a `DS4_EXPERIMENT_COOP_INPUT_SINGLE_SG` guard. It does not compile in normal
builds. It serves as documentation of the approach and could be revived if future
Apple hardware/SDK lifts the single-simdgroup restriction.
