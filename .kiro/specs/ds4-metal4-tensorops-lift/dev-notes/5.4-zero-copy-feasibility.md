# 5.4 Zero-Copy Native MX Feasibility — Decision

## Status: REJECTED — Zero-copy native MX view is NOT feasible

**Validates:** R3, R7, R19  
**Prerequisites:** 5.1 (byte layout), 5.2 (SDK inspection), 5.3 (conformance probe)  
**Date:** Determined from accumulated evidence across tasks 5.1–5.3

---

## 1. Conclusion

**Zero-copy native MX view of DS4 MXFP4 weights is NOT feasible** on the installed macOS 26.5 SDK, nor on any foreseeable SDK revision that requires separate data/scale planes.

This is a structural incompatibility, not a missing API that a future OS update can trivially fix.

---

## 2. Why Zero-Copy Fails

### 2.1 DS4 interleaves [scale][data] per 17-byte block

DS4's `block_mxfp4` stores each 32-element group as:

```
Byte 0:      E8M0 shared scale exponent
Bytes 1–16:  32 × E2M1 values, nibble-packed (16 bytes)
```

Blocks are packed contiguously along each row with no inter-block padding:

```
[e₀][qs₀[0..15]] [e₁][qs₁[0..15]] [e₂][qs₂[0..15]] ...
     17 bytes          17 bytes          17 bytes
```

### 2.2 Metal inline tensors cannot express this with stride descriptors

Metal tensor strides operate in **element units**, not bytes. The available `tensor_inline` constructor accepts:

```metal
tensor(data_ptr, extents, strides)  // strides in elements
```

To express DS4's layout as a native MX tensor, the stride descriptor would need to:
- Skip 1 scale byte every 17 bytes for the data plane
- Extract 1 scale byte every 17 bytes for the scale plane

This is a **byte-granularity interleave pattern**, not an element stride. No documented Metal tensor stride can express a 17-byte period with heterogeneous byte roles within it.

### 2.3 Separate-plane MX tensors require contiguous data and scale planes

Metal's native MX format (when it arrives in macOS 27) is expected to require:

```
Data plane:  [all nibble bytes contiguously for the entire tensor]
Scale plane: [all E8M0 bytes contiguously, one per 32 elements]
```

DS4's interleaved layout has scale bytes at offsets 0, 17, 34, 51, ... and data bytes filling the gaps between them. There is no way to present either the data or scale bytes as contiguous without a copy/repack.

### 2.4 17-byte block size prevents aligned nibble addressing

- 17 is not a power of 2.
- Metal 8-byte inline tensor alignment cannot cleanly divide 17-byte blocks.
- Pointer arithmetic into DS4 blocks requires byte-cast addressing (the existing kernel does this explicitly).
- Hardware-accelerated nibble gather assumes aligned, contiguous nibble storage — not 16-byte data islands separated by 1-byte scale sentinels.

### 2.5 Additionally: nibble ordering may differ

DS4 uses a split-half convention (`qs[j] & 0x0F` → element j, `qs[j] >> 4` → element j+16). If Metal's native MX uses sequential nibble ordering (element 2j, element 2j+1), an additional per-block nibble shuffle would be required on top of plane separation.

## 3. Current SDK Status

The macOS 26.5 SDK (Xcode 26.6) provides **none** of the native MX types:

| Required for native MX | Available? |
|------------------------|-----------|
| FP4 / E2M1 tensor element type | ✗ |
| E8M0 scale-plane type | ✗ |
| Multi-plane tensor constructors | ✗ |
| Block-factor / scale-grouping | ✗ |

Only `int4b_format` and `uint4b_format` (plain 4-bit integers) exist. These perform integer arithmetic, not E2M1 floating-point decode.

Even when macOS 27 adds native MX types, the structural layout incompatibility (§2.1–2.4) means zero-copy from DS4's on-disk format will remain impossible.

## 4. Viable Paths Forward

From design.md §8.3–8.5, three approaches remain:

### 4.1 Resident expert cache repack (design §8.3 + §14.2)

When an expert enters the hot resident cache, create a native-MX-friendly layout (separate contiguous data plane + scale plane). 

- **Cost:** One-time repack per expert cache entry, amortized across all tokens routed to that expert.
- **Bounded:** Limited to the existing resident cache budget — no full-model copy.
- **Prerequisite:** macOS 27 SDK with actual native MX types to target.
- **Evaluation:** Task 5.5 (benchmark bounded repack).

### 4.2 Custom dequant to cooperative tensor — Candidate B (design §8.4)

```
MXFP4 packed blocks (device memory, existing layout)
  → custom shader dequant to half/bfloat
  → cooperative tensor
  → matmul2d
  → cooperative output
  → post-matmul fusion
```

- **Available NOW** on macOS 26.5.
- **No layout change required** — reads DS4's interleaved blocks directly.
- **Selected as the active implementation path** in task 6.
- **Preserves R3** — no model copy, no format conversion, mmap intact.

### 4.3 Threadgroup-staged dequant — Candidate C (design §8.5)

```
MXFP4 packed blocks
  → custom dequant to threadgroup tile (half/bfloat)
  → tensor load from threadgroup
  → matmul2d
```

- **Compatibility tier** for older OS versions without cooperative tensor inputs.
- **Baseline** for performance comparison against Candidate B.
- **Still benefits from M5 Neural Accelerator** via the matmul2d itself.

---

## 5. Impact on TensorOps Lift

This finding does **NOT** block the TensorOps lift:

- Custom dequant (task 6) is the active path and requires no native MX types.
- The existing Metal MXFP4 kernel already dequants from the interleaved format — TensorOps wraps the same decode logic into a cooperative/staged pipeline.
- Performance gains come from `matmul2d` using the M5 Neural Accelerator, regardless of whether the input was native MX or custom-dequanted.

---

## 6. Future Work (Task 5.5)

When a macOS 27 SDK with native MX types becomes available, task 5.5 should evaluate:

1. **Resident-cache repack cost** — time to separate planes for one expert at typical dimensions (128 blocks × 17 bytes → 128 bytes scale + 2048 bytes data for gate/up).
2. **Cache hit amortization** — given typical expert reuse rates, does the repack cost amortize?
3. **Native matmul2d performance vs custom dequant** — does hardware MX decode outperform a shader-based dequant into cooperative tensors?
4. **Nibble ordering conformance** — verify whether Metal MX uses split-half or sequential ordering; add nibble shuffle to repack if needed.
5. **Memory budget** — ensure dual-layout cache entries fit within the existing resident cache budget or a documented sub-budget.

If native MX hardware decode is significantly faster than shader dequant AND repack amortizes at realistic hit rates, the resident-cache repack becomes worthwhile. Otherwise, custom dequant (Candidate B) remains optimal.
