## 1. Q8_0 — SKIPPED (Not Used for MoE Expert Weights)

From the MoE inventory (task 0.3, section 1):

> Q8_0 — Simple block-of-32 8-bit + f16 scale — **Attention output; non-MoE use in this file**

Q8_0 is used in DS4 for:
- Attention output low-rank projections (already lifted to TensorOps via
  `kernel_attn_out_low_q8_0_mpp_direct_rhs_n64`)
- Dense projection prefill (already has TensorOps via `kernel_mul_mm_mpp_direct_rhs`)

Q8_0 is **NOT** used for DeepSeek-V4 MoE expert gate/up weights. No Q8_0 MoE
gate/up TensorOps kernel is created.

## 2. Q4_K — IMPLEMENTED (TensorOps Pair+SwiGLU)

Q4_K is used for MoE expert gate/up weights in DS4 quantized configurations:
- Existing simdgroup kernel: `kernel_mul_mm_id_q4_K_pair_swiglu_f16`
- New TensorOps kernel: `kernel_mul_mm_id_q4_K_pair_swiglu_mpp`

### 2.1 Kernel Design

Combines the winning mechanism from task 6.5 (staged dequant → threadgroup →
matmul2d with execution_simdgroups<4>) with the paired gate+up SwiGLU epilogue
from `kernel_mul_mm_id_pair_swiglu_f16_impl`.

Structure:
```
Per K iteration:
  1. Dequant gate weights → sa_gate[NR0*NK] using dequantize_q4_K
  2. Dequant up weights → sa_up[NR0*NK] using dequantize_q4_K
  3. Stage activations → sb[NR1*NK] (float → half, scattered gather)
  4. threadgroup_barrier
  5. mm.run(sB, sA_gate, cT_gate)  — matmul2d for gate
  6. mm.run(sB, sA_up, cT_up)      — matmul2d for up (same activation)
  7. threadgroup_barrier

Output phase:
  1. cT_gate.store(tC_gate) → threadgroup float tile
  2. cT_up.store(tC_up) → threadgroup float tile
  3. threadgroup_barrier
  4. SwiGLU epilogue: clamp, SiLU, multiply, route weight → half mid
```

### 2.2 Tile Geometry

- NR0 = 64 (weight rows / output dimension per threadgroup)
- NR1 = 32 (activation columns / tokens per tile)
- NK = 32 (reduction tile)
- execution_simdgroups<4> (128 threads)
- Threadgroup memory: 16384 bytes (output phase: 2 × NR0 × NR1 × 4)

### 2.3 Dequant Reuse

Reuses `dequantize_q4_K` (existing function from moe.metal) without
duplication. The template parameterization `<block_q4_K, QK_NL, dequantize_q4_K>`
plugs the existing dequant directly into the TensorOps tile staging loop.

### 2.4 Host-Side Dispatch

- Enabled when `ds4_gpu_mpp_available()` returns true (M5 + TensorOps SDK)
- Controlled by `mpp_mask & 3` (same gate/up TensorOps bits as IQ2_XXS)
- Disabled via `DS4_METAL_DISABLE_Q4_K_PAIR_SWIGLU_MPP` environment variable
- Falls back to legacy `kernel_mul_mm_id_q4_K_pair_swiglu_f16` (simdgroup)
  when TensorOps pipeline creation fails or is disabled
- Increments `g_ctr_moe_gate_up_tensorops` counter on successful dispatch

### 2.5 Correctness Contract

The SwiGLU epilogue is identical to the legacy simdgroup kernel:
- Same clamp/SiLU/multiply/route-weight arithmetic
- Same output format (half precision mid tensor)
- Same per-token scatter pattern

The matmul reduction order differs (matmul2d vs simdgroup_multiply_accumulate),
so bit-identity with the legacy kernel is **not** guaranteed. Numerical
equivalence must be validated by task 7.7 parity tests (Class B).

### 2.6 Files Modified

- `metal/moe.metal`: New `kernel_mul_mm_id_pair_swiglu_mpp` template and Q4_K
  instantiation
- `ds4_metal.m`: Host-side dispatch logic in the pair_swiglu pipeline selection

## 3. Rollback Controls

| Variable | Effect |
|----------|--------|
| `DS4_METAL_DISABLE_Q4_K_PAIR_SWIGLU_MPP` | Disables Q4_K TensorOps pair+SwiGLU; uses legacy simdgroup kernel |
| `DS4_METAL_DISABLE_TENSOROPS` | Global TensorOps disable (existing) |
| `DS4_METAL_DISABLE_MOE_MM_ID_PAIR_SWIGLU` | Disables all pair+SwiGLU fusion (existing) |
