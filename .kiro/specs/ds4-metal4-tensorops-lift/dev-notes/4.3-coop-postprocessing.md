# Task 4.3 — Cooperative Post-Processing Analysis

## Decision: REJECT

Weighted ReLU accumulation **cannot** consume cooperative tensor results without
materializing `dot` to threadgroup memory. The Metal cooperative tensor API does not
provide a mechanism to map element indices to known (row, col) positions, making
the fusion structurally impossible without relying on implementation-defined behavior.

---

## 1. The Optimization Hypothesis

Current kernel flow per head-pair:

```
matmul2d × 4 k-steps → cooperative tensor ct (accumulates 32×32 result)
    ↓
ct.store(td)                    ← 4096 bytes to threadgroup (column-major)
    ↓
threadgroup_barrier
    ↓
each thread reads dot[cc*TQ + r] → max(·, 0) × weight → acc[j]
```

Proposed fusion:

```
matmul2d × 4 k-steps → cooperative tensor ct
    ↓
each thread reads ct[i] → determine (row, col) → max(·, 0) × weight → acc[j]
    ↓
(skip store + barrier entirely)
```

---

## 2. Why It Cannot Work

### 2.1 No position-to-index mapping exists in the API

The cooperative tensor API surface is:

```metal
ct.get_capacity()        // number of elements this thread can access
ct.is_valid_element(i)   // is index i valid for this thread?
ct[i]                    // read/write element i (thread-local subset only)
ct.store(tensor_view)    // store full distributed result to a tensor view
```

There is **no**:
- `ct.get_row(i)` or `ct.get_col(i)`
- `ct.element_position(i)` → (row, col)
- `ct.get_element_at(row, col)`
- Any mapping between the opaque per-thread index space and logical matrix coordinates

The cooperative tensor is a distributed object. Each thread "owns" some elements of
the 32×32 result matrix, but the assignment is implementation-defined. The only
guaranteed way to access elements by (row, col) is to `store()` to a tensor with a
known layout.

### 2.2 The accumulation needs position-addressed access

The weighted ReLU accumulation is:

```metal
acc[j] += max(dot[cc*TQ + r], 0.0f) * (w[head0] * args.scale);
```

Where `(r, cc)` is derived from the thread's linear index:
```metal
const uint linear = tid + j*NUM_THREADS;
const uint r = linear / TN;       // row = token within tile
const uint cc = linear - r*TN;    // col = compressed row within tile
```

Each thread needs **specific** elements at known (row, col) positions. Thread T
responsible for `acc[j]` needs the dot-product value at `(r, cc)` — but there is
no guarantee that thread T "owns" that element in the cooperative tensor. The
cooperative distribution assigns elements arbitrarily across the 4 SIMD groups.

### 2.3 Empirical reverse-engineering is not viable

One could write a probe that stores known values to the cooperative tensor, reads
them back, and infers the per-thread element-to-position mapping. However:

- The layout is **not specified** by the Metal Shading Language specification
- It could differ between:
  - M5 vs future M6/M7 hardware
  - Different GPU core counts
  - Different SIMD group counts in the descriptor
  - Different matmul descriptor shapes
  - macOS/driver versions
- Relying on reverse-engineered layout violates R8 (OS capability tiers must be
  based on documented API) and R17 (preserve pre-M5 compatibility)
- If Apple changes the cooperative tensor distribution in a future driver, the
  kernel would silently produce incorrect results

### 2.4 Even with known mapping, the pattern is adversarial

The current accumulation distributes work as: thread `tid` handles positions
`tid, tid+128, tid+256, tid+384` (for `j=0..3`). These are scattered across
the 32×32 tile. There is no reason to expect the cooperative tensor assigns
these same positions to thread `tid`. In general, cooperative tensor distributions
are optimized for SIMD-level matrix operations, not for arbitrary per-thread
element extraction.

---

## 3. Potential Gain (If It Were Possible)

| Saved Operation | Cost Per Head-Pair |
|----------------|--------------------|
| Threadgroup write | 4096 bytes (32×32×4) |
| Barrier | ~1 synchronization point |
| Threadgroup read | 4–16 bytes per thread (each thread reads 4 elements) |

For `n_head = 64` (32 head-pairs per threadgroup dispatch):
- Total saved: 32 × (4096 bytes write + barrier + scattered reads)
- ~128 KB of threadgroup writes removed per threadgroup

However:
- The threadgroup `dot` buffer is almost certainly in L1/register-file-adjacent
  on-chip memory — threadgroup stores to 4 KB are extremely fast on Apple GPUs
- The barrier is a single-cycle instruction when no actual conflict exists
- The post-matmul arithmetic (max + multiply + add) is trivially cheap
- Profiling from task 4.2 would need to show this barrier/store as material

The entire post-matmul phase is likely **<5% of the per-head-pair time**,
dominated by the 4 × matmul2d invocations + Q staging + device-memory K loads.

---

## 4. Risk Assessment

| Risk | Impact | Likelihood |
|------|--------|------------|
| Cooperative layout is hardware-specific | Silent correctness failure on new hardware | Very high (specified as implementation-defined) |
| FP drift from different reduction order | Changed top-k selection → wrong compressed rows → incorrect attention | Medium (but moot since fusion is impossible) |
| Regression on pre-M5 | N/A (TensorOps kernel only runs on M5+) | N/A |
| API change in future Metal versions | Breakage on macOS update | High (relying on undocumented behavior) |

---

## 5. Alternative Considered: Thread-Shuffle Redistribution

One could imagine: after matmul completes, use SIMD shuffle/broadcast to
redistribute cooperative tensor elements to the threads that need them. This would:

- Require knowing the cooperative layout (same fundamental problem)
- Add shuffle overhead that likely exceeds the saved threadgroup write
- Add complexity without clear gain

Not viable.

---

## 6. Conclusion and Recommendation

**REJECT.** The cooperative tensor API is designed for two patterns:
1. Accumulate across multiple matmul iterations (ct[i] += ... over k-steps)
2. Store the final result to a memory-backed tensor view

It is explicitly **not** designed for post-matmul element-addressed consumption.
The `store()` → threadgroup → position-addressed read pattern is the correct and
intended usage for any post-processing that needs to know which (row, col) an
element corresponds to.

The potential gain (~128 KB threadgroup writes per dispatch, a few dozen barriers)
is modest relative to the matmul compute itself, and the optimization is
**structurally impossible** without relying on undocumented, non-portable hardware
behavior.

The current `ct.store(td) → barrier → read dot[cc*TQ + r]` pattern remains the
correct implementation for this kernel's weighted ReLU accumulation.
