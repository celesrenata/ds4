# 3.3 — Additional Tile Shapes: Decision

_Task: Candidate smaller tail tile and/or larger tile. Reject any candidate that is neutral/slower or increases fallback complexity without end-to-end gain._

_Requirements: R4, R16_

---

## Decision

**No additional tile shapes are justified at this time.**

The existing NR1 ∈ {32, 64, 128} tile selection with Q8_0 split-prefix for unaligned tails is production-ready. No candidate tile demonstrates sufficient motivation to warrant implementation, benchmarking overhead, or added dispatch complexity.

---

## Candidate Analysis

### Candidate 1: NR1 = 16 (smaller tail tile)

**Motivation:** Reduce fallback to legacy for prompts with token counts like 48, 80, 112, 144, 176 (remainder after dividing by 32 that isn't itself 32-aligned at a coarser level).

**Rejection rationale:**

1. **Q8_0 split-prefix already handles tails.** The split-prefix logic (documented in 3.1 §4.3) processes aligned prefix via TensorOps and sends only the <32-token remainder to legacy. This is already the efficient solution for the most common DS4 quant.

2. **F16/Q4 unaligned counts fall through to legacy entirely.** For these quants, the minimum TensorOps admission is `n_tok % 32 == 0`. A 16-token tile would help prompts of exactly 16, 48, 80... tokens, but these are rare in production DeepSeek-V4 workloads where typical prefill is ≥128 tokens.

3. **Insufficient amortization at NR1=16.** The kernel uses 4 SIMD groups (128 threads) with NR0=64. At NR1=16, each threadgroup produces only 64×16 = 1024 output elements. The TensorOps `matmul2d` setup, double-buffer staging, and dispatch overhead likely dominate at this tile size. The per-element cost of the cooperative tensor and K-loop machinery amortizes poorly over 16 columns.

4. **Added dispatch complexity.** A fourth tile variant means a fourth pipeline per quant (4 quants × 4 tiles = 16 pipelines vs current 12). The tile selection logic gains another branch, and the tail-handling strategy interacts with split-prefix in ways that need separate correctness testing.

5. **No empirical evidence of bottleneck.** No profiling data shows that unaligned tail handling via legacy fallback is a material contributor to prefill time. The legacy kernel is already fast for small token counts.

**Status: REJECTED — insufficient amortization, existing split-prefix handles tails for Q8_0, other quants acceptably use legacy for small unaligned counts.**

---

### Candidate 2: NR1 = 256 (larger tile)

**Motivation:** Exploit higher arithmetic intensity and amortize staging over more output columns for very large prompts (512, 1024, 2048+ tokens).

**Rejection rationale:**

1. **Existing NR1=128 already won empirically.** The code comment in `dense.metal` explicitly records: _"the 128-token RHS tile is kept when the batch alignment allows it because the later tile_n=64 retest was neutral/slower."_ This is direct empirical evidence that the 128 tile is already at or near the performance plateau for the current architecture on M5.

2. **Register pressure and occupancy risk.** At NR1=256, the cooperative destination tensor is 64×256 = 16384 F32 values distributed across the threadgroup. Even with cooperative distribution, the per-thread register footprint for the accumulator doubles versus NR1=128. This risks reducing occupancy from the current level, which would harm latency hiding and memory-access overlap.

3. **Threadgroup memory stays constant** (8192 bytes for weight staging), but the output tile is larger, meaning each threadgroup runs proportionally longer. Fewer threadgroups in flight reduces the GPU's ability to hide memory latency through occupancy. On bandwidth-sensitive transitions (K-loop iterations fetching the next weight tile), reduced occupancy directly hurts.

4. **Marginal gains when compute is saturated.** At NR1=128 with large prompts, the M5 Neural Accelerator is likely already near peak utilization for the `matmul2d` operation. Doubling the tile does not double the hardware — it just increases per-threadgroup work, potentially worsening tail effects when `n_tok` isn't divisible by 256.

5. **Limited applicability.** Only prompts with `n_tok % 256 == 0` benefit. Prompts of 256, 512, 1024, 2048 tokens already get excellent service from the 128-token tile (dispatching 2, 4, 8, or 16 threadgroup columns respectively). The marginal gain of halving dispatch count for already-large grids is negligible versus the risks.

**Status: REJECTED — existing 128 tile already won empirically; no evidence suggests 256 would improve; risks occupancy regression.**

---

### Candidate 3: NR0 changes (output-dimension tile)

**Motivation:** NR0=128 could halve the number of threadgroup rows for large `out_dim`, reducing total dispatch count.

**Rejection rationale:**

1. **No empirical motivation.** No profiling data from the baseline traces identifies dispatch count (grid Y dimension) as a bottleneck. The current NR0=64 produces grids of `out_dim/64` rows — for typical DeepSeek-V4 dimensions (4096, 7168, etc.) this is 64–112 rows, which is ample parallelism.

2. **Doubles threadgroup memory.** Weight staging would need `2 × 128 × 32 × 2 = 16384 bytes` per threadgroup (up from 8192). This directly reduces maximum occupancy on M5 shader cores.

3. **Interacts with dequantization.** The NR0 tile determines how many weight rows are staged per K-step. Changing it requires reworking the `dequantize_func` calls, potentially the block alignment assumptions for Q8_0/Q4_K, and the cooperative tensor accumulator shape.

4. **No design commentary suggests benefit.** Neither the code comments, the existing benchmarks, nor the design document identify NR0 as a limiting factor.

**Status: REJECTED — no empirical motivation found in profiling data; risks occupancy and dequant complexity.**

## Production Tile Configuration (Retained)

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| NR0 | 64 | Output-dimension tile; proven, no motivation to change |
| NR1 | 32 | Minimum token tile; handles ≥32-aligned prompts |
| NR1 | 64 | Mid-tier tile; auto-selected when `n_tok % 64 == 0` |
| NR1 | 128 | Maximum tile; empirically fastest for large aligned batches |
| NK | 32 | K-step; matches dequant block alignment |
| Tail handling | Q8_0 split-prefix + legacy fallback | Handles unaligned counts efficiently |

### Selection Policy (unchanged)

```
n_tok % 128 == 0  →  NR1 = 128
n_tok %  64 == 0  →  NR1 = 64
n_tok %  32 == 0  →  NR1 = 32
else              →  split-prefix (Q8_0) or legacy fallback
```

## Reopening Conditions

This decision will be revisited if any of the following emerge from later benchmark phases:

1. **End-to-end profiling (Task 13)** shows tile-related dispatch overhead as a material fraction of prefill time.
2. **MoE expert bucketing (Task 7.5)** reveals that small expert buckets (8–24 tokens) are common enough to warrant a sub-32 TensorOps tile for MoE specifically.
3. **Speculative verification (Task 10)** identifies a token-batch size between 16 and 31 where a smaller tile would avoid legacy fallback at verification depth.
4. **Future hardware** (M6+) changes the occupancy/register trade-offs enough to shift the 128 vs 256 balance.

Until then, the existing three-tile configuration is the production answer.
