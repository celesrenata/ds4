# 7.6 — Preserve TP/Streaming Behavior

_Requirements: R18, R19_

---

## 1. Summary

The new TensorOps pair+SwiGLU kernels (tasks 7.2, 7.3, 7.4) **support the resident
expert cache** and **are correctly excluded from SSD streaming dispatch**. Tensor
parallelism (TP) ownership is handled correctly through a combination of host-side
guards and GPU-side checks.

No code changes are needed. The existing dispatch logic is safe and conservative.

---

## 2. What the TensorOps Pair+SwiGLU Kernels Handle

### 2.1 Resident Expert Cache (Contiguous Layout) — SUPPORTED

Both TensorOps pair+SwiGLU kernels read weights via the contiguous resident pattern:

```metal
device const block_q *xg =
    (device const block_q *)(src0_gate + args.nb01*(r0 + lr0) + im*args.nb02);
```

This is identical to the simdgroup baseline (`kernel_mul_mm_id_pair_swiglu_f16_impl`).
The host binds `src0_gate` / `src0_up` by wrapping the model mmap range through
`ds4_gpu_wrap_model_range()`, which resolves to pre-registered Metal buffer views
covering the full expert layer.

**Conclusion:** When experts are resident (mmapped or in the resident expert cache),
the TensorOps kernels consume the same buffers with no extra copies. No changes needed.

### 2.2 Tensor Parallelism — SUPPORTED (with host-side conservative guard)

**GPU-side TP check (kernel_mul_mm_id_mpp_pair_swiglu_f16_impl, task 7.4):**

```metal
if (!ds4_tp_owns_expert(im, args.ne02, args.tp_rank, args.tp_world)) {
    for (short j = sgitg; j < nr1; j += 4) {
        // ... zero unowned expert's mid output rows ...
    }
    return;
}
```

This matches the legacy simdgroup pair kernel behavior exactly:
- Unowned experts zero their output region
- Downstream expert-sum stages remain correct
- The `ds4_tp_owns_expert()` function uses the same range partition:
  `first = tp_rank * (n_total / tp_world); last = ...`

**Host-side guard:**

```c
const bool use_mm_id_pair_swiglu =
    use_mm_id &&
    ...
    g_tp_split_world != 2 &&    /* pair-swiglu mm kernel lacks expert ownership */
    ...
```

The comment is **stale** for the task 7.4 kernel (`kernel_mul_mm_id_mpp_pair_swiglu_f16_impl`)
which does have the TP check, but it was originally correct for the task 7.3 kernel
(`kernel_mul_mm_id_pair_swiglu_mpp`) which does NOT have a TP check.

The guard is **overly conservative** but **safe**: it prevents all pair+SwiGLU matmul
kernels (both simdgroup and TensorOps) from being selected when `tp_world == 2`.
Since the host blocks the entire code path, the fact that one kernel has the check
and one doesn't is irrelevant at runtime.

**Note:** The `g_tp_split_world != 2` condition blocks pair+SwiGLU only for
2-way TP. If the comment was already wrong (i.e., the kernel DOES have the check
and should be enabled for TP), relaxing this guard would be a **performance
improvement** but is outside the scope of this task (requires targeted TP testing).

### 2.3 SSD Streaming: Address-Based Access — NOT SUPPORTED (explicitly falls back)

The TensorOps pair+SwiGLU kernels have no `_addr_` or `_slots6_` variants.
They cannot consume GPU-address-table pointers or per-slot expert buffers.

SSD streaming is handled through three explicit fallback mechanisms in the
host dispatch:

**Mechanism 1: IQ2_XXS streaming prefill (batch addr path)**

```c
const bool use_iq2_batch_selected_addr =
    ds4_gpu_stream_prefill_batch_selected_addr_enabled(...) &&
    ...;
```

This path requires `g_ssd_streaming_mode` and IQ2_XXS gate type. When active:
- `use_mm_id` becomes false (explicit exclusion in definition)
- `use_mm_id_pair_swiglu` becomes false (depends on `use_mm_id`)
- TensorOps pair+SwiGLU is never selected
- Instead, `kernel_mul_mv_addr_iq2_xxs_pair_swiglu_f32` (decode matvec) handles it

**Mechanism 2: Q4_K streaming prefill (expert table path)**

```c
const bool use_q4_batch_expert_table =
    gate_type == DS4_METAL_TENSOR_Q4_K &&
    ...;
```

This path uses `DS4MetalQ4ExpertTable` for GPU-resolved expert lookup. When active:
- `use_mm_id` becomes false (explicit exclusion)
- TensorOps pair+SwiGLU is never selected
- Uses `kernel_mul_mv_table_q4_K_pair_swiglu_f32` instead

**Mechanism 3: MXFP4 streaming prefill — implicit fallback**

MXFP4 has no dedicated streaming batch path (no `use_mxfp4_batch_selected_addr`).
In SSD streaming mode with MXFP4:
- Neither `use_iq2_batch_selected_addr` nor `use_q4_batch_expert_table` is true
- `use_mm_id` depends on `n_tokens >= 32` (could be true)
- If true, the code tries `ds4_gpu_wrap_model_range()` to bind the expert weights
- In SSD streaming configurations where model views don't cover the expert range,
  `ds4_gpu_wrap_model_range()` returns `nil` → function returns 0 (failure)
- The caller handles this gracefully (no crash, no corruption)

In practice, MXFP4 SSD streaming primarily operates in **decode mode** (n_tokens == 1)
using `kernel_mul_mv_slots6_mxfp4_pair_swiglu_f32` / `kernel_mul_mv_slots6_mxfp4_sum6_f32`.
MXFP4 prefill with streaming is not a standard deployment configuration since MXFP4
models are smaller (half the size of Q4_K expert tensors) and typically fit resident.

### 2.4 SSD Streaming: Slot-Based Access — NOT SUPPORTED (decode-only)

The `_slots6_` kernels handle streaming for single-token decode:
- `kernel_mul_mv_slots6_mxfp4_pair_swiglu_f32`
- `kernel_mul_mv_slots6_q4_K_pair_swiglu_f32`
- `kernel_mul_mv_slots6_iq2_xxs_pair_swiglu_f32`

These are selected via `use_mxfp4_selected_slots` / `use_q4_selected_slots` / etc.
in `ds4_gpu_routed_moe_one_tensor()`, NOT in the batch function.

TensorOps pair+SwiGLU only applies to the **batch** (prefill) path and is never
confused with the slot-based decode path.

### 2.5 Masked Variants (Partial Cache Hits) — NOT SUPPORTED (explicit fallback)

Masked kernels (`*_masked_*` + `active_mask`) handle partial cache hits in SSD
streaming where only some requested experts are resident. These are a sub-variant
of the addr-based streaming kernels.

Since the TensorOps pair+SwiGLU kernel has no addr variant, it cannot encounter
a masked dispatch. The `use_iq2_batch_selected_addr` path handles masked scenarios
internally through `ds4_gpu_stream_expert_cache_prepare_selected_batch()`.

## 3. Dispatch Flow Summary

```
ds4_gpu_routed_moe_batch_tensor():
    │
    ├── use_iq2_batch_selected_addr? (streaming IQ2 prefill)
    │   → YES: addr-based streaming kernels; TensorOps EXCLUDED
    │
    ├── use_q4_batch_expert_table? (streaming/table Q4_K prefill)
    │   → YES: table-based kernels; TensorOps EXCLUDED
    │
    ├── use_mm_id? (!streaming paths && n_tokens >= 32)
    │   │
    │   ├── use_mm_id_pair_swiglu? (g_tp_split_world != 2 && ...)
    │   │   │
    │   │   ├── Q4_K + TensorOps available?
    │   │   │   → kernel_mul_mm_id_q4_K_pair_swiglu_mpp ← TensorOps
    │   │   │
    │   │   ├── MXFP4 + TensorOps available?
    │   │   │   → kernel_mul_mm_id_mxfp4_mpp_pair_swiglu_f16 ← TensorOps
    │   │   │
    │   │   └── else: legacy simdgroup pair kernel
    │   │
    │   └── separate gate/up/down matmul dispatch (non-fused)
    │
    └── tiny_pair_mv / mv fallback (n_tokens < 32)
```

## 4. Comparison: TP Check in TensorOps vs Legacy

| Kernel | Has `ds4_tp_owns_expert`? | Host blocks at TP>1? |
|--------|--------------------------|---------------------|
| `kernel_mul_mm_id_pair_swiglu_f16_impl` (legacy simdgroup) | YES (line 7849) | YES (`g_tp_split_world != 2`) |
| `kernel_mul_mm_id_pair_swiglu_mpp` (task 7.3, Q4_K) | NO | YES (same guard) |
| `kernel_mul_mm_id_mpp_pair_swiglu_f16_impl` (task 7.4, all quants) | YES (line 9927) | YES (same guard) |

The host guard is conservative: it blocks ALL pair+SwiGLU prefill at TP world 2,
regardless of whether the specific kernel has the GPU-side check. This is correct.

The behavior when the TP check fires (both legacy and TensorOps) is identical:
- Zero the `mid` output rows for unowned expert tiles
- Return early from the threadgroup
- Downstream expert-sum sees zeros for unowned experts

## 5. Cases that Explicitly Fall Back to Legacy Kernels

| Case | Why TensorOps is excluded | Fallback path |
|------|--------------------------|---------------|
| SSD streaming + IQ2_XXS prefill | `use_iq2_batch_selected_addr` blocks `use_mm_id` | `kernel_mul_mv_addr_iq2_xxs_pair_swiglu_f32` (addr matvec) |
| SSD streaming + Q4_K prefill | `use_q4_batch_expert_table` blocks `use_mm_id` | `kernel_mul_mv_table_q4_K_pair_swiglu_f32` (table matvec) |
| SSD streaming + MXFP4 prefill | `ds4_gpu_wrap_model_range()` fails if views unavailable | Function returns 0; caller handles |
| SSD streaming + any decode (n=1) | Batch function not called | `kernel_mul_mv_slots6_*` (slot-based matvec) |
| TP world == 2 | `g_tp_split_world != 2` guard | Legacy simdgroup pair kernel (also blocked) or separate gate/up matmul |
| Masked/partial cache hit | Sub-case of addr streaming; excluded with it | Handled within streaming infrastructure |
| Compact tile on M5 + MXFP4 | `!use_mxfp4_mm_id_pair_swiglu_compact_tile` guard | Legacy compact-tile simdgroup kernel |
| Quality mode | `g_quality_mode` blocks mpp_available | Legacy kernel (reference path) |

## 6. Resident Expert Cache Support

The resident expert cache stores contiguous per-expert weight buffers at known offsets.
When the cache is warm, the host binds the same contiguous model-map range that the
TensorOps kernel expects.

**No additional work is needed.** The TensorOps pair+SwiGLU kernels inherently support
the resident expert cache because:
1. They read weights at `src0_gate + nb01*row + im*nb02` — the standard contiguous layout
2. The host binds the same `gate_buf`/`up_buf` buffers regardless of whether the data
   came from mmap or from a resident cache fill
3. The kernel doesn't care about the provenance of the buffer data

## 8. Potential Future Improvement (Out of Scope)

The `g_tp_split_world != 2` guard blocks the task 7.4 kernel unnecessarily (it has the
TP check). If TP performance with the TensorOps path becomes important, the guard
could be relaxed to allow `kernel_mul_mm_id_mpp_pair_swiglu_f16_impl` to run under TP,
since it correctly zeros unowned expert outputs. This would require:
1. Confirming the guard doesn't also protect the task 7.3 kernel (it does — but that
   kernel is only selected for Q4_K which would need its own TP check added)
2. Targeted TP correctness tests (verify zero-output equivalence)
3. TP performance benchmarks

This is filed as a note, not a required action for task 7.6.
