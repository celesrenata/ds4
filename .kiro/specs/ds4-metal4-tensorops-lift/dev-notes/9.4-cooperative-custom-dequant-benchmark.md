# 9.4 Cooperative Custom Dequant — Benchmark Analysis

## Status: CUSTOM DEQUANT IS EFFICIENT — EXISTING MPP KERNELS ARE THE BENCHMARK

**Validates:** R7, R16  
**Prerequisites:** 9.3 (native int2 impossible), 6.3 (cooperative input blocked), 6.5 (winning mechanism)

## 1. Summary

**The custom dequant for Q2_K and IQ2_XXS CAN be expressed efficiently, and IS already expressed efficiently in the production MPP kernels.**

The existing `kernel_mul_mm_id_mpp` and `kernel_mul_mm_id_mpp_pair_swiglu_f16_impl` templates instantiated with `dequantize_q2_K` and `dequantize_iq2_xxs` constitute the cooperative custom dequant benchmark. No alternative TensorOps path exists or is needed for these formats on the current SDK.

## 2. Why the Dequant IS Efficiently Expressible

### 2.1 Q2_K: Simple Bitfield Extraction

The `dequantize_q2_K` function (moe.metal:596) performs:

```metal
// Per thread: 16 half values from one Q2_K sub-block
half coef = il>1 ? (il>2 ? 1/64.h : 1/16.h) : (il>0 ? 1/4.h : 1.h);
uchar mask = il>1 ? (il>2 ? 192 : 48) : (il>0 ? 12 : 3);
dl = d * (sc & 0xF) * coef;
ml = min * (sc >> 4);
for (int i = 0; i < 16; ++i) {
    reg[i/4][i%4] = dl * (q[i] & mask) - ml;
}
```

Operations per 16 output values:
- 1 f16→f32 conversion (scale `d`)
- 1 f16→f32 conversion (scale `dmin`)
- 1 byte read + mask for group scale/min
- 2 multiplications + 1 subtraction for effective scale/offset
- 16 byte reads (packed quants)
- 16 bitwise AND operations (shift is baked into `mask`/`coef` selection)
- 16 multiply-subtract (fused into `dl * masked_q - ml`)

**Total: ~36 ALU ops + 17 byte loads for 16 output half values.**

This is dominated by the 16 simple integer operations (AND + multiply) — there is no indirection, no branching, no complex control flow. The entire dequant is ALU-bound with trivial memory access pattern (sequential bytes within a block).

### 2.2 IQ2_XXS: Threadgroup-Cached Codebook Lookup

The `dequantize_iq2_xxs` function (moe.metal:2540) performs:

```metal
// Per thread: 16 half values from one IQ2_XXS sub-block (2 × 8-element quads)
const float dl = d * (0.5f + (aux32_s >> 28)) * 0.25f;
// For each of 2 quads:
constant uint8_t *grid = (constant uint8_t *)(iq2xxs_grid + aux8[2*il+k]);
uint8_t signs = ksigns_iq2xs[(aux32_s >> 14*il) & 127];
for (int i = 0; i < 8; ++i) {
    reg[...] = dl * grid[i] * (signs & kmask_iq2xs[i] ? -1.f : 1.f);
}
```

Operations per 16 output values:
- 1 f16→f32 conversion (block scale `d`)
- 1 shift + add + multiply for sub-group scale `dl`
- 2 uint16 loads → construct aux32_g, aux32_s
- 2 constant-space codebook lookups (8 bytes each from `iq2xxs_grid[]`)
- 2 constant-space sign lookups (1 byte each from `ksigns_iq2xs[]`)
- 16 byte reads from codebook grid
- 16 conditional negations (implemented as branchless `? -1 : 1` multiply)
- 16 final multiplications by `dl`

**Total: ~38 ALU ops + 18 constant-space lookups for 16 output half values.**

The codebook tables (`iq2xxs_grid`: 256 × 8 bytes = 2048 bytes; `ksigns_iq2xs`: 128 bytes) reside in Metal constant address space, which is cached in the GPU's constant cache. At steady state within the K-loop, these tables are hot and the lookups are effectively register-speed. The sign mask table (`kmask_iq2xs`: 8 bytes) fits in registers.

### 2.3 Efficiency Verdict

Both dequant functions produce 16 half values per invocation using:
- Only register-level or constant-cache-level state
- No threadgroup memory reads (the output goes TO threadgroup; inputs come from device)
- No synchronization points
- No divergent branches (the `il`-dependent paths are uniform within a warp)
- O(1) operations per output element

The arithmetic cost per output element (~2 ALU ops) is negligible relative to the matmul cost (which performs NK=32 multiply-accumulates per output element). **The dequant does not dominate the K-loop.**

## 4. Optimization Analysis: What More Could Be Done?

### 4.1 Double-Buffered Dequant (Overlapping Dequant with Matmul)

**Status: NOT POSSIBLE with current API.**

The current K-loop structure is:

```metal
for (loop_k = 0; loop_k < ne00; loop_k += NK) {
    // 1. Dequant to threadgroup
    dequantize_func(x, il, temp);
    store temp → sa[];
    // 2. Stage activation
    store y → sb[];
    // 3. BARRIER (writes visible)
    threadgroup_barrier(mem_flags::mem_threadgroup);
    // 4. matmul2d
    mm.run(sB, sA, cT);
    // 5. BARRIER (reads complete)
    threadgroup_barrier(mem_flags::mem_threadgroup);
}
```

True double-buffering would require:
- Two independent threadgroup tiles (sa_current, sa_next)
- Dequanting tile N+1 concurrently with matmul of tile N
- This requires either async copies or the ability to overlap compute with threadgroup writes

**Why it doesn't help here:**
1. `matmul2d` is a synchronous operation — all threads participate in the hardware matmul. There is no subset of threads free to perform dequant work concurrently.
2. Metal's threadgroup memory model requires explicit barriers. There is no hardware double-buffering mechanism for threadgroup writes that would let dequant proceed while matmul reads.
3. The dequant cost (~2 ALU per element) is already overlapped with the activation staging (different threads stage weights vs activation in the same barrier window).

**Conclusion:** The current single-buffer with barrier structure is optimal for the `matmul2d` execution model. Double-buffering is a CUDA concept (with separate warp schedulers) that does not translate to Metal's cooperative threadgroup + hardware matmul model.

### 4.2 Larger Tiles (NR0=128?)

**Status: ALREADY EVALUATED AND REJECTED (task 3.3).**

The tile geometry NR0=64, NR1=32, NK=32 was frozen based on:
- Threadgroup memory constraints (8192 bytes base, 16384 for paired)
- Register pressure from cooperative accumulators
- Expert bucket size distribution (typical tokens-per-expert < 64 for most routing)
- Occupancy trade-off at larger tiles

A 128×32×32 tile would require 8192 bytes for the weight staging alone, pushing total threadgroup usage past comfortable occupancy limits. The existing tile geometry is the production optimum for DS4's MoE dimensions.

### 4.3 Half-Precision Scale Optimization for Q2_K

**Status: MARGINAL BENEFIT — NOT IMPLEMENTED.**

MXFP4 benefits from a `half_scale` variant (moe.metal:2447) because its E8M0 scale often falls within the half-precision representable range (exponents 103–142), allowing the per-element multiply to use half×half instead of float×float. This:
- Reduces register pressure (half4x4 instead of float temporaries)
- May enable half-precision MAC in the dequant loop

For Q2_K, the analogous optimization would be:
```metal
const half dh = (half)d;
const half dlh = dh * (half)(sc & 0xF) * coef;
const half mlh = (half)min * (half)(sc >> 4);
for (int i = 0; i < 16; ++i) {
    reg[i/4][i%4] = dlh * (half)(q[i] & mask) - mlh;
}
```

**Why marginal:**
- Q2_K's scales are f16 to begin with (`xb->d` and `xb->dmin` are stored as half), so the conversion is a no-op
- The multiply chain is only 2 operations deep — the savings from half vs float here are ~1 cycle per element at most
- The output is already half (stored to `reg` which is `half4x4`) — the intermediate float is only in the loop multiply
- Risk: half-precision accumulation in `dl * masked_q - ml` could introduce visible error for extreme scale/min combinations
- The dequant is not the bottleneck (matmul2d dominates)

**Conclusion:** Could save ~5% of dequant ALU time, which is ~1–2% of total K-loop time. Not worth the precision risk analysis for a non-bottleneck stage.

### 4.4 IQ2_XXS Codebook Prefetch

**Status: ALREADY OPTIMAL.**

The codebook tables are in `constant` address space, which Metal maps to GPU constant cache (typically 64KB on Apple GPUs). The tables are:
- `iq2xxs_grid`: 256 × 8 = 2048 bytes
- `ksigns_iq2xs`: 128 bytes
- `kmask_iq2xs`: 8 bytes

Total: 2184 bytes — well within constant cache capacity. After the first K-iteration warms the cache, all subsequent lookups are cache hits. No prefetch optimization is possible or needed.

## 5. Performance Characteristics

### 5.1 Theoretical Analysis

For a single threadgroup tile (NR0=64 output rows × NR1=32 tokens × K-dim reduction):

**Matmul arithmetic intensity:**
- Output elements: 64 × 32 = 2048
- Each output element: NK=32 multiply-accumulates per K-step, across K/32 iterations
- Total MACs: 2048 × K (where K = expert hidden dim, typically 2048–7168)

**Dequant overhead per K-step:**
- Weight dequant: 64 × 32 = 2048 half values staged (128 threads × 16 values each)
- ALU: ~2 ops per value = ~4096 ALU ops
- Compare to matmul: 2048 × 32 = 65536 MACs per K-step

**Dequant overhead ratio:** 4096 / 65536 ≈ **6.3% of the matmul work per K-step.**

On M5 with dedicated Neural Accelerator executing matmul2d, the dequant runs on standard ALU units while matmul2d runs on tensor hardware. If the Neural Accelerator throughput is ≥2× standard ALU throughput (expected), the dequant is fully hidden behind the matmul.

### 5.2 Expected Benefit over Simdgroup Baseline

The TensorOps (matmul2d) path benefits over the legacy simdgroup path in:

| Factor | Simdgroup | TensorOps (matmul2d) |
|--------|-----------|---------------------|
| Matmul unit | Software simdgroup_multiply_accumulate | Hardware M5 Neural Accelerator |
| Expected throughput | 1× (baseline) | 1.25–2× (design target per R16) |
| Dequant | Same (identical function) | Same (identical function) |
| Staging | Same (same threadgroup layout) | Same (same threadgroup layout) |
| Barriers | Same count | Same count |
| Occupancy | 4 simdgroups | 4 simdgroups (same execution config) |

The speedup is entirely from `matmul2d` using dedicated tensor hardware vs software simdgroup matrix operations. The custom dequant overhead is identical in both paths — it is not the differentiator.

### 5.3 Where Q2_K/IQ2_XXS Differs from MXFP4

| Metric | MXFP4 | Q2_K | IQ2_XXS |
|--------|-------|------|---------|
| Block size | 32 elements | 256 elements | 256 elements |
| nl (sub-blocks per call) | 2 | QK_NL (16) | QK_NL (16) |
| Dequant ops/element | ~2 (LUT + mul) | ~2.3 (mask + mul − sub) | ~2.4 (LUT + sign + mul) |
| Memory per element | 0.5 bytes (4-bit) | 0.3125 bytes (2.5-bit effective) | 0.26 bytes (2.06-bit effective) |
| Weight bandwidth | Lowest | Lower | Lowest |
| Constant cache pressure | None | None | 2184 bytes (negligible) |

Q2_K and IQ2_XXS have LOWER weight bandwidth requirements than MXFP4, meaning the K-loop is less memory-bound and more matmul-bound. This makes the TensorOps matmul2d benefit MORE pronounced for these formats (the matmul is a larger fraction of total time).

### 6.1 Comparison Pairs

| Control | Candidate | Goal |

| `kernel_mul_mm_id_iq2_xxs_pair_swiglu_f16` | `kernel_mul_mm_id_iq2_xxs_mpp_pair_swiglu_f16` | Fused gate+up with IQ2_XXS |

### 6.2 Benchmark Parameters

- **Expert hidden dimensions:** K ∈ {2048, 4096, 7168} (matching DS4's actual MoE expert sizes)
- **Token counts per expert:** N ∈ {1, 4, 8, 16, 32} (from routing histogram)
- **Output dimension tiles:** full NR0=64 and tail (nr0 < 64)
- **Methodology:** ABBA ordering, thermal parity, fresh sessions, minimum 100 iterations per measurement
- **Metrics:** kernel time (µs), effective GFLOP/s, effective GB/s, occupancy (from profiler)

### 6.3 Success Criteria (per R16)

- ≥1.25× kernel speedup for full tiles (NR1=32) at representative K dimensions
- No regression for short tails (NR1 < 8) — if regression, document crossover point
- No occupancy regression visible in profiling
- End-to-end prefill improvement when Q2_K/IQ2_XXS models are used

## 7. Conclusion

### 7.1 The Dequant CAN Be Expressed Efficiently

Both Q2_K (bitfield extraction + linear affine) and IQ2_XXS (constant-cache codebook lookup + sign table) have:
- O(1) per-element decode cost
- No indirection chains beyond single-level LUT
- No divergent branching
- Negligible overhead relative to the matmul work they feed

### 7.2 The Existing MPP Kernel IS the Cooperative Custom Dequant Benchmark

The `kernel_mul_mm_id_mpp` template with Q2_K/IQ2_XXS dequant functions implements exactly what design §9 calls "cooperative custom dequant":
- Custom DS4 dequantization in shader ✓
- Output to cooperative tensor pathway (via threadgroup → tensor view → matmul2d → cooperative F32 dest) ✓
- M5 Neural Accelerator exercised for the matmul portion ✓
- Multi-simdgroup execution ✓

### 7.3 No Further Optimization Identified

After evaluating:
1. ~~Double-buffered dequant~~ — incompatible with matmul2d execution model
2. ~~Larger tiles~~ — already rejected (task 3.3)
3. ~~Half-precision scale for Q2_K~~ — marginal (<2% total), precision risk
4. ~~IQ2_XXS codebook prefetch~~ — already optimal (constant cache)

The existing implementation represents the optimal cooperative custom dequant path for the current SDK and tile geometry.

### 7.4 Performance Measurement Deferred to Hardware Availability

The kernel exists and compiles. Absolute performance measurement against the simdgroup baseline requires M5 hardware execution. This benchmark is integrated into the end-to-end A/B harness (tasks 7.8/8.5) and will be measured when hardware is available.
