# 6.5 Winning Mechanism — Staged Dequant to Threadgroup → TensorOps matmul2d

## Status: FROZEN

**Validates:** R6, R16  
**Outcome of:** Tasks 6.2 (staged-dequant control), 6.3 (cooperative-input blocked), 6.4 (microbenchmark)

---

## 1. Decision

**The winning mechanism for DS4 MoE TensorOps is: staged-both-operands dequant through threadgroup memory into tensor views consumed by `matmul2d` with `execution_simdgroups<4>`.**

This is the pattern already used by `kernel_mul_mm_id_mpp` (Q2_K, IQ2_XXS) and validated by the task 6.2 Q8_0 control kernel (`kernel_mul_mm_id_q8_0_staged_dequant_control`).

The cooperative-input shortcut (task 6.3) is blocked by SDK constraint and the native-MX path (task 5.6) is deferred pending macOS 27. Staged dequant is the only viable multi-simdgroup TensorOps path on the current SDK.

---

## 2. The Reusable Pattern

Tasks 7.2, 7.3, 8.2 SHALL use this structure:

```metal
// ═══════════════════════════════════════════════════════════════════════════
// DS4 MoE Staged-Dequant TensorOps Pattern
// ═══════════════════════════════════════════════════════════════════════════
//
// Tile geometry (fixed for DS4 MoE):
//   NR0 = 64   (weight rows = output dimension per threadgroup)
//   NR1 = 32   (activation columns = tokens per tile)
//   NK  = 32   (reduction tile, matches MXFP4/Q8_0 block size)
//   execution_simdgroups<4> (128 threads per threadgroup)
//
// Threadgroup memory layout:
//   sa: half[NR0 * NK] = 4096 bytes  (weight tile, dequanted)
//   sb: half[NR1 * NK] = 2048 bytes  (activation tile, gathered + converted)
//   sc: float[NR0 * NR1] = 8192 bytes (output, reuses shmem after matmul)
//   Total shmem: max(4096 + 2048, 8192) = 8192 bytes
//
// Dataflow per K iteration:
//   1. Dequant weight block → store half values to sa[]
//   2. Gather scattered activation → store half values to sb[]
//   3. threadgroup_barrier(mem_flags::mem_threadgroup)
//   4. tensor view tA over sa, tensor view tB over sb
//   5. mm.run(sB, sA, cT)  — M5 Neural Accelerator matmul2d
//   6. threadgroup_barrier(mem_flags::mem_threadgroup)
//
// Final store:
//   cT.store(tC) → threadgroup float tile → scatter to per-token device output
//
// ═══════════════════════════════════════════════════════════════════════════
```

### 2.1 Tile layout convention

Weight tile `sa[]` is indexed as:
```metal
sa[NK * (8*sy + ly) + 8*sx + lx]
```
where:
- `sy = (tiitg / NL0) / 8` — row group
- `ly = (tiitg / NL0) % 8` — row within group
- `sx = 2*il0 + i/8` — K sub-block (2 per Q8_0/MXFP4 iteration)
- `lx = i % 8` — element within sub-block

Activation tile `sb[]` uses the same layout convention with `NL1 = NK/8`:
```metal
sb[NK * (8*sy + ly) + 8*sx + lx]
```

This layout matches the tensor descriptor `dextents<int32_t, 2>(NK, NR0)` for weights and `dextents<int32_t, 2>(NR1, NK)` for activations.

### 2.2 matmul2d descriptor

```metal
matmul2d<
    matmul2d_descriptor(NR1, NR0, NK, false, true, false,
        matmul2d_descriptor::mode::multiply_accumulate),
    execution_simdgroups<4>> mm;
```

The descriptor computes: `B(NR1×NK) × A(NK×NR0)^T → C(NR0×NR1)` in multiply-accumulate mode (cooperative accumulator survives across K iterations).

### 2.3 Work dispatch

```metal
device const uint32_t *work_count = (device const uint32_t *)work;
device const uint2 *work_items = (device const uint2 *)(work + 8);
// item.x = expert index (im)
// item.y = token column offset within expert bucket (r1)
// tgpig.y = weight row tile index → r0 = tgpig.y * NR0
```

Each threadgroup processes one `(expert, token_column_tile)` pair. The work buffer is pre-built by the host based on routing.

### 2.4 Routed output scatter

```metal
auto tC = tensor(sc, dextents<int32_t, 2>(NR0, NR1));
cT.store(tC);
threadgroup_barrier(mem_flags::mem_threadgroup);

for (short j = tiitg/32; j < nr1; j += 4) {
    const int idj = ids_i32[im*args.ne21 + r1 + j];
    // ... scatter float output to per-token device positions
}
```

### 2.5 TP ownership

Unowned experts zero their output region immediately and return. This preserves downstream sum correctness across tensor-parallel ranks.

## 3. What New Kernels Must Supply (the "plug-in" point)

The only part that changes between quant formats is **the weight dequant logic inside the K-loop**. Specifically, each new format provides:

```metal
// Inside the K-loop, after the threadgroup_barrier for write safety:
{
    // FORMAT-SPECIFIC: read device weight data, decode to half, store to sa[]
    // Must produce 16 half values per thread per iteration following §2.1 layout.
    //
    // For kernel_mul_mm_id_mpp (template), this is:
    //   dequantize_func(x, il, temp_a);  // → half4x4
    //   store temp_a to sa[] using (sx, sy, lx, ly) indexing
    //
    // For MXFP4 (task 7.2), this will be:
    //   read E8M0 scale → lut lookup → 16 half values → store to sa[]
}
```

The activation staging, tensor views, matmul descriptor, cooperative accumulator, and output scatter are **identical** across all quant formats and do not need reimplementation.

## 5. How Tasks 7.2, 7.3, 8.2 Should Use This

### 5.1 MXFP4 gate/up (task 7.2)

Instantiate `kernel_mul_mm_id_mpp` with:
- `block_q = block_mxfp4` (DS4's 17-byte MXFP4 block)
- `nl` = appropriate sub-block count for MXFP4 (1 scale + 16 nibble bytes = 32 elements per block; `nl=2` gives 16 values per thread per call)
- `dequantize_func = dequantize_mxfp4` — uses `ds4_metal_mxfp4_half_lut` for single-LUT decode

OR: write a specialized MXFP4 kernel following the exact same staged pattern (preferred if the LUT-based decode benefits from inlining rather than function pointer dispatch).

### 5.2 Q8_0/Q4_K gate/up (task 7.3)

Already covered by the template. Instantiate with existing dequant functions. The Q8_0 control kernel (task 6.2) serves as the reference.

### 5.3 Down projection (task 8.2)

Same pattern, same tile geometry. The only difference is the output post-processing: down-projection results may participate in expert-sum accumulation rather than being scattered individually. The cooperative store → threadgroup → scatter portion may be replaced with an atomic add or a sequential accumulation depending on task 8.3's fusion decision.

---

## 6. What Was NOT Made Generic

Per the task requirement "do not create a generic abstraction larger than DS4 needs":

- **No abstraction layer** between the kernel and the dequant logic. The template instantiation IS the mechanism — no vtables, no protocol types, no runtime dispatch within the kernel.
- **No configurable tile sizes** beyond what already exists. NR0=64, NR1=32, NK=32 is fixed for all MoE variants. Task 3.3 already evaluated alternative tiles for dense and rejected them for the MoE shape.
- **No generic "staged matmul framework"**. The pattern is concrete Metal code with a known template, not a library.
- **The cooperative-input path is retained but guarded** (`DS4_EXPERIMENT_COOP_INPUT_SINGLE_SG`) — it does not participate in production dispatch and exists only as future documentation.

## 7. Why This Wins

| Criterion | Staged dequant (winner) | Cooperative input (blocked) | Native MX (deferred) |
|-----------|------------------------|---------------------------|---------------------|
| Multi-simdgroup (4× occupancy) | ✓ | ✗ (SDK: single SG only) | Unknown |
| Production tile geometry (64×32×32) | ✓ | ✗ (would need 1-SG tile) | Unknown |
| No model repack | ✓ | ✓ | Requires repack |
| mmap-compatible | ✓ | ✓ | ✗ (interleaved blocks) |
| Available now (macOS 26.3+) | ✓ | ✗ | ✗ (needs macOS 27) |
| M5 Neural Accelerator exercised | ✓ (via matmul2d) | ✓ | ✓ |
| Proven by existing production kernels | ✓ (Q2_K, IQ2_XXS) | — | — |

## 8. Requirement Traceability

### R6 (Routed-MoE TensorOps lift)

The frozen mechanism is the implementation vehicle for R6. Tasks 7–8 use this exact pattern to accelerate gate/up and down projections.

### R16 (Performance acceptance)

The mechanism exercises the M5 Neural Accelerator through `matmul2d` while preserving the multi-simdgroup tile geometry that achieves full threadgroup occupancy. The task 6.4 microbenchmark confirmed this staged approach outperforms the legacy SIMD-group matmul for the relevant K/M/N dimensions.

---

## 9. Summary

The winning mechanism is not a new invention — it is the existing `kernel_mul_mm_id_mpp` pattern, validated by the task 6.2 Q8_0 control, and confirmed as the only viable multi-simdgroup TensorOps path after the cooperative-input SDK constraint (task 6.3) and native-MX deferral (task 5.6).

Tasks 7–8 should instantiate or specialize this pattern for their target quant formats. The dequant function is the only variable; everything else is fixed infrastructure.
