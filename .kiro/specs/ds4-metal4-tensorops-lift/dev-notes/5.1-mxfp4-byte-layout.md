# 5.1 DS4 MXFP4 Byte Layout — Reference Document

> Source of truth: `metal/moe.metal`, `tests/test_mxfp4_dot.c`, `tests/test_mxfp4_metal.c`  
> Validates: R7

---

## 1. Block Structure

```c
#define QK_MXFP4 32

struct block_mxfp4 {
    uchar e;              // byte 0: E8M0 shared scale exponent
    uchar qs[16];         // bytes 1–16: 32 × E2M1 values, nibble-packed (2 per byte)
};

static_assert(sizeof(block_mxfp4) == 17);
```

Each block encodes exactly **32 scalar values** in **17 bytes total**:
- 1 byte: E8M0 scale (shared exponent for all 32 values)
- 16 bytes: 32 nibbles packed into byte pairs

---

## 2. Nibble Ordering (Critical for Native MX Compatibility)

Within each byte `qs[j]`, two 4-bit E2M1 codes are packed:

| Nibble position | Extraction | Logical element index |
|-----------------|-----------|----------------------|
| Low nibble (bits 3:0) | `qs[j] & 0x0F` | Element `j` (first half of block) |
| High nibble (bits 7:4) | `qs[j] >> 4` | Element `j + 16` (second half of block) |

This means the 32 elements within a block are **NOT** stored in sequential nibble order. Instead:

```
qs[0] low  → element 0
qs[1] low  → element 1
qs[2] low  → element 2
  ...
qs[15] low → element 15
qs[0] high → element 16
qs[1] high → element 17
qs[2] high → element 18
  ...
qs[15] high → element 31
```

**The low nibbles of all 16 bytes map to elements 0–15, and the high nibbles map to elements 16–31.** This is a split-half interleave, not a sequential packed order.

### Evidence

From `tests/test_mxfp4_dot.c` — the reference dot product:
```c
for (int j = 0; j < QK_MXFP4 / 2; j++) {
    const uint8_t q = x[ib].qs[j];
    sum += d * mxfp4_values[q & 0x0f] * y[ib * QK_MXFP4 + j];           // element j
    sum += d * mxfp4_values[q >> 4]   * y[ib * QK_MXFP4 + j + QK_MXFP4/2]; // element j+16
}
```

From `metal/moe.metal` kernel inner loop (using `il` parameter for half-select):
```metal
const uint shift = il == 0 ? 0u : 4u;  // il=0 → low nibbles (elts 0-15), il=1 → high nibbles (elts 16-31)
FOR_UNROLL (short i = 0; i < QK_MXFP4/2; i++) {
    const uint q = ((uint)xb->qs[i] >> shift) & 0x0fu;
    reg[i/4][i%4] = d * ds4_metal_mxfp4_values[q];
}
```

### Implication for Native MX Tensor

If Metal's native MXFP4 tensor expects sequential element ordering (element 0 in the first nibble, element 1 in the second nibble, element 2 in the third nibble, etc.), a direct zero-copy view is **NOT possible** without verifying that Metal uses the same split-half nibble convention. This must be explicitly tested in task 5.3.

## 3. E8M0 Scale Semantics

The E8M0 format is a pure power-of-two scale with no mantissa:

```c
float e8m0_to_f32(uint8_t e) {
    uint32_t bits = e == 0 ? 0x00400000u : (uint32_t)e << 23;
    return as_type<float>(bits);
}
```

| E8M0 byte | Float value | Meaning |
|-----------|------------|---------|
| 0 | `2^(-126)` ≈ 1.175e-38 | Minimum scale (NOT zero — encodes smallest normal float) |
| 1 | `2^(-126)` | Same as IEEE float exponent 1 |
| 127 | `2^0` = 1.0 | Unity scale |
| 128 | `2^1` = 2.0 | — |
| 254 | `2^127` ≈ 1.701e38 | Maximum finite scale |
| 255 | +∞ | Infinity (special-cased in half LUT path) |

Key observations:
- **e=0 produces a tiny but non-zero scale** (`2^(-126)`), NOT a zero block. There is no way to represent exact zero scaling.
- The conversion is `2^(e-127)` for e ∈ [1, 254], which matches standard IEEE 754 exponent bias.
- e=255 (infinity) is special-cased in the half-LUT path to avoid NaN table entries.

### Decoded value formula

```
decoded_value[i] = e8m0_to_f32(block.e) × mxfp4_values[nibble_code]
```

## 4. E2M1 Value Table (All 16 Codes)

```c
static constant float ds4_metal_mxfp4_values[16] = {
     0.0f,  0.5f,  1.0f,  1.5f,  2.0f,  3.0f,  4.0f,  6.0f,   // codes 0–7 (positive)
    -0.0f, -0.5f, -1.0f, -1.5f, -2.0f, -3.0f, -4.0f, -6.0f,   // codes 8–15 (negative)
};
```

| Code (4 bits) | Binary | Sign | Value | Notes |
|---------------|--------|------|-------|-------|
| 0x0 | 0000 | + | 0.0 | Positive zero |
| 0x1 | 0001 | + | 0.5 | Subnormal (mantissa only) |
| 0x2 | 0010 | + | 1.0 | |
| 0x3 | 0011 | + | 1.5 | |
| 0x4 | 0100 | + | 2.0 | |
| 0x5 | 0101 | + | 3.0 | |
| 0x6 | 0110 | + | 4.0 | |
| 0x7 | 0111 | + | 6.0 | Maximum positive |
| 0x8 | 1000 | − | −0.0 | Negative zero |
| 0x9 | 1001 | − | −0.5 | |
| 0xA | 1010 | − | −1.0 | |
| 0xB | 1011 | − | −1.5 | |
| 0xC | 1100 | − | −2.0 | |
| 0xD | 1101 | − | −3.0 | |
| 0xE | 1110 | − | −4.0 | |
| 0xF | 1111 | − | −6.0 | Maximum negative |

Bit layout interpretation: `[S][E1 E0][M0]` — 1 sign bit, 2 exponent bits, 1 mantissa bit.

## 5. Block Size and Row Stride

### Constants

| Symbol | Value | Meaning |
|--------|-------|---------|
| `QK_MXFP4` | 32 | Elements per block |
| `sizeof(block_mxfp4)` | 17 | Bytes per block |
| `DS4_MXFP4_PAIR_STATIC_NB` | 128 | Blocks/row for gate/up (ne00=4096) |
| `DS4_MXFP4_PAIR_STATIC_ROW_BLOCKS` | 128 | Same as above (row_blocks alias) |
| `DS4_MXFP4_DOWN_STATIC_NB` | 64 | Blocks/row for down (ne00=2048) |
| `DS4_MXFP4_DOWN_STATIC_ROW_BLOCKS` | 64 | Same as above |

### Row stride calculation

```
row_bytes = (ne00 / QK_MXFP4) * sizeof(block_mxfp4)
          = blocks_per_row * 17
```

| Dimension (ne00) | Blocks/row | Row bytes | Typical use |
|------------------|-----------|-----------|-------------|
| 2048 | 64 | 1088 | Down projection |
| 4096 | 128 | 2176 | Gate/up projection |

The row byte count equals `args.nb01` in the kernel. Rows are stored contiguously — no padding or alignment between rows within a single expert's weight matrix.

## 6. Expert Stride and Memory Layout

### Expert memory layout

Expert weights are stored as a **flat row-major array of experts**, where each expert is a contiguous block of rows:

```
Expert 0:  [row 0][row 1][row 2]...[row N-1]
Expert 1:  [row 0][row 1][row 2]...[row N-1]
  ...
Expert E-1: [row 0][row 1][row 2]...[row N-1]
```

### Expert stride

```
expert_bytes = n_rows × row_bytes
             = n_rows × blocks_per_row × sizeof(block_mxfp4)
```

For typical DeepSeek-V4 dimensions:

| Projection | n_rows (ne01) | ne00 | row_bytes | expert_bytes |
|------------|--------------|------|-----------|-------------|
| Gate | mid_dim | in_dim (2048) | 1088 | mid_dim × 1088 |
| Up | mid_dim | in_dim (2048) | 1088 | mid_dim × 1088 |
| Down | out_dim | mid_dim | varies | out_dim × row_bytes |

### Kernel access pattern

The kernel addresses expert data as:
```metal
device const char *gate_expert = src0_gate + (int64_t)expert * args.nb02;
device const char *up_expert   = src0_up   + (int64_t)expert * args.nb02;
```

Where `args.nb02` = expert stride in bytes. Within an expert:
```metal
device const block_mxfp4 *x = (device const block_mxfp4 *)(expert_base + first_row * args.nb01);
// Access: x[row * row_blocks + block_index]
```

### Three separate tensors

Gate, up, and down projection weights are stored as **three separate GPU buffer regions** (not interleaved). Each tensor contains all experts contiguously:

```
[gate tensor: expert0...expertE-1] [up tensor: expert0...expertE-1] [down tensor: expert0...expertE-1]
```

The test allocates them at page-aligned offsets within a single mmap region.

## 7. Interleaved vs. Separate Planes

### Within each block: INTERLEAVED

The scale byte (`.e`) and data bytes (`.qs`) are stored as a single contiguous 17-byte struct:

```
Offset 0:     E8M0 scale byte
Offset 1–16:  16 packed nibble bytes (32 E2M1 values)
```

This repeats for every block along the row:

```
[e₀][qs₀[0..15]] [e₁][qs₁[0..15]] [e₂][qs₂[0..15]] ... [eₙ₋₁][qsₙ₋₁[0..15]]
```

### NOT separate scale/data planes

The layout is **interleaved block-by-block** — scales and data are NOT stored in separate contiguous arrays. There is no "scale plane" and "data plane" in memory. Every 17th byte (starting at offset 0, 17, 34, 51, ...) is a scale byte; the remaining bytes are data.

### Implication for Metal native MX tensors

Metal's native MX tensor format typically expects:
- A contiguous data plane (all nibbles together)
- A separate scale plane (all E8M0 bytes together)

DS4's block-interleaved layout `[scale][16 data bytes][scale][16 data bytes]...` is **structurally incompatible** with a two-plane representation unless:
1. Metal inline tensor strides can express the interleaved stride pattern (17-byte period with 1-byte scale at offset 0 and 16-byte data at offset 1), OR
2. A gather/repack is performed to separate the planes

This is the central compatibility question for task 5.3/5.4.

## 8. Decode Path Variants

### 1. Float LUT (threadgroup)

Used in the main matvec kernel. 16-entry float table loaded into threadgroup memory:
```metal
threadgroup float *lut = (threadgroup float *)shmem;
if (sgitg == 0) lut[tiisg] = ds4_metal_mxfp4_values[tiisg & 15];
```
Scale applied per-block: `e8m0_to_f32(xb.e) * sum_of_products`

### 2. Half LUT (pre-multiplied)

256×16 table: `ds4_metal_mxfp4_half_lut[E8M0_byte][E2M1_code]` → half  
Pre-computes `scale × value` for every possible (scale, code) pair.  
Special case: E8M0=0xFF falls back to float arithmetic (infinity × zero → NaN issue).

### 3. Half-domain scaling

Uses `ds4_metal_mxfp4_half_values[16]` with `half(scale) * half(value)`.  
Valid only when E8M0 ∈ [103, 142] (scale is exactly representable in half without double-rounding).  
Falls back to float arithmetic outside that range.

---

## 9. Alignment and Packing Notes

- **No inter-block padding:** Blocks are packed contiguously, 17 bytes each.
- **No inter-row padding:** `nb01 = blocks_per_row × 17` with no alignment gaps.
- **No inter-expert padding** within a tensor: `nb02 = n_rows × nb01`.
- **Page alignment between gate/up/down tensors:** Test code uses `align_up(offset, pagesize)` between the three weight matrices.
- **17-byte alignment is NOT power-of-2:** This makes pointer arithmetic irregular. The kernel uses byte-offset casting rather than aligned struct arrays.

| Property | DS4 MXFP4 value | Standard MX E2M1 (expected) | Compatible? |
|----------|-----------------|---------------------------|-------------|

### Key compatibility risks (for task 5.3/5.4):

1. **Plane separation:** Metal MX tensors almost certainly require separate data and scale planes. DS4 interleaves them per-block.
2. **Nibble ordering:** DS4 uses a split-half convention. If Metal expects sequential nibble order, a reorder is needed.
3. **17-byte non-aligned stride:** Metal tensors likely require power-of-2 or specific alignment for inline construction.
4. **Scale=0 semantics:** DS4 maps e=0 to `2^(-126)` (nonzero). Need to confirm this matches Metal's E8M0 convention.
