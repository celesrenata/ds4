# Task 0.2 — TensorOps Implementation Inventory

## 1. `DS4_METAL_HAS_TENSOR` usage

The macro is defined as a preprocessor symbol (`@"1"`) at library compile time in `ds4_metal.m` line 6405, gated by `g_metal4_tensor_api_enabled`. It guards three shader-level `#ifdef` blocks and the source preamble:

| Location | Purpose |
|---|---|
| `ds4_metal.m:4267-4275` | Source preamble: `#include <metal_tensor>`, `#include <MetalPerformancePrimitives/MetalPerformancePrimitives.h>`, `using namespace mpp::tensor_ops;` |
| `metal/dense.metal:1903` | Dense prefill TensorOps kernel (`kernel_mul_mm_mpp_direct_rhs` family) |
| `metal/dsv4_misc.metal:6317` | Indexer score TensorOps kernel (`kernel_dsv4_indexer_scores_nax`) |
| `metal/moe.metal:8727` | Attention-output low-rank projection + routed-expert grouped matmul TensorOps kernels |

## 2. TensorOps API usage summary

All TensorOps code uses:
- `metal_tensor` (inline tensor construction from device/threadgroup pointers)
- `mpp::tensor_ops::matmul2d` with `matmul2d_descriptor`
- `execution_simdgroups<4>` (4 SIMD groups / 128 threads)
- Cooperative destination tensors (`get_destination_cooperative_tensor`)
- `tensor.slice()` for sub-views
- `cT.store(tD)` for writing results

No cooperative tensor *inputs* to `matmul2d` are used yet — all current kernels stage weights into threadgroup memory and read activations directly from device memory.

## 4. Host pipeline registration and dispatch map

### 4.1 TensorOps enable chain

```
ds4_gpu_init()
  → ds4_gpu_detect_capabilities()
    → checks Metal4 family, device name (M5/M6/A19/A20)
    → ds4_gpu_compile_tensor_probe()  [compiles+creates pipeline from inline source]
    → g_metal4_tensor_api_enabled = 1
  → DS4_METAL_HAS_TENSOR macro set at library compile time
  → g_metal4_tensor_api_enabled gates ds4_gpu_mpp_available()
```

### 4.2 Runtime dispatch gates

| Function | Returns true when |
|---|---|
| `ds4_gpu_mpp_available()` | `g_metal4_tensor_api_enabled && !g_quality_mode` |
| `ds4_gpu_use_mpp_attn_out_low_matmul()` | `ds4_gpu_mpp_available()` |
| `ds4_gpu_routed_mm_mpp_mask()` | `ds4_gpu_mpp_available() ? 7 : 0` (bits: gate=1, up=2, down=4) |

### 4.3 Pipeline lookup

All TensorOps shader pipelines are retrieved on-demand via:
- `ds4_gpu_get_mul_mm_pipeline(name, bc_inp, bc_out)` — for dense matmul
- `ds4_gpu_get_mul_mm_id_pipeline(name, bc_out)` — for routed-expert matmul  
- `ds4_gpu_get_pipeline(name)` — for indexer/other kernels

Pipelines are lazily created from the compiled Metal library. The library itself is compiled once at init from concatenated `.metal` source with the `DS4_METAL_HAS_TENSOR` macro injected.

### 4.4 Tile selection logic (dense)

For Q8_0, Q4_0, Q4_K, F16:
```
if n_tok % 128 == 0 → NR1 = 128
else if n_tok % 64 == 0 → NR1 = 64
else → NR1 = 32
```
The host picks the widest tile that evenly divides the batch (or the aligned prefix in split mode).

### 4.5 Split-prefix dispatch (Q8_0 only currently)

When `n_tok >= 192 && n_tok % 32 != 0`:
- TensorOps handles the aligned prefix `n_tok - (n_tok % 32)` rows
- Legacy boundary-safe kernel handles the tail `n_tok % 32` rows

## 5. Default vs retained/forced/experimental status

### Default paths (auto-enabled on M5+ without user intervention)

| Path | Condition |
|---|---|
| Dense F16/Q8_0/Q4_0/Q4_K prefill TensorOps | `mpp_available` + alignment + batch ≥ 32 |
| Indexer score NAX | `mpp_available` + `n_tokens ≥ 16` |
| Attention-output low-rank Q8_0/Q4_K | `mpp_available` + `n_tokens ≥ 32` + 64-alignment |
| Routed IQ2_XXS gate/up/down TensorOps | `mpp_available` (all 3 bits of `mpp_mask`) |
| Routed Q2_K/IQ2_XXS down F16 TensorOps | `mpp_available` + `request_mid_f16` |

### Retained / conditional paths

| Path | Status |
|---|---|
| Dense Q8_0 decode TensorOps (batch-1) | Only used when caller passes `prefer_decode_mpp=true`; not the global default |
| Prefill dual-head indexer | `mpp_available` + specific head geometry (64 heads, top_k=512, window=128, head_dim=512) |

### Forced / experimental

No user-facing force-enable flags for TensorOps specifically. The system has:
- `DS4_METAL_DISABLE_METAL4` — global kill switch (disables all TensorOps)
- `--quality` mode — disables TensorOps paths (forces legacy for correctness comparison)
- Individual `DS4_METAL_DISABLE_*` env vars for other subsystems but none specifically for "force TensorOps on pre-M5"

### Not TensorOps (gaps identified for this spec)

| Operation | Current state | Opportunity |
|---|---|---|
| Routed MXFP4 gate/up/down prefill | Simdgroup matrix only | **Primary target** — no `matmul2d` in moe.metal for MXFP4 |
| Routed Q4_K gate/up prefill | Simdgroup pair-swiglu | Potential TensorOps candidate |
| Dense Q2_K/IQ2_XXS prefill | Only routed Q2_K/IQ2_XXS has TensorOps | Complex dequant; feasibility unclear |
| Speculative verify small-batch | Legacy mul_mv paths | Crossover point research needed |
| FlashAttention | Custom compressed kernels | Only if post-MoE profiling shows material |
| Batch-1 decode (all quants) | Manual matvec | Bandwidth-bound; unlikely win |

## 6. Terminology conventions in codebase

| Term | Meaning in DS4 |
|---|---|
| `mpp` / `MPP` | Metal Performance Primitives (the TensorOps namespace) |
| `nax` / `NAX` | Neural Accelerator eXtensions — DS4's informal name for TensorOps kernels; used in host_name strings for Q4/Q8 variants |
| `tensor` / `TensorOps` | Metal 4 tensor API (`metal_tensor` + `mpp::tensor_ops`) |
| `direct_rhs` | TensorOps design where activation (RHS) is read directly from device memory, not staged to threadgroup |
| `cooperative tensor` / `cT` | The `matmul2d` destination cooperative tensor — distributed accumulator that avoids device-memory round trip |
| `Metal4` | Apple Metal 4 family; `g_metal4_*` prefix for all capability state |
| `M5 neural accelerators` | M5 GPU shader-core matrix acceleration exposed through TensorOps |

## 7. Key architectural observations

1. **All current TensorOps kernels use the same pattern**: stage weights to threadgroup half tile → create inline tensor from device-memory RHS → `matmul2d` with 4 simdgroups → cooperative accumulator → store. No cooperative tensor *inputs* are used yet.

2. **The routed MoE IQ2_XXS/Q2_K TensorOps path (`kernel_mul_mm_id_mpp`)** stages BOTH operands to threadgroup memory before tensor creation, unlike the dense direct-RHS design. This is the older staged pattern noted in comments as slower for dense, but necessary here because routed tokens are indexed non-contiguously.

3. **MXFP4 has no TensorOps path** — the current MXFP4 routed kernels use simdgroup matrix operations. This is the primary gap identified in this spec.

4. **The TensorOps enable is automatic on M5** — no user opt-in needed. The only controls are kill switches (`DS4_METAL_DISABLE_METAL4`, `--quality`).

5. **Pre-M5 devices are explicitly excluded** — the auto-enable checks for M5/M6/A19/A20 device name strings. Older Metal 4 capable devices get the legacy path by default.

6. **Compile-time probe** validates the full TensorOps pipeline creation at startup. If the probe fails (SDK too old, runtime issue), all TensorOps is disabled gracefully.
