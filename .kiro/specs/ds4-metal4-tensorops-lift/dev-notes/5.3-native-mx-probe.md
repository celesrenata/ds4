# 5.3 Native-MX Conformance Probe — Decision Notes

## Status: BLOCKED — SDK 26.5 Has No Native MX Types

**Date:** Task executed against macOS 26.5 SDK  
**Validates:** R7, R12  
**Test file:** `tests/test_mxfp4_native_mx_probe.c`

---

## 1. Finding

The installed macOS 26.5 SDK (Xcode 26.6, Metal compiler 32023.883) provides **NO**:
- FP4/E2M1 tensor element type
- E8M0 scale-plane type
- Multi-plane (MX) tensor constructors
- Block-factor / scale-grouping mechanism

Only `int4b_format` and `uint4b_format` (plain 4-bit integers) are available. These are **representation-incompatible** with E2M1 floating-point: the hardware performs integer arithmetic on int4b operands, not floating-point decode.

**Consequence:** The native-MX conformance test cannot exercise the actual Metal MX path. The GPU portion is deferred pending macOS 27 SDK availability.

---

## 2. What Was Produced

A complete CPU reference test (`tests/test_mxfp4_native_mx_probe.c`) that:

### Tests executed (all PASS):

1. **All 16 E2M1 codes × 10 representative E8M0 scales** — Verifies that the DS4 LUT matches an independent bit-field decode implementation. Scales tested: 0, 1, 64, 100, 126, 127, 128, 150, 200, 254.

2. **DS4 decoder consistency** — Constructs single-code weight blocks and dots against basis vectors at both low-nibble (element j) and high-nibble (element j+16) positions. 256 probes, all exact.

3. **Basis-vector matmul** — 16 rows × 64 elements with random patterns covering all 16 codes. For every element position, a basis-vector dot confirms exact value recovery. 1024 probes, zero failures.

4. **Nibble-ordering convention** — Proves the split-half convention holds: `qs[j] & 0x0F` → element j, `qs[j] >> 4` → element j+16.

5. **Multi-block row matmul** — 4 rows × 128 elements (4 blocks) with deliberately different E8M0 scales per block. Cross-checks dot-product result against element-wise decode.

### Stub for native path:

The test contains a `#if defined(DS4_METAL_SDK_NATIVE_LOWBIT)` section that outlines exactly what must be done when macOS 27 SDK arrives:
- Create a native MX tensor from the same weight bytes
- Matmul against basis vectors
- Compare against CPU reference values
- Document any nibble-ordering or scale-semantic differences

## 3. E8M0 Scale Convention (DS4)

| E8M0 byte | DS4 float value | Formula |
|-----------|----------------|---------|
| 0 | 2^(-127) ≈ 5.877e-39 | bit pattern 0x00400000 (smallest positive subnormal) |
| 1 | 2^(-126) | `(uint32_t)1 << 23` |
| 127 | 2^0 = 1.0 | Unity |
| 254 | 2^127 ≈ 1.7e38 | Maximum finite |

**Important:** DS4's e=0 maps to 2^(-127), NOT zero and NOT 2^(-126). The OCP MX spec may define e=0 differently. This must be verified against the actual Metal native-MX implementation.

---

## 4. Nibble-Ordering Question

### DS4 convention (split-half):
```
qs[j] & 0x0F → element j       (j = 0..15)  — first half of block
qs[j] >> 4   → element j + 16  (j = 0..15)  — second half of block
```

### Possible Metal conventions:

**A) Sequential (most common for hardware nibble packing):**
```
qs[j] & 0x0F → element 2j      — even elements
qs[j] >> 4   → element 2j + 1  — odd elements
```

**B) Split-half (same as DS4):**
```
qs[j] & 0x0F → element j       — first half
qs[j] >> 4   → element j + 16  — second half
```

### Impact:

| Metal convention | Nibble reorder needed? | Additional cost |
|-----------------|----------------------|-----------------|
| Sequential (A) | YES — must repack or reinterpret | Per-block nibble shuffle |
| Split-half (B) | NO — nibbles are compatible | Only plane separation needed |

This cannot be answered without the macOS 27 SDK. The test infrastructure is ready to determine this immediately once the types are available.

---

## 5. Plane Separation (Structural Incompatibility)

Regardless of nibble ordering, DS4's layout is structurally incompatible with separate-plane MX tensors:

**DS4 on-disk layout (per block, 17 bytes):**
```
[E8M0 scale byte][16 data bytes (32 nibbles)]
```

**Metal MX tensor (expected, separate planes):**
```
Data plane:  [all nibble bytes contiguously]
Scale plane: [all E8M0 bytes contiguously]
```

With DS4's 17-byte stride and interleaved scale/data, a zero-copy native MX tensor view is almost certainly impossible. The stride descriptor would need to skip 1 byte every 17 bytes for the data plane and extract 1 byte every 17 bytes for the scale plane — which exceeds what inline tensor stride descriptors typically support.

### Viable paths (in preference order):
1. **Resident expert cache repack** — When an expert enters the hot cache, create a native-MX-friendly copy (separate planes). Cost amortized over many tokens.
2. **Per-tile custom dequant** — Use existing custom dequant into cooperative tensors (Candidate B). No layout change needed.
3. **Full repack** — NOT acceptable (violates R3: no full-model copy).

---

## 6. Decision for Task 5.6

The native-MX decision cannot be finalized until macOS 27 SDK is available. Current evidence supports a **conditional deferred** state:

- **If** Metal MX uses split-half nibble ordering **and** inline stride descriptors can express the interleaved layout → possible native view (unlikely given 17-byte non-power-of-2 stride)
- **If** Metal MX requires separate planes → resident-cache repack is the best option
- **If** nibble ordering differs → additional reorder step required on top of plane separation
- **In all cases** → custom dequant to cooperative tensors (Candidate B) remains the fallback and is implementable NOW
