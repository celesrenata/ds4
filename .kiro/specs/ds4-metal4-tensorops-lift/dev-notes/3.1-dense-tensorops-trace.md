## 1. Kernel Implementation (`metal/dense.metal`, ~line 1903)

### Template Signature

```metal
template<
    short NR1,                   // token tile width (32, 64, or 128)
    typename SA, typename SA_4x4, typename block_q, short nl,
    void (*dequantize_func)(device const block_q *, short, thread SA_4x4 &),
    typename T0, typename T0_4x4, typename T1>
kernel void kernel_mul_mm_mpp_direct_rhs(...)
```

### Fixed Constants

| Symbol | Value | Meaning |
|--------|-------|---------|
| `NR0` | 64 | Output-dimension tile (rows of weight matrix processed per threadgroup) |
| `NK` | 32 | K-step (inner-dimension depth per matmul iteration) |
| `NL` | NK/16 = 2 | Number of 16-value dequant chunks per k-step |
| `NUM_THREADS` | 128 | Threads per threadgroup |

### Tile Geometry

- Output tile: **NR0 × NR1** = 64 × {32, 64, 128} output elements per threadgroup
- K-step: 32 (each loop iteration accumulates 32 inner-dimension values)
- `matmul2d_descriptor(NR1, NR0, NK, false, true, true, multiply_accumulate)`
- Execution: `execution_simdgroups<4>` (4 SIMD groups per threadgroup)

## 2. Direct RHS Design (Confirmed)

The activation matrix (RHS, `srcB`) is accessed **directly from device memory** — no threadgroup staging:

```metal
device T1 *ptrB = (device T1 *)(srcB + args.nb12*i12 + args.nb13*i13);
const int strideB = args.nb11/sizeof(T1);
auto tB = tensor(ptrB, dextents<int32_t, 2>(K, N), array<int, 2>({1, strideB}));
```

The inline `tensor()` call wraps the existing device pointer, avoiding any copy.

The kernel comment explicitly states: _"this version stages only the model weight tile and lets MPP read the dense RHS activation matrix directly from device memory. That direct-RHS shape was the clear win for DS4's large aligned F16/Q8_0 prompt matmuls."_

## 3. Double-Buffered Weight Staging (Confirmed)

Two threadgroup tile buffers are allocated:

```metal
threadgroup SA *sa = (threadgroup SA *)shmem;
auto tA0 = tensor(sa,          dextents<int32_t, 2>(NK, NR0));   // buffer 0
auto tA1 = tensor(sa + NR0*NK, dextents<int32_t, 2>(NK, NR0));   // buffer 1
```

Total threadgroup memory needed: `2 × NR0 × NK × sizeof(SA)` = `2 × 64 × 32 × 2` = **8192 bytes**.

The K-loop alternates between buffers:

```metal
stage_tile(0, sa);                          // prefetch first tile into buffer 0
threadgroup_barrier(mem_flags::mem_threadgroup);

uint buf_sel = 0;
for (int loop_k = 0; loop_k < K; loop_k += NK) {
    auto mA = (buf_sel ? tA1 : tA0).slice(0, 0);   // consume current buffer
    auto mB = tB.slice(loop_k, r1);
    mm.run(mB, mA, cT);                             // matmul2d

    const int next_k = loop_k + NK;
    if (next_k < K) {
        buf_sel ^= 1u;                               // flip to other buffer
        stage_tile(next_k, buf_sel ? sa + NR0*NK : sa);  // prefetch next tile
    }
    threadgroup_barrier(mem_flags::mem_threadgroup);   // one barrier per step
}
```

This yields one threadgroup barrier per K-step instead of two (the earlier prototype that staged both operands required two barriers).

### Host-Side Threadgroup Memory Allocation

| Quant | Prefill allocation | Decode allocation |
|-------|-------------------|-------------------|
| F16 | `2u * 64u * 32u * sizeof(uint16_t)` = 8192 | — |
| Q8_0 | `2u * 64u * 32u * sizeof(uint16_t)` = 8192 | `64u * 32u * sizeof(uint16_t)` = 4096 |
| Q4_0/Q4_K | `64u * 32u * sizeof(uint16_t)` = 4096 | — |

**Note:** The Q4 prefill dispatch allocates only 4096 bytes (single buffer), while the kernel template requires 8192 bytes for double-buffering. The Q4 path either relies on Metal allocating at least the minimum (threadgroup bounds may differ by implementation), or this represents a latent allocation mismatch worth investigating in task 3.2.

## 4. Host Dispatch Chain

### 4.1 Capability Gate

```
ds4_gpu_mpp_available()
    = g_metal4_tensor_api_enabled && !g_quality_mode
```

`g_metal4_tensor_api_enabled` is set during init when:
1. macOS ≥ 26.0 runtime is available
2. Device supports `MTLGPUFamilyMetal4`
3. Device name contains "M5", "M6", "A19", or "A20"
4. `ds4_gpu_compile_tensor_probe()` succeeds (compiles a minimal TensorOps shader)
5. `DS4_METAL_DISABLE_METAL4` env var is **not** set
6. `DS4_METAL_DISABLE_TENSOROPS` env var is **not** set (global rollback)

### 4.2 Full Dispatch Decision Tree (Per Quant)

All quant paths follow the same structure:

```
ds4_gpu_matmul_{F16,Q8_0,Q4}_tensor(out, model_map, ..., n_tok)
  │
  ├─ n_tok == 1 → matvec / decode path
  │     ├─ [Q8_0 only] if ds4_gpu_mpp_available() && prefer_decode_mpp && (in_dim % 64) == 0
  │     │      → "kernel_mul_mm_q8_0_f32_nax_direct_rhs" (NR1=32, single-token TensorOps)
  │     └─ else → legacy matvec kernel
  │
  ├─ n_tok <= {8 or 16} → mul_mv_ext small-batch path
  │
  └─ n_tok >= 32 (prefill) → TensorOps candidate
        │
        ├─ Check: ds4_gpu_mpp_available()
        ├─ Check: (in_dim % 64) == 0   [Q8_0/Q4: 64; F16: 32]
        ├─ Check: (out_dim % 64) == 0
        ├─ Check: (n_tok % 32) == 0  OR split-prefix logic [Q8_0 only]
        │
        ├─ Tile selection:
        │     n_tok % 128 == 0 → NR1 = 128
        │     n_tok %  64 == 0 → NR1 = 64
        │     else             → NR1 = 32
        │
        ├─ Pipeline lookup: ds4_gpu_get_mul_mm_pipeline(nax_fn, false, false)
        │     ├─ success → encode and dispatch TensorOps kernel
        │     └─ fail → ds4_gpu_warn_mpp_fallback() → fall through to legacy
        │
        └─ Fallback: kernel_mul_mm_{quant}_f32 (simdgroup-matrix tiled kernel)
```

### 4.3 Q8_0 Split-Prefix Logic

Unique to the Q8_0 path. When n_tok is not 32-aligned:

```c
const bool split_nax_prefix =
    !g_quality_mode && n_tok >= 192u && (n_tok % 32u) != 0u;
const uint64_t nax_rows =
    (n_tok % 32u) == 0u ? n_tok :
    (split_nax_prefix ? n_tok - (n_tok % 32u) : 0u);
```

- If `n_tok >= 192` and `n_tok % 32 != 0`: split into aligned TensorOps prefix + legacy tail
- If `n_tok < 192` and unaligned: entire projection goes to legacy kernel
- If `--quality` mode: never split (single kernel for reproducibility)

### 4.4 Compute Command Encoding

```objc
id<MTLComputeCommandEncoder> enc = ds4_gpu_compute_encoder(cb);
[enc setComputePipelineState:pipeline];
[enc setBytes:&args length:sizeof(args) atIndex:0];           // mm args struct
[enc setBuffer:wbuf  offset:inner_offset     atIndex:1];      // weight matrix (model-mapped)
[enc setBuffer:xbuf  offset:tensor_offset(x) atIndex:2];      // activation (device buffer)
[enc setBuffer:outbuf offset:tensor_offset(out) atIndex:3];   // output (device buffer)
[enc setThreadgroupMemoryLength:{4096 or 8192} atIndex:0];    // weight staging shmem
[enc dispatchThreadgroups:MTLSizeMake(
        n_tok / nax_tile_n,        // X: token tiles
        out_dim / 64u,             // Y: output-row tiles (NR0=64)
        1)                         // Z: batch dimension
     threadsPerThreadgroup:MTLSizeMake(128, 1, 1)];           // 128 threads = 4 SIMD groups
```

### Selection Criteria (All Quants)

The dispatch is **not** gated by experimental flags or per-quant force-enables. The only controls are:
- `DS4_METAL_DISABLE_METAL4` — disables Metal 4 family detection
- `DS4_METAL_DISABLE_TENSOROPS` — global rollback for all TensorOps
- `--quality` mode — disables all TensorOps in favor of deterministic legacy paths

### No Experimental-Only Dense Variants

At the current revision, no dense `kernel_mul_mm_mpp_direct_rhs` variant is behind a separate force-enable or retained as experiment-only. All compiled variants enter the dispatch path automatically when the capability gate passes.

## 6. Dispatch Flow Summary (Graph Operation → Kernel Execution)

```
DS4 model forward pass
  │
  ├─ Dense projection (attention Wq/Wk/Wv/Wo, FFN, etc.)
  │     calls ds4_gpu_matmul_{f16,q8_0,quant}_tensor()
  │
  ├─ Validate: model range, buffer sizes, dimensions
  │
  ├─ Wrap model weight range → MTLBuffer (mmap-backed)
  │
  ├─ Obtain command buffer
  │
  ├─ Batch dispatch decision:
  │     n_tok == 1          → matvec path (not TensorOps by default)
  │     n_tok 2..{8-16}     → mul_mv_ext small-batch path
  │     n_tok >= 32         → TensorOps candidate
  │
  ├─ TensorOps admission:
  │     ds4_gpu_mpp_available() ?
  │     alignment checks passed ?
  │     pipeline lookup succeeded ?
  │
  ├─ Tile selection:
  │     n_tok % 128 == 0 → 128-token tile
  │     n_tok %  64 == 0 →  64-token tile
  │     else             →  32-token tile
  │
  ├─ Encode compute command:
  │     args + weight buffer + activation buffer + output buffer + threadgroup memory
  │     Grid: (n_tok/tile_n) × (out_dim/64) × 1
  │     Threads: 128 × 1 × 1
  │
  └─ Submit and wait (or continue encoding)
```

## 7. Observations and Potential Issues

1. **Q4 threadgroup memory mismatch**: Q4_0 and Q4_K prefill dispatch allocates `64 * 32 * sizeof(uint16_t)` = 4096 bytes, while Q8_0 and F16 allocate `2 * 64 * 32 * sizeof(uint16_t)` = 8192 bytes. The kernel template uses two buffers (`tA0` and `tA1`), requiring 8192 bytes for correct double-buffering. This may be harmless if Metal over-allocates threadgroup memory, or it could cause subtle corruption. Needs investigation in task 3.2.

2. **Q8_0 decode path uses TensorOps**: The single-token Q8_0 path offers TensorOps when `prefer_decode_mpp` is true, but the default public API passes `false`. The `prefer_decode_mpp` code comment says "Classic Q8_0 matvec is substantially faster than MPP at n_tok=1." So decode TensorOps is compiled but not default-enabled.

3. **128-token tile retained**: The code comment says "the 128-token RHS tile is kept when the batch alignment allows it because the later tile_n=64 retest was neutral/slower." This is empirical project knowledge — 128 outperforms 64 for aligned batches on M5.

4. **Split-prefix is Q8_0 exclusive**: Only the Q8_0 path implements the split-prefix optimization for unaligned token counts. The F16 and Q4 paths require full 32-alignment, falling entirely to legacy when unaligned.

5. **No MXFP4 or Q2_K TensorOps in dense**: Only F16, Q8_0, Q4_0, and Q4_K have `kernel_mul_mm_mpp_direct_rhs` variants. MoE quants (MXFP4, Q2_K, IQ2_XXS) do not have dense TensorOps implementations.
