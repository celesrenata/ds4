# Task 9.3 — Native int2 Tensor Representability Proof

_Requirements: R7_

---

## 1. Summary

**Native Metal int2/uint2 tensors cannot represent Q2_K or IQ2_XXS data.**

This is proven on three independent grounds:

1. **SDK absence**: The installed macOS 26.5 SDK does not contain any `int2b_format` or `uint2b_format` tensor element type. The type does not exist — it cannot be instantiated, compiled, or tested.
2. **Q2_K structural incompatibility**: Even if a hypothetical int2 type existed, Q2_K's asymmetric per-group scale+min dequantization cannot be expressed as a single linear scale+zero_point mapping over a 2-bit integer tensor.
3. **IQ2_XXS fundamental mismatch**: The 2-bit data in IQ2_XXS is a codebook index, not a weight value. No linear transformation of a 2-bit integer can reproduce the codebook's non-linear output.

**Conclusion**: The only viable TensorOps path for Q2_K and IQ2_XXS remains custom dequantization → threadgroup/cooperative f16 tile → `matmul2d`. This path already exists in the production MPP kernels.

## 3. Q2_K Structural Incompatibility

### 3.1 Q2_K Dequantization Formula

From `metal/moe.metal`:

```metal
void dequantize_q2_K(device const block_q2_K *xb, short il, thread type4x4 & reg) {
    const float d = xb->d;           // per-block f16 scale
    const float min = xb->dmin;      // per-block f16 minimum
    uint8_t sc = xb->scales[il];     // per-16-element group: packed scale+min

    // ...extract 2-bit weight q from qs[]...
    dl = d * (sc & 0xF) * coef;      // effective group scale
    ml = min * (sc >> 4);            // effective group minimum

    for (int i = 0; i < 16; ++i) {
        reg[i/4][i%4] = dl * (q[i] & mask) - ml;
    }
}
```

The per-element dequantization is:

```
x[i] = d × (scale_4bit) × shift_factor × raw_2bit_value − dmin × (min_4bit)
```

Where:
- `d` = f16 per-block (1 value per 256 elements)
- `dmin` = f16 per-block (1 value per 256 elements)
- `scale_4bit` = lower 4 bits of `scales[group]` (1 value per 16 elements)
- `min_4bit` = upper 4 bits of `scales[group]` (1 value per 16 elements)
- `shift_factor` = {1, 1/4, 1/16, 1/64} depending on which pair of bits within the byte
- `raw_2bit_value` = unsigned integer ∈ {0, 1, 2, 3}

### 3.2 What a Native int2 Tensor Would Provide

A hypothetical native `int2` or `uint2` tensor assumes a linear affine mapping:

```
x[i] = scale × int2_value + zero_point
```

Where `scale` and `zero_point` are uniform across the entire tensor (or at most per-channel/per-block at a fixed granularity determined by the API).

### 3.3 Proof of Incompatibility

**Argument 1 — Group-varying scale**: Q2_K has 16 independent scale values within each 256-element block (one `scale_4bit` per 16 elements). A native int2 tensor has at most one scale per tensor or per block. There is no way to express 16 distinct multiplicative scales within a single 256-element tensor view.

**Argument 2 — Group-varying zero point (min)**: The subtractive term `dmin × min_4bit` varies per 16-element group (16 distinct values per block). Native tensor zero_point is uniform per tensor/block.

**Argument 3 — Coupled scale dimensions**: The effective per-element scale is `d × scale_4bit × shift_factor` — a product of three terms at different granularities (per-block × per-group × per-position-in-byte). This three-level coupling has no representation in a flat `scale × value + offset` model.

**Argument 4 — Non-trivial bit extraction**: The 2-bit weights are packed 4 per byte. Extracting them requires position-dependent masking and shifting ({& 0x03, >> 2 & 0x03, >> 4 & 0x03, >> 6}). A native int2 tensor type would need to handle this packing implicitly — but Q2_K's packing is interleaved with a non-trivial group structure (the `il` indexing in the dequant function selects different byte ranges), not a simple dense pack.

### 3.4 Q2_K Verdict

Even with a hypothetical int2 tensor type:
- The format requires **per-16-element variable scales AND variable zero points**.
- Native tensor types provide **per-tensor or per-block uniform** scale/zero_point.
- No configuration of `int2 × scale + zero_point` can reproduce `d × scale_4bit × coef × q - dmin × min_4bit`.
- The mismatch is **structural and unfixable** without changing the quantization format itself.

**Q2_K cannot be represented by a native int2 tensor. ∎**

## 4. IQ2_XXS Fundamental Mismatch

### 4.1 IQ2_XXS Data Semantics

From the format documentation (dev-note 9.2) and `metal/moe.metal`:

The raw stored data for each 8-element quad is:
- An **8-bit codebook index** → selects one of 256 entries from `iq2xxs_grid[]`
- A **7-bit sign index** → selects one of 128 entries from `ksigns_iq2xs[]`
- A **4-bit sub-group scale** (shared per 32 elements)

The dequantization is:

```
value[j] = d × (0.5 + sub_group_scale) × 0.25 × iq2xxs_grid[codebook_idx][j] × sign[j]
```

Where:
- `iq2xxs_grid[idx]` returns 8 magnitude values, each ∈ {8, 25, 43}
- `sign[j]` ∈ {-1, +1}, encoded via lookup into `ksigns_iq2xs[]`

### 4.2 Why "2-bit" is Misleading

The "2-bit" in IQ2_XXS refers to the **bits-per-weight** compression ratio (2.0625 bpw), not to the stored representation. The actual stored fields are:

| Field | Bits | Nature |
|-------|------|--------|
| Codebook index per 8 values | 8 | Memory-indirect lookup key |
| Sign index per 8 values | 7 | Lookup key into sign table |
| Sub-group scale per 32 values | 4 | Linear multiplier |
| Block scale | 16 (f16) | Linear multiplier |

No individual stored quantity is a 2-bit weight value. The information compression comes from the codebook design (256 patterns × 128 sign patterns cover the weight space efficiently), not from 2-bit integers.

### 4.3 Proof of Incompatibility

**Argument 1 — Indirection**: The data bits are codebook indices, not weight values. A native int2 tensor interprets each 2-bit field AS the (scaled) value. IQ2_XXS requires a table lookup to recover the actual value. Hardware tensor units cannot perform arbitrary memory-indirect table lookups.

**Argument 2 — Non-linear value space**: The codebook outputs are {8, 25, 43}. These three magnitudes are not linearly spaced:
- 25 − 8 = 17
- 43 − 25 = 18
- Ratio: not exactly uniform, and there are only 3 distinct values mapped from 256 codebook patterns of 8 elements each.

No affine transformation `scale × int2 + zero_point` over {0, 1, 2, 3} can produce {8, 25, 43} (or any subset) because:
- 3 output values cannot be mapped from 4 input values linearly (one input would be unused or collide)
- Even if we tried: `scale × 0 + zp = 8`, `scale × 1 + zp = 25` → scale = 17, zp = 8 → `scale × 2 + zp = 42 ≠ 43`

**Argument 3 — Separate sign encoding**: IQ2_XXS encodes sign independently from magnitude via a lookup table. Native int2 (signed) would encode sign in the 2-bit value itself (e.g., two's complement: -2, -1, 0, 1). The format's sign-magnitude separation with parity-encoded sign tables has no analog in integer tensor semantics.

**Argument 4 — 8-element group atomicity**: Each codebook index determines all 8 values in a quad simultaneously. There is no per-element 2-bit field — the closest analog is "1 byte indexes 8 values." This is fundamentally incompatible with any per-element tensor type.

### 4.4 IQ2_XXS Verdict

IQ2_XXS's stored data is not a 2-bit weight. It is a structured codebook encoding requiring:
- Memory-indirect table lookup (256-entry × 8-byte grid)
- Separate sign-table lookup (128-entry table)
- Multi-level scale composition

No native tensor type — int2, uint2, or any linear-affine type — can express this. The format requires custom decode logic.

**IQ2_XXS cannot be represented by a native int2 tensor. ∎**

## 5. What Already Works: Custom Dequant → TensorOps

The production MPP kernels already implement the correct architecture:

```
kernel_mul_mm_id_q2_K_f16_mpp     — Q2_K via staged dequant → simdgroup matmul
kernel_mul_mm_id_iq2_xxs_f16_mpp  — IQ2_XXS via staged dequant → simdgroup matmul
```

These kernels:
1. Load compressed block data from device memory
2. Perform custom dequantization (bitfield extraction for Q2_K; codebook + sign lookup for IQ2_XXS)
3. Stage decompressed f16 values into threadgroup memory
4. Feed the f16 tile to `matmul2d` / simdgroup matrix operations
5. Accumulate and store results

This is the **only correct** path. It preserves the exact dequantization semantics while still benefiting from TensorOps hardware for the matrix multiply itself.

### 5.1 Architecture Diagram

```
Q2_K / IQ2_XXS blocks (device memory, mmap-backed)
    │
    ▼
Custom shader dequant (per-thread)
    │  - Q2_K: bitfield extract → group scale × q − group min
    │  - IQ2_XXS: grid LUT + sign LUT → magnitude × sign × scale
    │
    ▼
Threadgroup f16 tile (staging)
    │
    ▼
matmul2d / simdgroup_matrix (TensorOps / M5 Neural Accelerator)
    │
    ▼
Cooperative f32 accumulator → final output
```

### 5.2 Why This Path Cannot Be Bypassed

A "native int2" path would skip the custom dequant step, interpreting raw bytes directly as 2-bit integers for hardware matmul. This would:
- For Q2_K: multiply by wrong group-varying scale/offset, producing garbage
- For IQ2_XXS: multiply codebook indices (not weights) by activations, producing nonsense

The dequant step is not optional overhead — it is the format's semantics.

## 6. Policy Determination

Per design §9 policy:

> 1. Document the exact DS4 block structure. ✓ (Tasks 9.1, 9.2)
> 2. Determine whether a native tensor can represent it exactly. **No — proven impossible** (this document)
> 3. If not, do not build a misleading "native int2" path. **Confirmed: no native int2 path will be built.**

### 6.1 Implications for Task 9.4

Task 9.4 (benchmark cooperative custom dequant) should evaluate whether the existing staged-dequant path through threadgroup memory can be improved by:
- Using cooperative tensors as matmul inputs (avoiding threadgroup round-trip) — requires custom dequant output directly to cooperative tensor mapping
- Larger tile sizes on M5
- Overlapped dequant with matmul (double-buffering the dequant stage)

The question is *performance optimization of the correct custom-dequant path*, not whether a native bypass exists.

### 6.2 Implications for Task 9.5 (Keep/Reject)

The native int2 TensorOps path for Q2_K and IQ2_XXS is **rejected**:
- Representation incompatibility is structural and proven
- No SDK support exists on the current platform (macOS 26.5)
- Even future int2 SDK support would not help — the formats cannot map to linear affine int2

The custom-dequant TensorOps path (existing MPP kernels) is the only viable acceleration route for these formats. Its retention depends on benchmark results from task 9.4.
