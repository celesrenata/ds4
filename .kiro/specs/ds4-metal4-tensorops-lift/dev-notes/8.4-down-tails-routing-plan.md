## 1. Summary of Expected Result

**The TensorOps down-projection kernel inherits identical tail behavior to
gate/up (task 7.5).** The `matmul2d` hardware tile runs at constant speed
regardless of valid column count. Tail distributions do not materially affect
TensorOps performance.

This is a validation benchmark, not a discovery benchmark: we expect to confirm
that the analysis from 7.5 holds for the down path with no surprises.

- Net wasted compute at 8192 tokens: ~7% — but "wasted" matmul2d cycles do not

## 3. Down-Projection Specifics

### 3.1 Tile geometry (from 8.2)

Same as gate/up TensorOps:
- NR0=64 (output dimension tile)
- NR1=32 (token tile)
- NK=32 (reduction tile)
- `execution_simdgroups<4>`
- Formats: MXFP4 (half-LUT dequant), Q4_K, Q8_0

### 3.2 Difference from gate/up

The down projection differs structurally in one way:

- **Gate/up:** Produces paired outputs per tile (gate + up), applies SwiGLU in epilogue
- **Down:** Produces a single output per tile, writes to per-expert scratch slot

This means the down epilogue is **simpler** (one scatter-write per tile instead
of paired write + SwiGLU). Tail handling in the down kernel is strictly a subset
of the gate/up tail handling. If tails are fine for gate/up, they are fine for down.

### 3.3 Post-GEMM sum kernel

Per task 8.3, the sum across experts (`kernel_dsv4_moe_sum6_f32`) is a separate
dispatch, operating on the per-expert scratch buffer. It is pure bandwidth-bound
(~0.24 μs/token) and completely independent of tile tail distribution.

### 4.1 Objective

Confirm that the TensorOps down-projection kernel shows < 5% performance
variation across different tail distributions. This validates the 7.5 decision
for the down path specifically.

### 4.2 Controlled-distribution protocol

Construct synthetic work buffers with four controlled tail distributions:

| Config | Description | Expected tail fraction |
|--------|-------------|----------------------|

### 4.4 Acceptance criteria

| Metric | Pass | Investigate |
|--------|------|-------------|
| Config A vs B kernel time | < 5% difference | > 10% difference |
| Config A vs C kernel time | < 5% difference | > 10% difference |
| Config D end-to-end prefill | ≥ control or < 1% regression | > 1% regression |
| Down TensorOps vs legacy A/B | Repeatable improvement | Neutral or regression |

### 4.5 What "investigate" means

If > 10% variation is observed between all-full and all-short-tail configurations:
1. The hardware MAY benefit from smaller tiles (contradicts matmul2d constant-time model)
2. Re-evaluate whether NR1=16 tail tile is warranted for the down path
3. Check if the performance delta comes from the epilogue (write coalescing) rather than matmul2d itself

## 5. Why We Expect Constant-Time Behavior

From 7.5 §2.4 and the M5 hardware model:

1. **matmul2d is a hardware tile operation.** The Neural Accelerator processes
   a 32×64×32 tile as a single unit. No "partial tile" instruction exists.

2. **The epilogue short-circuits.** The scatter-write loop iterates only `nr1`
   times. For the down kernel this is a single write per valid token (no
   SwiGLU/paired complexity).

3. **Weight staging is independent of nr1.** The K-loop stages the full 64×32
   weight tile regardless of how many activation columns are valid. This is the
   dominant cost at small batch sizes — tails don't change it.

4. **Dispatch is per-expert, independent.** Each threadgroup processes one expert
   tile independently. A fast-finishing tail tile doesn't block or interfere with
   full tiles on other SIMDgroups.

## 6. Routing Distribution: Down vs Gate/Up

The down projection processes the **same token-to-expert assignment** as gate/up
within the same MoE layer. The `map0` kernel generates work items identically
for both paths. Therefore:

- Expert bucket sizes are identical
- Tail sizes are identical
- Empty/small expert distribution is identical

The only difference is the weight matrix dimensions:
- Gate/up: `[expert_mid_dim × hidden_dim]` — two matrices per expert
- Down: `[hidden_dim × expert_mid_dim]` — one matrix per expert

Both use the same NR0=64, NR1=32, NK=32 tile. The number of K-loop iterations
differs (proportional to the reduction dimension), but the tail-tile behavior
in the token dimension is identical.

## 8. Requirement Traceability

### R13 (Benchmark methodology)

> WHEN an optimization is retained  
> THE SYSTEM SHALL show repeatable benefit across more than one prompt/batch shape
> relevant to the target operation.

**Plan satisfies R13.** The protocol tests at 2048/4096/8192 token prefill sizes,
each producing different tail distributions. The controlled-distribution configs
(A–D) provide shape diversity. The A/B harness uses fresh sessions, alternating
order, and bit-identity enforcement.

### R16 (Performance acceptance)

> WHEN TensorOps is used for a production prefill path  
> THE SYSTEM SHALL demonstrate a repeatable improvement over the immediately
> preceding production path for the shapes it claims.

**Plan satisfies R16.** The down-specific A/B (`--candidate-env
DS4_METAL_DISABLE_MXFP4_MOE_DOWN_MPP`) directly compares the TensorOps down path
against the legacy simdgroup path. If TensorOps shows repeatable improvement at
the specified prompt sizes, R16 is met for the down projection. If tail
distributions degrade the improvement below significance, the benchmark will
reveal it.
