# 9.5 Keep/Reject Decision — Quant-Specific TensorOps Paths

**Validates:** R7  
**Prerequisites:** 9.1 (Q2_K format), 9.2 (IQ2_XXS format), 9.3 (native int2 impossible), 9.4 (custom dequant efficient)  
**Triggers:** Stop condition 14.5

---

## 1. Summary

| Format | Native int2 TensorOps Path | Custom Dequant TensorOps Path |
|--------|---------------------------|-------------------------------|
| Q2_K | **REJECT** — impossible | **KEEP** — production MPP kernels |
| IQ2_XXS | **REJECT** — impossible | **KEEP** — production MPP kernels |

Native low-bit tensor APIs are **NOT used** for Q2_K or IQ2_XXS because representation does not match. This is not a performance trade-off — it is a structural impossibility.

---

## 2. Q2_K — Native int2 Path

### Decision: REJECT

### Evidence

1. **SDK absence** (task 9.3 §2): macOS 26.5 SDK contains no `int2b_format` or `uint2b_format` tensor element type. The type cannot be instantiated.

2. **Structural incompatibility** (task 9.1, task 9.3 §3): Q2_K uses asymmetric per-group (16-element) scale+min dequantization:
   ```
   x[i] = d × scale_4bit × shift_factor × raw_2bit − dmin × min_4bit
   ```
   A native int2 tensor provides only `scale × int2 + zero_point` with uniform scale/zero_point per tensor or per block. The three-level coupled scale (per-block × per-group × per-position) and group-varying zero point have no representation in a flat affine model.

3. **Non-trivial bit packing** (task 9.3 §3.3 Argument 4): Q2_K's byte layout interleaves 2-bit weights with a group structure (`il` indexing) that does not correspond to dense sequential packing expected by hardware int2 interpretation.

### Conclusion

Even if Apple adds `int2b_format` in a future SDK (macOS 27+), the format remains structurally incompatible. The mismatch is in the quantization semantics, not merely in SDK availability.

**No native int2 path will be built for Q2_K. ∎**

---

## 3. IQ2_XXS — Native int2 Path

### Decision: REJECT

### Evidence

1. **SDK absence** (task 9.3 §2): Same as Q2_K — no int2 tensor type exists on macOS 26.5.

2. **Fundamental semantic mismatch** (task 9.2, task 9.3 §4): IQ2_XXS does not store 2-bit weight values. It stores:
   - 8-bit codebook indices → lookup into `iq2xxs_grid[]` (256 × 8 bytes)
   - 7-bit sign indices → lookup into `ksigns_iq2xs[]` (128 entries)
   - 4-bit sub-group scales

   The "2-bit" refers to bits-per-weight compression ratio (2.0625 bpw), not to a stored 2-bit integer. The data requires memory-indirect table lookup — hardware tensor units cannot perform this.

3. **Non-linear value space** (task 9.3 §4.3 Argument 2): Codebook magnitudes {8, 25, 43} are not linearly spaced and cannot be produced by any affine transformation of {0, 1, 2, 3}.

4. **Group atomicity** (task 9.3 §4.3 Argument 4): Each codebook index determines all 8 values in a quad simultaneously. There is no per-element 2-bit field — the format is "1 byte indexes 8 values."

### Conclusion

IQ2_XXS is a codebook-based format that requires table lookup and sign expansion. No native tensor type — int2, uint2, or any linear-affine type — can express this. The incompatibility is fundamental and permanent.

**No native int2 path will be built for IQ2_XXS. ∎**

## 4. Q2_K — Custom Dequant TensorOps Path

### Decision: KEEP

### Production Implementation

```
kernel_mul_mm_id_q2_K_f16_mpp
```

### Architecture (frozen per task 6.5)

```
device Q2_K blocks (mmap-backed)
    │
    ▼
dequantize_q2_K (per-thread, ~2.3 ALU ops/element)
    │  bitfield extract → group scale × q − group min
    │
    ▼
threadgroup f16 tile (staging)
    │
    ▼
matmul2d (NR0=64, NR1=32, NK=32, execution_simdgroups<4>)
    │  M5 Neural Accelerator exercised here
    │
    ▼
cooperative F32 accumulator → store → scatter
```

### Performance Justification (task 9.4)

- Dequant cost: ~36 ALU ops + 17 byte loads per 16 output half values
- Dequant overhead relative to matmul: **~6.3%** per K-step
- On M5: dequant runs on standard ALU while matmul2d runs on tensor hardware → dequant is fully hidden
- No optimization path identified that would improve on the existing implementation (§4 of task 9.4 evaluated and rejected: double-buffering, larger tiles, half-precision scales, codebook prefetch)

### Why This Is the Permanent Path

The custom dequant step IS the format's semantics. Skipping it (as a native int2 path would) produces wrong results. The existing MPP kernel correctly implements staged custom dequant feeding TensorOps hardware matmul — this is the optimal and only valid architecture for Q2_K on Metal TensorOps.

## 5. IQ2_XXS — Custom Dequant TensorOps Path

### Decision: KEEP

### Production Implementations

```
kernel_mul_mm_id_iq2_xxs_f16_mpp          — standalone matmul
kernel_mul_mm_id_iq2_xxs_f32_mpp          — F32 RHS variant
kernel_mul_mm_id_iq2_xxs_mpp_pair_swiglu_f16  — fused gate+up with SwiGLU
```

### Architecture (frozen per task 6.5)

```
device IQ2_XXS blocks (mmap-backed)
    │
    ▼
dequantize_iq2_xxs (per-thread, ~2.4 ALU ops/element)
    │  constant-cache codebook LUT + sign LUT → magnitude × sign × scale
    │
    ▼
threadgroup f16 tile (staging)
    │
    ▼
matmul2d (NR0=64, NR1=32, NK=32, execution_simdgroups<4>)
    │  M5 Neural Accelerator exercised here
    │
    ▼
cooperative F32 accumulator → store → scatter
```

### Performance Justification (task 9.4)

- Dequant cost: ~38 ALU ops + 18 constant-space lookups per 16 output half values
- Codebook tables (2184 bytes total) fit entirely in GPU constant cache — steady-state lookups are effectively register-speed
- Dequant overhead relative to matmul: **~6.3%** per K-step
- On M5: fully hidden behind tensor hardware matmul
- The fused pair+SwiGLU variant (`mpp_pair_swiglu_f16`) already exists and exercises the same pattern

### Why This Is the Permanent Path

IQ2_XXS requires codebook lookup — this is not "overhead" that optimization could remove. The constant-cache-resident codebook + sign table decode is O(1) per element with no indirection chains beyond single-level LUT. The existing MPP kernel is the optimal implementation.

## 6. No Compatibility Theater

Per R7:

> WHEN Q2_K or IQ2_XXS is evaluated, THE SYSTEM SHALL NOT assume that "2-bit" Metal tensor support is representation-compatible merely because both formats use roughly two bits per weight.

This decision confirms:

- The name "2-bit" in Q2_K/IQ2_XXS describes compression ratio, not stored data type.
- No native int2 tensor path will be built for these formats regardless of future SDK support.
- Native low-bit APIs are used ONLY when representation matches (e.g., MXFP4 with native MX tensors per task 5.x series). For Q2_K/IQ2_XXS, representation does not and cannot match.
- The custom-dequant → threadgroup → matmul2d path is not a "fallback" or "workaround." It is the architecturally correct and only valid acceleration path.

---

## 7. Stop Condition 14.5 Triggered

> Stop native low-bit work for a quant format once byte-level incompatibility is proven.

**Status: TRIGGERED for both Q2_K and IQ2_XXS.**

The following are permanently closed for these formats:
- ❌ Native int2 compile probes
- ❌ Int2 tensor layout experiments
- ❌ Int2 alignment or stride tests
- ❌ Native int2 kernel prototypes
- ❌ Any "int2 TensorOps" code path for Q2_K or IQ2_XXS

The following remain active:
- ✓ Custom dequant optimization (if future profiling reveals opportunity)
- ✓ Tile geometry changes (if hardware generation changes trade-offs)
- ✓ Hardware benchmark measurement (pending M5 availability, per task 9.4 §6)

---

## 8. Final Statement

The existing production MPP kernels — `kernel_mul_mm_id_q2_K_f16_mpp`, `kernel_mul_mm_id_iq2_xxs_f16_mpp`, and `kernel_mul_mm_id_iq2_xxs_mpp_pair_swiglu_f16` — constitute the **permanent TensorOps acceleration path** for Q2_K and IQ2_XXS in DS4.

These kernels implement staged custom dequantization feeding the M5 Neural Accelerator through `matmul2d`. The dequant overhead (~6% of matmul work) is negligible and fully hidden on tensor hardware. No alternative architecture exists or is needed.

Native low-bit tensor APIs are reserved for formats where representation actually matches (MXFP4 ↔ native MX). For Q2_K and IQ2_XXS, the answer is definitive: custom dequant is the path, and it works.
