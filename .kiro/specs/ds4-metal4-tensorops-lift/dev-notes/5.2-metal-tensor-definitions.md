## 1. FP4 Data Type — NOT PRESENT

There is **no FP4, E2M1, float4b_format, or any low-bit floating-point tensor element type** in the macOS 26.5 SDK.

### What exists (Tier 3 — integer 4-bit only):
```metal
struct int4b_format {};    // signed 4-bit integer format
struct uint4b_format {};   // unsigned 4-bit integer format
```

These are **integer** format types — they have no floating-point semantics, no exponent bits, no mantissa interpretation, and no sign-magnitude encoding compatible with E2M1.

### What does NOT exist:
- No `float4b_format` or `fp4_format`
- No `e2m1_format` type
- No floating-point sub-half tensor element type
- No `__HAVE_FLOAT4B_FORMAT_TYPE__` or similar capability macro
- No float format types in `is_numeric_format<>` trait (only int4b and uint4b)

### Valid tensor element types (complete list from `metal_tensor` header):
- `half` (float16)
- `bfloat` (bfloat16)
- `float` (float32)
- `double` (if `__HAVE_NATIVE_DOUBLE__`)
- `char`, `signed char`, `uchar` (8-bit integers)
- `short`, `ushort` (16-bit integers)
- `int`, `uint` (32-bit integers)
- `int4b_format`, `uint4b_format` (4-bit integer format types)

## 3. Alignment and Block-Factor Requirements

### Tensor inline alignment
```cpp
#define __TENSOR_INLINE_ATTRS(EXTENTS_TYPE) \
    [[sizeas(...)]] \
    alignas(8)
```
- **Inline tensor (`tensor_inline`) alignment:** 8 bytes.
- The tensor descriptor itself requires 8-byte alignment.

### Packed numeric storage
For `packed_numeric_type<Format, N>`:
- Storage is `packed_vec<uchar, N * bits_per_element / 8>`
- Valid `N`: 1 to 32, where `N * format_bits % 8 == 0`
- For `int4b_format`: N must be even (since 4*N must be divisible by 8), so N ∈ {2, 4, 6, 8, ..., 32}
- **Maximum pack size: 32 elements** in a single `packed_numeric_type`

### Data pointer alignment for inline tensors
- The `__metal_init_strided_tensor()` call takes a raw data pointer — no explicit alignment constraint beyond natural type alignment is documented in the header.
- For format types, `data_handle_type` is `const device uchar *` (byte pointer), so **any byte-aligned device buffer is acceptable as a data source**.

### Block factor
- **No block_factor concept exists** in this SDK. The `packed_numeric_type` simply packs N elements of a given format into a byte vector. There is no grouping, scaling, or multi-plane semantics.

## 4. Allowed Inline Tensor Strides / Layout

### Strided tensor construction
The inline tensor constructor accepts:
```metal
tensor(data_handle_type ptr,
       thread const ExtentsType &extents,
       thread const array<StrideType, rank> &strides)
```

Strides are per-element (in units of elements, not bytes), with stride[0] being the innermost dimension stride.

### Packed layout (no explicit strides)
When constructed without strides:
```metal
tensor(data_handle_type ptr, thread const ExtentsType &extents)
```
The strides are computed as packed/row-major:
```metal
strides[0] = 1;
strides[i] = strides[i-1] * extents.extent(i-1);  // for i > 0
```

### Format-type stride restriction
For **format types** (int4b_format, uint4b_format), the `__is_tensor_inline_strides_packed` trait is based on `__is_thread_addrspace<ElementType>`. When the tensor is NOT in thread address space (i.e., device/constant — the normal case for weight tensors), **custom strides ARE allowed**.

However, the stride interpretation for sub-byte formats depends on how `packed_numeric_type` maps to storage — the actual byte packing of N elements means strides operate on packed groups, not individual sub-byte elements.

### Tensor descriptor types
Three tensor descriptor types are supported:
1. **`tensor_handle`** — host-created tensor passed via argument buffer
2. **`tensor_inline`** — shader-constructed from a device pointer + extents + optional strides
3. **`tensor_offset`** — sliced view of another tensor

For DS4's mmap-backed weights, `tensor_inline` is the relevant path: construct directly from existing device buffer pointers at runtime.

## 7. Implications for Task 5 (Native MXFP4 Compatibility)

**The native-MX path cannot be implemented or tested on this SDK.**

DS4's MXFP4 format uses E2M1 floating-point values with E8M0 scale blocks. The SDK provides only `int4b_format` (signed 4-bit integer) and `uint4b_format` (unsigned 4-bit integer). These are **representation-incompatible** with E2M1 floating-point:

- E2M1 has sign + 2-bit exponent + 1-bit mantissa → floating interpretation
- int4b_format is a plain signed 4-bit integer → linear integer interpretation
- The matmul hardware will perform integer arithmetic on int4b, not floating-point decode

**This means:**
1. Task 5.3 (native-MX conformance probe) cannot compile the MX tensor path.
2. Task 5.4 (zero-copy feasibility) has no native API to test against.
3. The native-MX decision (Task 5.6) can only be: **deferred pending macOS 27 SDK**.
4. Custom dequantization (Candidate B in design §8.4) remains the viable path for MXFP4 TensorOps.

---

## 8. Available Acceleration Path for MXFP4

Even without native FP4/MX support, the following TensorOps path exists:

```
MXFP4 packed data (device memory)
  → custom shader dequant to half/bfloat (threadgroup or cooperative tensor)
  → matmul2d with half/bfloat inputs
  → cooperative destination
  → post-matmul fusion
```

The `uint4b_format` type could theoretically be used to load the raw nibbles via a tensor view, but the actual FP4→half conversion must still happen in custom shader code since the hardware treats these as unsigned integers, not E2M1 floats.
