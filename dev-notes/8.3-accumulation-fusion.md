# 8.3 Accumulation Fusion — Evaluation

## Status: REJECT FUSION — Keep Per-Expert GEMM + Existing Sum

**Validates:** R6, R12  
**Prerequisites:** 8.1 (down accumulation order)  
**Decision:** Do NOT fuse the expert sum into the TensorOps down kernel. Retain per-expert `kernel_mul_mm_id_mpp` tiles with the existing `kernel_dsv4_moe_sum6_f32` sum.

---

## 1. Decision

**The accumulation across selected experts SHALL NOT be fused into the TensorOps down kernel.** The existing architecture — per-expert GEMM writes to scratch `[token][slot][out_dim]`, then a separate `kernel_dsv4_moe_sum6_f32` sums sequentially — is retained.

Individual per-expert projections are optimized via task 8.2's TensorOps kernel (`kernel_mul_mm_id_mpp` with MXFP4/Q4_K/Q8_0 dequant). The sum kernel is unchanged.

---

## 2. Why Fusion Is Infeasible

### 2.1 Per-token routing destroys expert coherence

The fundamental obstacle: each token routes to a **different** set of 6 experts from the pool of 256. A tile of 32 tokens will generally have 32 different expert selections.

The existing work-buffer dispatch groups tokens **by expert** — all tokens routed to expert E are batched into contiguous tiles for that expert's weight matrix. This gives:
- Coalesced weight reads (one base address per expert tile)
- High token-dimension occupancy per expert (many tokens share the same weight)
- Efficient threadgroup utilization (NR1=32 tokens per tile)

A fused kernel would need to group tokens **by token** instead, processing all 6 experts for a token subset. This requires:

```
For each of 6 experts in token T's routing:
    Load weights from expert_base[routing[T][slot]]
    Run full K-loop (mid_dim/NK iterations)
    Accumulate into running sum
```

Each expert has a **different base address** (potentially scattered across the model map). Within a 32-token tile, each token's 6 experts could be entirely different. The kernel would need to:
- Handle up to 32×6 = 192 different expert weight addresses per threadgroup
- OR restrict to processing one token at a time (wasting the NR1=32 token tile)

### 2.2 Weight coalescing is destroyed

The staged-dequant pattern loads `NR0=64` rows from a weight matrix per K-step. When tokens are bucketed by expert, all 128 threads cooperatively load the same 64×32 weight tile — fully coalesced, maximum bandwidth utilization.

In a fused kernel processing 6 experts sequentially for the same token tile:
- Each expert switch requires loading from a completely different memory region
- The weight staging benefits of batching tokens (amortizing weight loads across NR1=32 tokens) are retained only if all 32 tokens share the same expert for that slot
- In practice, slot-aligned expert agreement across 32 tokens is rare for non-trivial prompt diversity

### 2.3 Cooperative accumulator cannot span experts (with batched tokens)

The `matmul2d` cooperative tensor in `multiply_accumulate` mode accumulates across K-loop iterations. You **could** run 6 experts' worth of K-loops into a single cooperative accumulator:

```metal
// Hypothetical fused approach:
for (int slot = 0; slot < 6; slot++) {
    for (int k = 0; k < mid_dim; k += NK) {
        stage weights[expert_for_slot[slot]][k]
        stage activation[k]
        mm.run(activation, weights, cT)  // accumulates
    }
}
// cT now holds sum of all 6 expert projections
```

This is mathematically correct and preserves slot-sequential accumulation order. However:

- **Token divergence**: Different tokens in the NR1=32 tile route to different experts. The weight tile for "slot 0" is expert A for token 0 but expert B for token 1. You cannot stage a single weight tile that works for all 32 tokens simultaneously.
- **Workaround**: Process only tokens with identical routing (effective batch size = 1 in worst case, defeating TensorOps entirely).
- **Alternative workaround**: Use NR1=1 token tile. This reduces to a matvec with 6× overhead and no batching benefit.

### 2.4 The sum kernel is nearly free

`kernel_dsv4_moe_sum6_f32` performs:
- 6 float reads + 5 adds + 1 float write per output element
- Pure memory-bandwidth-bound (arithmetic intensity ≈ 0)
- Launch cost: one threadgroup dispatch per token batch
- Data: reads `6 × out_dim × sizeof(float)` = 6 × 4096 × 4 = 96 KB per token
- At M5 memory bandwidth (~400 GB/s): ~0.24 μs per token for the sum alone

The sum kernel cost is negligible relative to the per-expert matmul time. Eliminating it provides no meaningful speedup.

---

## 3. What IS Optimized

### 3.1 Per-expert TensorOps down projection (task 8.2)

Each per-expert GEMM tile uses the frozen staged-dequant TensorOps pattern:
- NR0=64, NR1=32, NK=32, `execution_simdgroups<4>`
- M5 Neural Accelerator via `matmul2d`
- Format-specific dequant (MXFP4 half-LUT, Q4_K, IQ2_XXS, Q2_K)

This is where the TensorOps speedup matters — the matmul itself accounts for >99% of the down-projection compute time.

### 3.2 Existing sum6 retained unchanged

The sum kernel:
- Preserves the exact sequential accumulation order (slot 0→5)
- Produces bit-identical results vs the current path
- Has no correctness risk
- Is already optimally simple (a loop of 6 adds)

### 3.3 Intermediate buffer is free

The scratch buffer `[token][slot][out_dim]` (= `6 × 4096 × 4 × N_tokens` bytes) is:
- Already allocated by the existing dispatch infrastructure
- Reused across layers (not a per-layer allocation)
- Not an additional memory overhead introduced by this decision

## 4. Correctness Preservation

| Aspect | Status |
|--------|--------|
| Accumulation order | **Preserved exactly** — slot-sequential (0→5) via existing sum6 kernel |
| Per-expert GEMM arithmetic | Same staged-dequant pattern as existing `kernel_mul_mm_id_mpp` |
| `g_quality_mode` oracle | Compatible — non-fused path with sum kernel matches quality fallback |
| Speed-bench logit identity | No change in reduction semantics → existing tests pass unchanged |
| TP ownership | Preserved — unowned experts zero their slot in scratch, sum6 adds zero |

---

## 5. Comparison: Fused vs Retained

| Criterion | Fused (rejected) | Per-expert + sum (retained) |
|-----------|-------------------|---------------------------|
| Token batching (NR1=32) | ✗ (requires identical routing across tile) | ✓ (bucketed by expert) |
| Weight coalescing | ✗ (6 different addresses per slot) | ✓ (one expert base per tile) |
| TensorOps utilization | Poor (NR1≈1 effective) | Full (NR1=32 tokens per expert bucket) |
| Intermediate memory | Eliminated (~96KB/token) | Retained (already allocated) |
| Sum kernel cost eliminated | Yes (~0.24 μs/token) | No |
| Correctness risk | Medium (novel reduction path) | None (existing proven path) |
| Implementation complexity | High (new dispatch, new work buffer, routing-aware tiling) | None (existing infra) |
| Net performance impact | Negative (destroyed batching far exceeds sum-kernel savings) | Neutral (sum is noise) |

---

## 6. When Fusion WOULD Be Justified

Fusion could be reconsidered if:

1. **Decode single-token**: The existing `sum6` fused decode kernels already do this — they iterate 6 experts in a register loop because batch=1 means no NR1 tile to worry about. This is already production code and is unrelated to TensorOps prefill.

2. **All tokens route identically**: In degenerate cases (batch=1 or highly correlated routing), a fused approach might avoid scratch writes. But the sum kernel is so cheap that even in this case the benefit is immeasurable.

3. **Future hardware with cross-threadgroup cooperative reduction**: If Metal gained the ability to accumulate cooperative tensors across threadgroups dispatched to different experts, fusion could be revisited. No such API exists.

---

## 7. Requirement Traceability

### R6 (Routed-MoE TensorOps lift)

> WHEN a cooperative-tensor result can be consumed by the next operation without an intermediate device-memory store  
> THE SYSTEM SHALL evaluate that fusion and retain it only if correctness and end-to-end benchmarks pass.

**Evaluated and rejected.** The cooperative tensor result from each per-expert down GEMM cannot be directly consumed by a cross-expert sum because different threadgroups process different experts. The intermediate device-memory store (per-expert scratch) is the correct architectural boundary.

### R12 (Correctness)

> WHEN replacing an existing kernel whose benchmark contract is bit-identical  
> THE SYSTEM SHALL first attempt to preserve bit identity.

**Satisfied.** By retaining the existing `kernel_dsv4_moe_sum6_f32` with its slot-sequential accumulation, the TensorOps down path produces bit-identical sum results vs the current simdgroup path (given bit-identical per-expert outputs, which share the same matmul reduction contract).

---

## 8. Summary

Accumulation fusion is **rejected** for the TensorOps down prefill path because:

1. Per-token routing makes it impossible to batch weight loads across tokens in a fused kernel
2. The existing per-expert bucketing is optimal for weight coalescing and TensorOps tile utilization
3. The sum kernel costs ~0.24 μs/token — negligible vs the per-expert matmul time
4. The intermediate scratch buffer is already allocated
5. Retaining the existing sum preserves bit-identical accumulation order with zero correctness risk

The TensorOps speedup for the down projection comes entirely from accelerating the per-expert GEMM (task 8.2), not from eliminating the trivial sum.
