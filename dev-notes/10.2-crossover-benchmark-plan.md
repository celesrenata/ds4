# 10.2 — TensorOps Crossover Benchmark Plan

_Requirements: R11, R13_

Status: **PENDING HARDWARE EXECUTION** (requires M5 Apple Silicon)

---

## 1. Objective

Determine the batch size N at which TensorOps `matmul2d` becomes faster than the
existing small-batch kernels (tiny_pair matvec, per-token matvec, expert-major
grouped matmul) for each operationally relevant quantization format. This crossover
point informs the dispatch threshold that replaces the current hard-coded N≥32
boundary for `use_mm_id`.

From task 10.1: the N=6–31 gap zone has no specialized dispatch path, and session
batching at N=8–16 is the most operationally frequent scenario in that range.

---

## 2. Benchmark Matrix

### 2.1 Batch Sizes (N)

| N  | Source Scenario                              | Current Dispatch Path       |
|----|----------------------------------------------|-----------------------------|
| 2  | MTP verify                                   | tiny_pair matvec            |
| 4  | MTP/DSpark verify                            | tiny_pair matvec            |
| 5  | DSpark default block                         | tiny_pair matvec (boundary) |
| 8  | Session batch                                | per-token matvec (gap zone) |
| 12 | Session batch                                | per-token matvec (gap zone) |
| 16 | Max session batch / NAX indexer threshold    | per-token matvec (gap zone) |
| 24 | Large session batch                          | per-token matvec (gap zone) |
| 32 | Current mm_id threshold                      | expert-major grouped matmul |
| 48 | Above threshold (reference)                  | expert-major grouped matmul |

### 2.2 Quantization Formats

**Dense layers (attention Q/K/V/O projections):**
- Q8_0 — highest bandwidth, baseline quality
- Q4_K — production dense quant

**MoE layers (gate/up/down expert projections):**
- MXFP4 — primary MoE quant (E2M1 values, E8M0 scales, 32-value blocks)
- Q4_K — fallback/alternative MoE quant

### 2.3 Kernels Under Comparison

| Control Kernel                     | TensorOps Candidate            | Applicable N         |
|------------------------------------|--------------------------------|----------------------|
| `kernel_mul_mv_id_*` (tiny pair)   | TensorOps `matmul2d`           | N = 2–5             |
| `kernel_mul_mv_id_*` (per-token)   | TensorOps `matmul2d`           | N = 6–31            |
| `kernel_mul_mm_id_*` (grouped)     | TensorOps `matmul2d`           | N = 32–48           |
| `kernel_mul_mm_mpp_direct_rhs_*`   | — (self-reference for dense)   | N ≥ 32 (existing)   |

## 3. Measurement Protocol

### 3.1 Principles (per R13)

- Same engine instance for control and candidate.
- Warmed sessions (minimum 32 tokens warmup per variant).
- Alternating run order (ABBA/BAAB blocks) to cancel thermal drift.
- Fresh-session discipline: new session per measurement to avoid KV-cache effects.
- Minimum 4 ABBA repeats per data point for statistical significance.
- Report median and p5/p95 for each cell.

### 3.2 Isolation Method

Use environment variable rollback controls to A/B within the same binary:

```bash
# Control: force legacy path (disable TensorOps for MoE)
export DS4_METAL_DISABLE_MXFP4_MOE_GATE_UP_MPP=1
export DS4_METAL_DISABLE_Q4_K_PAIR_SWIGLU_MPP=1

# Candidate: enable TensorOps (unset the disables)
unset DS4_METAL_DISABLE_MXFP4_MOE_GATE_UP_MPP
unset DS4_METAL_DISABLE_Q4_K_PAIR_SWIGLU_MPP
```

For dense TensorOps (existing `matmul2d` path):
```bash
# Control: disable existing dense TensorOps
export DS4_METAL_DISABLE_TENSOROPS=1

# Candidate: TensorOps enabled (default)
unset DS4_METAL_DISABLE_TENSOROPS
```

### 3.3 Metrics to Capture (per R13)

For each (N, quant, kernel) cell:
1. **Kernel microbenchmark time** — isolated matmul dispatch latency (μs)
2. **Layer/stage time** — full MoE or attention projection stage (μs)
3. **Arithmetic throughput** — TFLOPS achieved
4. **Memory bandwidth utilization** — GB/s measured vs theoretical peak
5. **Dispatch overhead** — command encoder setup cost at small N

## 4. Execution Commands

### 4.1 Build

```bash
make metal-prefill-variant-bench
```

### 4.2 Dense TensorOps Crossover (Q8_0, Q4_K)

Run the prefill variant bench at controlled batch sizes. The `--prefix-tokens`
flag controls the prefill chunk; to isolate small-N behavior, set prefill chunk
equal to N so the entire forward pass runs at that batch width:

```bash
# For each N in {2, 4, 5, 8, 12, 16, 24, 32, 48}:
DS4_METAL_PREFILL_CHUNK=$N \
./speed-bench/metal_prefill_variant_bench \
  -m ds4flash-q8_0.gguf \
  --candidate-env DS4_METAL_DISABLE_TENSOROPS \
  --prefix-tokens $N \
  --warmup-tokens 32 \
  --repeats 4

DS4_METAL_PREFILL_CHUNK=$N \
./speed-bench/metal_prefill_variant_bench \
  -m ds4flash-q4k.gguf \
  --candidate-env DS4_METAL_DISABLE_TENSOROPS \
  --prefix-tokens $N \
  --warmup-tokens 32 \
  --repeats 4
```

Note: when `--candidate-env` is used, the harness **sets** that env var for the
candidate run and **unsets** it for control. So `DS4_METAL_DISABLE_TENSOROPS` as
candidate means: control = TensorOps enabled, candidate = TensorOps disabled.
A TensorOps win appears as candidate being slower than control.

### 4.5 Scripted Sweep (Recommended)

```bash
#!/bin/bash
# crossover_sweep.sh — run on M5 Apple Silicon
set -euo pipefail

MODELS=("ds4flash-q8_0.gguf" "ds4flash-q4k.gguf" "ds4flash-mxfp4.gguf")
NS=(2 4 5 8 12 16 24 32 48)
REPEATS=4
WARMUP=32
OUTDIR="speed-bench/crossover-results"
mkdir -p "$OUTDIR"

for model in "${MODELS[@]}"; do
  quant="${model%.gguf}"
  quant="${quant#ds4flash-}"

  for N in "${NS[@]}"; do
    echo "=== $quant N=$N ==="

    # Dense TensorOps crossover
    DS4_METAL_PREFILL_CHUNK=$N \
    ./speed-bench/metal_prefill_variant_bench \
      -m "$model" \
      --candidate-env DS4_METAL_DISABLE_TENSOROPS \
      --prefix-tokens $N \
      --warmup-tokens $WARMUP \
      --repeats $REPEATS \
      2>&1 | tee "$OUTDIR/${quant}_dense_N${N}.txt"

    # MoE TensorOps crossover (MXFP4-specific)
    if [[ "$quant" == "mxfp4" ]]; then
      DS4_METAL_PREFILL_CHUNK=$N \
      ./speed-bench/metal_prefill_variant_bench \
        -m "$model" \
        --candidate-env DS4_METAL_DISABLE_MXFP4_MOE_GATE_UP_MPP \
        --prefix-tokens $N \
        --warmup-tokens $WARMUP \
        --repeats $REPEATS \
        2>&1 | tee "$OUTDIR/${quant}_moe_gate_up_N${N}.txt"
    fi

    # MoE TensorOps crossover (Q4_K-specific)
    if [[ "$quant" == "q4k" ]]; then
      DS4_METAL_PREFILL_CHUNK=$N \
      ./speed-bench/metal_prefill_variant_bench \
        -m "$model" \
        --candidate-env DS4_METAL_DISABLE_Q4_K_PAIR_SWIGLU_MPP \
        --prefix-tokens $N \
        --warmup-tokens $WARMUP \
        --repeats $REPEATS \
        2>&1 | tee "$OUTDIR/${quant}_moe_pair_N${N}.txt"
    fi
  done
done
```

## 5. Expected Crossover Hypotheses

Based on the architecture (10.1 §5.2) and general TensorOps tile efficiency:

| Region          | Hypothesis                                                          |
|-----------------|---------------------------------------------------------------------|
| N = 2–4        | tiny_pair wins — too small for TensorOps tile utilization           |
| N = 5          | tiny_pair likely wins — hand-tuned fused pair for this exact shape  |
| N = 8          | **Crossover candidate** — enough arithmetic intensity for matmul2d  |
| N = 12–16      | TensorOps likely wins — neural accelerator tile becomes efficient   |
| N = 24–31      | TensorOps should win — currently falls to unoptimized per-token MV  |
| N = 32+        | Both use matmul; compare mm_id vs TensorOps matmul2d directly       |

The crossover point is expected to land in the **N = 8–16 range** for MXFP4 MoE
and possibly slightly lower (N = 6–12) for Q8_0 dense where the per-element
arithmetic is lighter.

---

## 6. Acceptance Criteria

Per R11 and R13:

1. Each cell in the matrix has at least 4 ABBA measurement pairs.
2. Crossover point identified to within ±2 tokens for each quant format.
3. Results saved as `speed-bench/crossover-results/*.txt` for reproducibility.
4. Statistical significance: the winning kernel must show ≥5% improvement at the
   crossover boundary (within measurement noise implies "no change, keep legacy").
5. If TensorOps wins at N < 32, document the recommended new dispatch threshold.
6. If TensorOps loses everywhere below N=32, document that finding and confirm the
   current threshold remains correct.

## 7. Profiling Follow-up (per R14)

After identifying the crossover point, capture Metal System Trace for:
- One N value below crossover (where legacy wins)
- The crossover N itself
- One N value above crossover (where TensorOps wins)

Verify that at the winning N values, the TensorOps dispatch actually utilizes the
M5 neural accelerator path (tensor instruction occupancy > 0 in GPU timeline).
