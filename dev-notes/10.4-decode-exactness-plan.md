# 10.4 — Decode Exactness Harness: PENDING HARDWARE EXECUTION

## Status

**PENDING HARDWARE EXECUTION** — requires Apple Silicon (M5-class) with macOS and the
ds4flash.gguf model file. Not executable on the current NixOS workstation.

## Command

```bash
./speed-bench/metal_decode_schedule_bench \
  -m ds4flash.gguf \
  --include-selection \
  --tokens 1024
```

Build prerequisite:

```bash
make metal-decode-schedule-bench
```

## Purpose

Verify that the TensorOps changes to MoE gate/up/down prefill paths (tasks 7–8) and the
measured crossover dispatch (task 10.3) have NOT regressed batch-1 decode performance or
correctness.

## What the harness validates

1. **Full-vocabulary bit-identical logit checking** — the harness aborts unless every
   full-vocabulary logit row is bit-identical between control and candidate.

2. **Token selection identity** (`--include-selection`) — both variants must select the
   same non-EOS token at every decode step.

3. **End-to-end decode throughput** — balanced A/B comparison with fresh sessions,
   alternating variant order (ABBA/BAAB), poisoned host logit buffers, and warmup.

## Expected result

**ALL logits bit-identical. No throughput regression.**

The TensorOps changes from tasks 7–10.3 affect only prefill and batched (N≥32) paths.
Batch-1 decode uses the existing specialized matvec/fused kernels and is never dispatched
through the new TensorOps code paths. Therefore:

- Logit bit-identity MUST hold (no new code is touched during batch-1 decode).
- Decode t/s MUST remain within normal benchmark noise.

## Critical invariant

**Batch-1 decode NEVER uses the new TensorOps kernels.**

The measured crossover dispatch (task 10.3) explicitly guards TensorOps activation behind
N≥32. The MoE TensorOps paths (tasks 7–8) are gated on prefill/batch token counts. The
existing dense/indexer TensorOps (tasks 3–4) were already prefill-only by design.

The decode schedule bench confirms this invariant holds end-to-end by checking that the
decode path produces identical results regardless of whether the TensorOps prefill paths
are present in the binary.

## Acceptance criteria

Per requirements R10, R12, R16:

| Criterion | Threshold | Source |
|-----------|-----------|--------|
| Logit correctness | Bit-identical full-vocabulary rows | R12 |
| Token selection | Identical non-EOS token at every step | R12, `--include-selection` |
| Decode throughput | No >1% regression vs control | R10, R16 |
| NaN/Inf | Zero occurrences | R12 |

## Failure modes and response

| Failure | Diagnosis | Action |
|---------|-----------|--------|
| Logit mismatch | New code leaking into batch-1 path | Find dispatch guard bug in crossover logic |
| Token selection divergence | Subtle precision change in shared path | Audit any shared constant/buffer changes |
| >1% decode regression | Pipeline creation overhead or cache pollution | Profile, isolate, gate pipeline creation to first prefill |
| Crash/abort | Pipeline or capability detection issue | Check runtime fallback path |

## Requirement traceability

- **R10** (Single-token decode): Retain existing specialized matvec path; TensorOps must
  not affect batch-1 decode unless it wins a balanced end-to-end benchmark.
- **R12** (Correctness): Bit-identical replacement contract; no silent weakening of tests.
- **R16** (Performance acceptance): No >1% regression in established end-to-end decode
  benchmark when TensorOps is enabled by default.

## When to execute

Run this harness on the Apple Silicon development machine after:
1. Tasks 7.x (MoE gate/up TensorOps) are merged.
2. Tasks 8.x (MoE down TensorOps) are merged.
3. Task 10.3 (measured crossover dispatch) is complete.
4. The binary is built with all TensorOps paths compiled and auto-enabled.

A passing result confirms the decode path is untouched and clears the gate for
tasks 11+ (post-MoE profiling and production hardening).
