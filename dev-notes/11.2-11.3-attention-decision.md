## 11.2 — Decision: Does Attention Merit TensorOps Work?

### Answer: Cannot determine — deferred per stop condition 14.6

The post-MoE prefill trace (task 11.1) has not been captured. Without profiling
data from Apple Silicon hardware showing the post-TensorOps-MoE bottleneck
distribution, this decision cannot be made on evidence.

### Decision Framework

When the trace is available, apply these thresholds (from 11.1 trace plan):

| Attention GPU time % | Action |
|---------------------|--------|
| >25% | Proceed with attention TensorOps investigation (11.3) |
| 15–25% | Evaluate absolute time saving vs complexity; may proceed |
| <15% | Defer per stop condition 14.6; redirect effort to hardening (task 12) |

### Why Deferral Is Correct

1. **No profiling data exists.** The decision requires a Metal System Trace from an
   Apple Silicon machine running the post-task-8 binary (combined MoE TensorOps
   enabled). This trace cannot be captured on the current NixOS workstation.

2. **The existing FlashAttention is highly specialized.** `flash_attn.metal` implements
   DeepSeek-V4 compressed attention with:
   - Causal visibility and mask scanning (block skip optimization)
   - KV padding for partial cache blocks
   - Sink token handling
   - ALiBi / linear bias support
   - Logit softcap
   - Broadcast mask support
   - SIMD-group matrix operations for QK and SV products
   - Dequantization paths for non-F16 K/V formats
   - Vector and non-vector variants with different parallelism strategies

   A TensorOps rewrite of these semantics carries significant correctness risk with
   uncertain performance benefit.

3. **Existing TensorOps coverage already handles the known compute-dense paths.**
   Tasks 3–4 lifted dense projections and indexer scoring. Tasks 7–8 lifted MoE
   gate/up/down. The ratio-4 indexer (task 4) already covers the regular matrix
   inner product within compressed attention scoring. The remaining FlashAttention
   work is dominated by memory-access patterns, softmax, masking, and causal logic —
   not pure matrix arithmetic.

4. **Design §10 is explicit.** The design document states:
   > "Do not start by replacing `flash_attn.metal`."
   > "Only proceed if attention remains a top prefill bottleneck."

5. **Risk/reward is unfavorable without data.** The existing attention kernel already
   uses SIMD-group matrix operations (`simdgroup_multiply_accumulate`). The inner
   QK and SV products are already hardware-accelerated via 8×8 matrix tiles. Moving
   to TensorOps `matmul2d` only helps if:
   - The tile sizes available through TensorOps are more efficient than 8×8 SIMD-group
     tiles for the actual K/V sequence lengths
   - The overhead of TensorOps tensor setup does not dominate for the relatively small
     per-block matrix multiplications within FlashAttention tiling
   - Cooperative tensor results can be consumed without extra materialization

### What Already Covers Attention Acceleration

The existing TensorOps indexer path (task 4, `kernel_dsv4_indexer_scores_nax`) already
accelerates the ratio-4 compressed-attention indexer scoring. This is the largest
regular matrix operation within DS4's attention system — the part most amenable to
TensorOps. The remaining FlashAttention operations are tiled block computations with
complex control flow that resist straightforward TensorOps replacement.

### Requirement Traceability

- **R16** (Performance acceptance): A production TensorOps path that improves a
  microbenchmark but regresses total prefill, TTFT, memory pressure, or load time
  SHALL NOT become default. Without profiling evidence that attention is a material
  bottleneck, adding TensorOps complexity to FlashAttention risks exactly this outcome.

## 11.3 — Conditional Prototype: Regular Matrix Inner Operation

### Status: CONDITIONAL ON 11.2 PROCEEDING — Currently Deferred

If task 11.2 proceeds (attention occupies >25% GPU time after MoE TensorOps), the
following surgical approach would be investigated. This section documents the plan
without implementing it.

### What Would Be Considered

**Only the regular QK score and Attn×V matrix inner products:**
- `Q × K^T` tile: token queries × key cache rows × head_dim (128 or 512)
- `Attn × V` tile: attention weights × value cache rows × head_dim

These are the two matrix multiplications within each FlashAttention tile block that
could potentially benefit from TensorOps `matmul2d`.

### What Would NOT Be Rewritten

- Causal masking logic
- Block skip optimization (the `blk` array scan)
- Top-k selection
- Softmax (online rescaling with M/S tracking)
- Sink token handling
- Logit softcap / ALiBi bias application
- Compressed-attention semantics
- KV padding kernel
- Mask broadcast logic
- Dequantization of non-F16 K/V formats
- Vector variant (single-query decode path)

### Candidate Approach

Within the existing FlashAttention tiling structure (Q queries × C cache rows per
block), replace the current SIMD-group 8×8 matrix multiply-accumulate loops with
TensorOps cooperative `matmul2d`:

```text
Current (SIMD-group matrix):
  for each K-tile step:
    simdgroup_load(mk, ...)    // 8×8 K block
    simdgroup_load(mq, ...)    // 8×8 Q block
    simdgroup_multiply_accumulate(mqk, mq, mk, mqk)

Candidate (TensorOps):
  for each K-tile step:
    cooperative load Q tile from threadgroup
    cooperative load K tile from device (direct RHS)
    matmul2d(Q_tile, K_tile, QK_accumulator)
```

The candidate would:
1. Use TensorOps only for the Q×K^T inner product within each (Q, C) tile block
2. Materialize QK scores back to threadgroup memory for softmax/mask application
3. Use TensorOps for the Attn×V inner product after softmax
4. Store output via the existing threadgroup O accumulator

### Why This Might Not Help

The FlashAttention tile sizes are relatively small:
- Q (query tile) = 8 queries per SIMD group (NSG groups share Q tile)
- C (cache tile) = 64 rows per block
- DK = 512 (head dimension for DeepSeek-V4)

The current 8×8 SIMD-group matrix operations already use hardware matrix units.
TensorOps `matmul2d` may offer larger effective tile sizes and better Neural
Accelerator utilization on M5, but:
- Setup overhead per small tile could dominate
- The cooperative tensor → threadgroup → cooperative tensor round-trip for softmax
  may negate any matmul speedup
- Register pressure from maintaining cooperative state alongside the complex
  FlashAttention bookkeeping (M, S, masks) may reduce occupancy

### Benchmark Required Before Committing

If 11.2 proceeds, the prototype must demonstrate:
- End-to-end attention stage speedup (not just QK matmul microbench)
- No correctness regression (same scores, same selected tokens)
- No occupancy regression severe enough to slow other concurrent work
- Benefit at realistic sequence lengths (8K–64K), not just synthetic short contexts

### Requirement Traceability

- **R5** (Existing indexer TensorOps path): The indexer already covers the largest
  regular matrix operation in compressed attention. Any FlashAttention TensorOps
  work must not duplicate or conflict with indexer acceleration.
- **R16** (Performance acceptance): Repeatable improvement required over the
  immediately preceding production path for the shapes it claims.
