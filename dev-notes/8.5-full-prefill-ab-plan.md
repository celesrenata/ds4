This workspace is **esnixi** (NixOS x86_64 workstation). The `metal-prefill-variant-bench`

- macOS with Metal GPU access
- Apple Silicon (M5-family for TensorOps dispatch)

The benchmark plan is documented here for execution on the macOS development machine.

---

## 2. Purpose

Task 7.8 measured gate/up TensorOps in isolation. Task 8.5 measures the **full MoE
TensorOps lift** by independently testing:

1. **Gate/up-only TensorOps** — down disabled, gate/up enabled (isolates gate/up contribution)
2. **Down-only TensorOps** — gate/up disabled, down enabled (isolates down contribution)
3. **Combined TensorOps** — all MoE TensorOps enabled (the production default)
4. **All disabled (control)** — full legacy simdgroup for both gate/up and down

This separates the contributions of each MoE phase and confirms they compose without
interference.

### 4.1 MoE Gate/Up TensorOps

| Variable | Effect when set |
|----------|----------------|
| `DS4_METAL_DISABLE_MXFP4_MOE_GATE_UP_MPP` | Disables MXFP4 gate/up TensorOps, falls back to simdgroup pair kernel |
| `DS4_METAL_DISABLE_Q4_K_PAIR_SWIGLU_MPP` | Disables Q4_K gate/up TensorOps, falls back to simdgroup pair kernel |

### 4.2 MoE Down TensorOps

| Variable | Effect when set |
|----------|----------------|
| `DS4_METAL_DISABLE_MXFP4_MOE_DOWN_MPP` | Disables `kernel_mul_mm_id_mxfp4_f16_mpp`, falls back to simdgroup down kernel |
| `DS4_METAL_DISABLE_Q4_K_MOE_DOWN_MPP` | Disables `kernel_mul_mm_id_q4_K_f16_mpp`, falls back to simdgroup down kernel |

### 4.3 Global TensorOps rollback

| Variable | Effect when set |
|----------|----------------|
| `DS4_METAL_DISABLE_TENSOROPS` | Disables ALL TensorOps dispatch (`mpp_mask = 0`) |

## 7. Harness Methodology (built into the binary)

Identical to the 7.8 plan — the `metal_prefill_variant_bench` harness enforces:

| Property | Implementation |
|----------|---------------|
| Same binary | Single Metal engine instance, variant selected by env var |
| Fresh sessions | New `ds4_session` created for every timed run |
| Alternating order | ABBA block (repeats 1, 3, 5…) + BAAB block (repeats 2, 4, 6…) |
| Warmup | ≥32 tokens untimed per variant before measurement |
| Bit-identical logits | Full vocabulary `memcmp` after each run; abort on mismatch |
| Logit buffer poisoning | Host buffer filled with alternating 0xa5/0x5a before copy |
| Default prefix | 8192 tokens |
| Default repeats | 2 (= 8 timed runs total: 4 control + 4 candidate) |

## 8. Acceptance Criteria (from R16)

### 8.1 Combined TensorOps prefill improvement target

> THE PROJECT SHOULD TARGET at least a **15% end-to-end M5 prefill improvement** on
> representative DeepSeek-V4 prompts after all enabled TensorOps work is combined.

Measured by §6.1 (Combined TensorOps vs All Legacy).

### 8.2 Individual kernel speedup target

> THE PROJECT SHOULD TARGET at least a **1.25× speedup** in the individual compute-dense
> kernels migrated to TensorOps.

The down-only A/B (§6.2) isolates the down projection contribution. Combined with
the 7.8 gate/up result, total MoE TensorOps benefit is assessed.

### 8.3 Additivity requirement

The combined benefit (§6.1) should approximately equal gate/up-only (§6.3) +
down-only (§6.2) contribution, within measurement noise. If combined is
materially less than the sum of parts, investigate interference (cache pressure,
occupancy, thermal throttling).

### 8.4 Bit-identical correctness

The harness aborts if any control/candidate logit row differs. Binary pass/fail
built into every measurement run.

### 8.5 Decode regression gate

> THE SYSTEM SHALL have no statistically significant regression greater than **1%** in the
> established end-to-end decode benchmark.

Verified separately via:
```bash
./speed-bench/metal_decode_schedule_bench \
  -m ds4flash.gguf \
  --include-selection \
  --tokens 1024
```

## 9. Expected Output Format

The harness prints per-run lines:
```
run=1 repeat=1 pattern=ABBA slot=1 variant=control tokens=8192 seconds=0.543210 tokens_per_second=15081.1234 exact=yes
run=2 repeat=1 pattern=ABBA slot=2 variant=candidate tokens=8192 seconds=0.612345 tokens_per_second=13381.5678 exact=yes
...
```

Followed by aggregates:
```
aggregate variant=control runs=4 tokens=32768 seconds=2.172840 tokens_per_second=15081.1234
aggregate variant=candidate runs=4 tokens=32768 seconds=2.449380 tokens_per_second=13381.5678
candidate_delta_percent=-11.2600 exact_runs=8 exact_floats=1048576 vocab=131072
```

A **negative** `candidate_delta_percent` means the candidate (legacy/rollback) is slower —
i.e., TensorOps (control) wins.

## 11. Decision Criteria

| Result | Action |
|--------|--------|
| Combined TensorOps wins ≥15% | ✓ Accept all MoE TensorOps as default. Full spec target met. |
| Combined wins 10–15% | ✓ Accept. Note gap to 15% target. |
| Combined wins 5–10% | ✓ Accept. Consider further tuning (tile sizes, occupancy). |
| Combined wins <5% | ⚠ Investigate. MoE may not be compute-bound enough for TensorOps to dominate. |
| Down-only shows <2% | ⚠ Down TensorOps may not be worth the complexity. Consider rejecting 8.2. |
| Gate/up + down < combined | ⚠ Synergy detected — investigate (shared cache warming, pipeline overlap). |
| Gate/up + down > combined | ⚠ Interference — investigate (thermal, cache pressure, occupancy contention). |
| Combined neutral or loses | **Reject** — revert to legacy for the losing component. |
| Logit mismatch | **Block** — fix correctness before retrying. |
| Decode regresses >1% | **Block** — investigate and fix before enabling as default. |

## 13. Relationship to Task 7.8

Task 7.8 measured gate/up TensorOps alone (down was already using legacy).
Task 8.5 extends this to measure:

- Whether the down TensorOps (task 8.2) adds incremental benefit
- Whether gate/up and down TensorOps compose cleanly
- The **total** MoE TensorOps prefill improvement (the spec's 15% target)

If 7.8 showed e.g. -8% `candidate_delta_percent` (gate/up TensorOps wins 8%),
and 8.5 combined shows -14%, then down adds approximately 6% incremental benefit.

## 14. Requirement Traceability

### R13 (Benchmark methodology)

> WHEN comparing a candidate against control  
> THE SYSTEM SHALL use the same engine, warmed sessions, alternating run order, and
> fresh-session discipline already used by DS4's Metal A/B harnesses.

**Satisfied.** The `metal_prefill_variant_bench` harness implements all of these.

> WHEN an optimization is retained  
> THE SYSTEM SHALL show repeatable benefit across more than one prompt/batch shape.

**Plan:** Commands in §6.1 and §6.5 cover 512, 2048, 8192, and 32768 token prefills.

### R16 (Performance acceptance)

> THE PROJECT SHOULD TARGET at least a 15% end-to-end M5 prefill improvement.

**Plan:** Measured by Combined A/B (§6.1). This is the primary spec acceptance metric.

> THE PROJECT SHOULD TARGET at least a 1.25× speedup in individual compute-dense kernels.

**Plan:** Per-component A/Bs (§6.2, §6.3) isolate each kernel's contribution.

> A production TensorOps path that improves a microbenchmark but regresses total prefill,
> TTFT, memory pressure, or load time SHALL NOT become default.

**Plan:** End-to-end prefill t/s is the primary metric. Decode regression gate (§8.5)
prevents hidden regressions.
