### Comparison Against Task 1.2 Baseline

Task 1.2 verified that the A/B harness worked pre-change. Task 13.2 uses the same
harness against the final production binary. The key comparison is:

- Task 1.2: default vs existing rollback (should have been ~0% delta, validating harness)
- Task 13.2: TensorOps-default vs full legacy (measures the total spec lift)

### Harness Methodology

Built into `metal_prefill_variant_bench`:

| Property | Implementation |
|----------|---------------|
| Same binary | Single Metal engine instance |
| Fresh sessions | New `ds4_session` per timed run |
| Alternating order | ABBA/BAAB block ordering |
| Warmup | ≥32 tokens untimed per variant |
| Bit-identical logits | Full vocabulary `memcmp`; abort on mismatch |
| Buffer poisoning | Host buffer 0xa5/0x5a fill before copy |

### Expected Output

```
aggregate variant=control runs=8 tokens=65536 seconds=4.345680 tokens_per_second=15081.1234
aggregate variant=candidate runs=8 tokens=65536 seconds=5.098123 tokens_per_second=12850.6789
candidate_delta_percent=-14.7800 exact_runs=16 exact_floats=2097152 vocab=131072
```

A **negative** `candidate_delta_percent` means TensorOps (control) wins.

### Acceptance Criteria

| Metric | Threshold | Source |
|--------|-----------|--------|
| Combined prefill improvement (8K) | ≥15% | R16 SHOULD target |
| Combined prefill improvement (all sizes) | Repeatable benefit across ≥2 context sizes | R13 |
| Bit-identical correctness | All runs pass `memcmp` | R12 |
| Harness integrity | No ABBA/BAAB anomalies, no thermal variance >3% | R13 |

### Interpretation

| Result (`candidate_delta_percent`) | Meaning | Action |
|------------------------------------|---------|--------|
| ≤ -15% | Spec target met | Record as primary success metric |
| -10% to -15% | Strong improvement, below target | Accept; note in ADR that target was aggressive |
| -5% to -10% | Moderate improvement | Accept; document what limits the gain |
| > -5% | Below expectations | Investigate — may indicate regression or disabled paths |
| Positive (candidate faster) | TensorOps slower than legacy | **Critical issue** — investigate immediately |

## 5. Task 13.3 — Final Balanced Decode A/B

### Purpose

Confirm that the TensorOps-enabled production binary introduces **no decode
regression** and that full-vocabulary token-selection identity is preserved.
This validates R10 (single-token decode) and the R16 mandatory decode gate
(no >1% regression).

### Commands

```bash
# Primary decode A/B with token selection (1024 tokens, extensive)
./speed-bench/metal_decode_schedule_bench \
  -m ds4flash.gguf \
  --include-selection \
  --tokens 1024 \
  | tee speed-bench/local-runs/13.3-decode-ab-1024-$(date +%Y%m%d-%H%M%S).txt

# Shorter run for quick validation
./speed-bench/metal_decode_schedule_bench \
  -m ds4flash.gguf \
  --include-selection \
  --tokens 256 \
  | tee speed-bench/local-runs/13.3-decode-ab-256-$(date +%Y%m%d-%H%M%S).txt
```

### What `--include-selection` Verifies

The `--include-selection` flag causes the decode harness to:
1. Generate tokens using the full sampling pipeline
2. Compare the **selected token ID** between control and candidate at every step
3. Verify full-vocabulary logit bit-identity (same as prefill harness)
4. Report token-selection identity as a binary pass/fail

This is the R10 validation: batch-1 decode must remain on the existing path, and
TensorOps must not alter token selection.

### Harness Methodology

Built into `metal_decode_schedule_bench`:

| Property | Implementation |
|----------|---------------|
| Same binary | Single Metal engine, schedule variant toggle |
| Fresh decode state | Clean KV cache per measured sequence |
| Alternating order | Control/candidate interleaved |
| Bit-identical logits | Full vocabulary comparison every token |
| Token selection identity | Same argmax/sampling result at every step |
| Timing | Per-token and aggregate decode t/s |

### Acceptance Criteria

| Metric | Threshold | Source |
|--------|-----------|--------|
| Decode regression | No >1% statistically significant slowdown | R16 |
| Token selection identity | 100% match across all generated tokens | R10 |
| Bit-identical logits | Full vocabulary match at every step | R12 |
| Stability | Consistent across 1024 tokens (no drift or late failures) | R10, R12 |

### Expected Output

```
decode_bench variant=tensorops_default tokens=1024 seconds=65.432 tokens_per_second=15.65 selection_match=1024/1024
decode_bench variant=legacy_schedule tokens=1024 seconds=65.789 tokens_per_second=15.56 selection_match=1024/1024
delta_percent=+0.58 selection_identity=pass logit_identity=pass
```

### Interpretation

| Result | Action |
|--------|--------|
| delta ≤ +1%, selection pass, logit pass | ✓ Accept. No decode regression. |
| delta +1% to +3%, selection pass | ⚠ Marginal. Investigate source (thermal? pipeline flush?) |
| delta > +3% | **Block** — Decode regression exceeds gate. Do not ship. |
| Selection mismatch at any token | **Block** — Token selection identity violated (R10). |
| Logit mismatch | **Block** — Bit-identity contract broken (R12). |


### What to Capture

For every GPU kernel dispatch during 8K prefill:

1. **Per-kernel GPU time** — wall-clock GPU occupancy per dispatch
2. **Kernel name** — confirms which kernel variant was dispatched
3. **TensorOps activity** — if trace exposes Neural Accelerator counters, confirm
   TensorOps dispatches hit the matrix units
4. **Dispatch gaps** — idle time between kernels
5. **Memory bandwidth utilization** — per-kernel read/write GB/s

## 10. Failure Modes and Recovery

| Failure | Cause | Recovery |
|---------|-------|----------|
| Logit mismatch in 13.2 or 13.3 | Correctness bug introduced after task 12 | Revert to last known-good; re-run task 12.7 tests |

| Trace shows legacy kernels | Runtime dispatch choosing fallback | Check capability detection; verify no stale env vars set |
| Pipeline creation failure | SDK/hardware mismatch | Fall back to staged TensorOps; document capability gap |

## 11. Requirement Traceability

### R10 (Single-token decode)
> WHEN the batch dimension is one and profiling shows the operation is memory-bandwidth-bound  
> THE SYSTEM SHALL retain the existing specialized matvec path.

**Validated by:** Task 13.3 token selection identity (100% match proves decode path unchanged).

### R13 (Benchmark methodology)
> THE SYSTEM SHALL use the same engine, warmed sessions, alternating run order, and

**Validated by:** Tasks 13.1, 13.2, 13.3 all use the established A/B harnesses with

> THE SYSTEM SHALL show repeatable benefit across more than one prompt/batch shape.

**Validated by:** Task 13.2 runs at 512, 2K, 8K, and 32K token contexts.

### R14 (Profiling)
> THE SYSTEM SHALL capture a Metal System Trace / GPU profile.

**Validated by:** Task 13.4 captures a full 8K prefill trace.

> THE SYSTEM SHALL gather the best available evidence that TensorOps executes through
> the intended hardware path.

**Validated by:** Task 13.4 kernel names + Neural Accelerator counters (if exposed).

### R16 (Performance acceptance)
> THE SYSTEM SHALL have no statistically significant regression greater than 1% in decode.

**Validated by:** Task 13.3.

> THE PROJECT SHOULD TARGET at least a 15% end-to-end M5 prefill improvement.

**Validated by:** Tasks 13.1 and 13.2.

> A production TensorOps path that improves a microbenchmark but regresses total prefill,
> TTFT, memory pressure, or load time SHALL NOT become default.

**Validated by:** Task 13.1 CSV includes TTFT, memory, and load time columns.
