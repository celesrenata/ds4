# Task 9.1 — Q2_K Format Documentation

_Requirements: R7_

Source: `metal/moe.metal`, `cuda/mmq/ggml-common.h`, `cuda/mmq/vecdotq.cuh`

---

## 1. Overview

Q2_K is a 2-bit "super-block" quantization format from the GGML K-quant family.
Each super-block encodes **256 elements** (`QK_K = 256`) at an effective rate of
**2.625 bits per weight**.

The weight reconstruction formula is:

```
x[i] = d * scale_g * q[i] - dmin * min_g
```

where `d` and `dmin` are per-block half-precision values, `scale_g` and `min_g`
are 4-bit per-group quantities, and `q[i]` is a 2-bit unsigned integer.

---

## 2. Block Structure (`block_q2_K`)

### 2.1 Metal struct (from `metal/moe.metal`)

```metal
struct block_q2_K {
    uchar scales[QK_K/16];   // 16 bytes — 4-bit scale + 4-bit min per group
    uchar qs[QK_K/4];        // 64 bytes — 2-bit weights packed 4 per byte
    half d;                   // 2 bytes  — super-block scale (for quantized scales)
    half dmin;                // 2 bytes  — super-block scale (for quantized mins)
};
// Total: 16 + 64 + 2 + 2 = 84 bytes per 256-element block
```

### 2.2 CUDA struct (from `cuda/mmq/ggml-common.h`)

```c
typedef struct {
    uint8_t scales[QK_K/16]; // 16 bytes
    uint8_t qs[QK_K/4];      // 64 bytes
    union {
        struct {
            ggml_half d;     // 2 bytes
            ggml_half dmin;  // 2 bytes
        };
        ggml_half2 dm;       // packed pair for CUDA half2 loads
    };
} block_q2_K;
static_assert(sizeof(block_q2_K) == 84, "wrong q2_K block size/padding");
```

### 2.3 Memory layout (byte-level)

```
Offset  Size   Field         Description
------  -----  -----------   -----------------------------------------------
0       16     scales[16]    4-bit scale + 4-bit min for each of 16 groups
16      64     qs[64]        2-bit quantized weights, 4 per byte (256 total)
80      2      d             f16 super-block scale for quantized scales
82      2      dmin          f16 super-block scale for quantized mins
------
Total: 84 bytes per block of 256 elements
```

**Note:** The Metal struct places `d` and `dmin` AFTER `qs`; CUDA places them in
a union at the same logical offset. Both produce the same 84-byte layout with
`scales` at offset 0.

---

## 3. Sub-Block / Group Structure

Each 256-element super-block is divided into **16 groups of 16 elements** each.

```
Block (256 elements)
├── Group 0:  elements [0..15]     — scale/min from scales[0]
├── Group 1:  elements [16..31]    — scale/min from scales[1]
├── ...
└── Group 15: elements [240..255]  — scale/min from scales[15]
```

Each group has:
- A 4-bit quantized scale: `scales[g] & 0x0F`
- A 4-bit quantized min:   `scales[g] >> 4`

The effective per-group scale and min are:
```
effective_scale[g] = d   * (scales[g] & 0x0F)
effective_min[g]   = dmin * (scales[g] >> 4)
```

---

## 4. Scale / Min Encoding

| Level | Precision | Count | Storage |
|-------|-----------|-------|---------|
| Super-block scales (`d`, `dmin`) | float16 (half) | 2 per block | 4 bytes |
| Group scales | unsigned 4-bit | 16 per block | packed in `scales[16]` (low nibble) |
| Group mins   | unsigned 4-bit | 16 per block | packed in `scales[16]` (high nibble) |

The `scales[]` byte for group `g`:
```
scales[g] = (min_g << 4) | scale_g
```

- `scale_g` ∈ [0, 15]
- `min_g` ∈ [0, 15]

This gives 4-bit dynamic range for both the multiplicative scale and the additive
offset within each 16-element group.

---

## 5. 2-Bit Weight Packing (`qs[]`)

Each byte in `qs[]` contains **4 two-bit weights** packed from LSB to MSB:

```
Byte qs[j]:
  bits [1:0] → q for element 4*j + 0
  bits [3:2] → q for element 4*j + 1
  bits [5:4] → q for element 4*j + 2
  bits [7:6] → q for element 4*j + 3
```

Values are unsigned: `q ∈ {0, 1, 2, 3}`.

### 5.1 Physical arrangement within the 256-element block

The `qs[64]` array is laid out so that the first 64 bytes cover all 256 elements
in sequential order: byte `qs[j]` encodes elements `4*j` through `4*j + 3`.

However, the **Metal kernel accesses** use interleaved addressing for SIMD
efficiency. The kernels read `qs` as `uint16_t` (2-byte pairs) to extract 8
elements per load, then apply bit-shift masks to isolate the 2-bit quants for
different groups simultaneously.

### 5.2 Bit extraction masks (from Metal kernel)

The Metal matvec kernel reads `qs` as `uint16_t` and uses these masks:

| Group within kernel tile | Mask (low byte) | Mask (high byte) | Shift-equivalent |
|--------------------------|-----------------|------------------|------------------|
| Sub-group 0 (shift 0)   | `0x0003`        | `0x0300`         | `>> 0, & 3`      |
| Sub-group 1 (shift 2)   | `0x000c`        | `0x0c00`         | `>> 2, & 3`      |
| Sub-group 2 (shift 4)   | `0x0030`        | `0x3000`         | `>> 4, & 3`      |
| Sub-group 3 (shift 6)   | `0x00c0`        | `0xc000`         | `>> 6, & 3`      |

This layout means the kernel processes 4 groups simultaneously from the same
physical `qs` bytes by using different shift/mask operations, accumulating into
separate accumulators that are later scaled independently.

## 6. Dequantization Arithmetic

### 6.1 Scalar dequant (element-level formula)

For element `i` within the block, belonging to group `g = i / 16`:

```
q = (qs[i/4] >> (2 * (i % 4))) & 0x03       // extract 2-bit weight
scale_g = scales[g] & 0x0F                    // 4-bit group scale
min_g   = scales[g] >> 4                      // 4-bit group min

x[i] = (float)d * (float)scale_g * (float)q  -  (float)dmin * (float)min_g
```

### 6.2 Metal `dequantize_q2_K` (simdgroup matmul path)

Used by the template-based batched matmul (`kernel_mul_mm_id`) and the
TensorOps/MPP path (`kernel_mul_mm_id_mpp`). Produces a 4×4 tile of 16 values:

```metal
template <typename type4x4>
void dequantize_q2_K(device const block_q2_K *xb, short il, thread type4x4 & reg) {
    const float d   = xb->d;
    const float min = xb->dmin;
    device const uint8_t *q = (device const uint8_t *)xb->qs;
    uint8_t sc = xb->scales[il];

    q = q + 32*(il/8) + 16*(il&1);       // navigate to correct 16-element span
    il = (il/2)%4;                         // which 2-bit shift position

    half  coef = il>1 ? (il>2 ? 1/64.h : 1/16.h) : (il>0 ? 1/4.h : 1.h);
    uchar mask = il>1 ? (il>2 ? 192    : 48)     : (il>0 ? 12    : 3);

    dl = d * (sc & 0xF) * coef;           // pre-scaled: d * group_scale * (1/2^shift)
    ml = min * (sc >> 4);                  // min contribution

    for (int i = 0; i < 16; ++i) {
        reg[i/4][i%4] = dl * (q[i] & mask) - ml;
    }
}
```

Key insight: `coef` absorbs the bit-shift normalization. When `mask = 0x0C` (bits
[3:2]) the raw masked value is `q[i] & 0x0C` = {0, 4, 8, 12}, so `coef = 1/4`
normalizes it back to {0, 1, 2, 3}. This avoids a per-element shift instruction.

### 6.3 Metal `ds4_glm_q2_K_value` (scalar element-at-index accessor)

```metal
static inline float ds4_glm_q2_K_value(device const block_q2_K *blocks, uint k) {
    const uint block = k / QK_K;
    const uint idx   = k - block * QK_K;
    const uint group = idx / 16u;
    const uint l     = idx - group * 16u;
    const uint q_base = 32u * (group / 8u) + 16u * (group & 1u);
    const uint shift  = ((group / 2u) & 3u) * 2u;
    const uint q = ((uint)xb->qs[q_base + l] >> shift) & 0x03u;
    const uint sc = (uint)xb->scales[group];
    return (float)xb->d * (float)(sc & 0x0fu) * (float)q -
           (float)xb->dmin * (float)(sc >> 4u);
}
```

### 6.4 Optimized fused dot-product form (Metal matvec kernel)

The decode-phase matvec kernel (`kernel_mul_mv_id_q2_K_sum6_f32`) avoids explicit
per-element dequant. Instead it computes:

```
dot(weights, activations) = d * Σ_g [scale_g * Σ_i(q_i * y_i)] - dmin * Σ_g [min_g * Σ_i(y_i)]
```

This is mathematically equivalent to dequant-then-dot but saves memory traffic
by working directly on packed weights:

```metal
// For each group pair processed simultaneously:
dall * ((acc1[0] + 1/256 * acc2[0]) * (sc[0] & 0xF) * 1/1  +
        (acc1[1] + 1/256 * acc2[1]) * (sc[2] & 0xF) * 1/4  +
        (acc1[2] + 1/256 * acc2[2]) * (sc[4] & 0xF) * 1/16 +
        (acc1[3] + 1/256 * acc2[3]) * (sc[6] & 0xF) * 1/64)
- dmin * 1/16 * (sumy[0] * (sc[0] & 0xF0) + sumy[1] * (sc[2] & 0xF0) +
                 sumy[2] * (sc[4] & 0xF0) + sumy[3] * (sc[6] & 0xF0))
```

The `1/256` factor on `acc2` compensates for the uint16 high-byte masks
(`0x0300`, `0x0c00`, etc.) being 256× larger than the low-byte masks. The
`1/{1,4,16,64}` factors correspond to the 2-bit shift positions (0, 2, 4, 6 bits).

## 7. Row Stride and Alignment

### 7.1 Row stride

A row of dimension `D` elements consists of `D / QK_K` = `D / 256` blocks.

```
row_bytes = (D / 256) * 84
```

For typical DS4 DeepSeek-V4 MoE dimensions:
- `D = 2048` → `8 blocks` → `672 bytes` per row
- `D = 7168` → `28 blocks` → `2352 bytes` per row

The Metal kernel references `args.nb01` (row stride in bytes) and
`args.gate_row_bytes` / `args.up_row_bytes` for expert-specific strides.

### 7.2 Alignment

- No explicit alignment beyond natural byte alignment is required by the struct.
- Block size is 84 bytes (not power-of-2), which means rows are NOT naturally
  aligned to 128-byte or 256-byte cache lines.
- The Metal kernel handles this via standard device pointer arithmetic without
  alignment assumptions.
- For TensorOps/MPP: the staged dequant writes to threadgroup memory in 8×8
  aligned tiles (`sa + NK*(8*sy + ly) + 8*sx + lx`), so alignment constraints
  apply to the threadgroup staging buffer, not the source data.

## 8. TensorOps / MPP Staging Pattern

In the `kernel_mul_mm_id_mpp` template, Q2_K is handled via the generic
dequantize-to-threadgroup path:

1. Each thread calls `dequantize_q2_K(x, il, temp_a)` → 16 half values in a 4×4 register
2. The 16 values are scattered into threadgroup memory `sa[]` in an 8×8 tile layout
3. A cooperative `matmul2d` reads from the staged threadgroup tiles

Tile dimensions for the MPP kernel:
- `NR0 = 64` (output rows per threadgroup)
- `NR1 = 32` (tokens per threadgroup)
- `NK = 32` (K-reduction per iteration)
- `NL0 = NK/16 = 2` (dequant calls per thread per K-step for LHS)

The `il` parameter advances through `[0, QK_NL)` = `[0, 16)` across iterations,
covering all 256 elements of a block across 16 dequant calls of 16 elements each.

## 9. DS4 vs Standard GGML Differences

| Aspect | DS4 | Standard GGML |
|--------|-----|---------------|
| Struct field order (Metal) | `scales`, `qs`, `d`, `dmin` | Same (GGML convention) |
| Block size | 84 bytes / 256 elements | Same |
| Effective bpw | 2.625 | Same |
| Scale encoding | 4-bit scale + 4-bit min per 16 elements | Same |
| Dequant formula | `d * scale * q - dmin * min` | Same |
| TensorOps path | Yes — staged dequant → tgmem → `matmul2d` | Not present in upstream |
| Fused kernel variants | Pair+SwiGLU, sum6, addr, masked, GLM | Not present in upstream |

The Q2_K **format** is identical to standard GGML. DS4's differentiation is
entirely in kernel fusion (SwiGLU, multi-expert summation, streaming cache)
and the TensorOps/MPP acceleration path, not in the data layout itself.

## 10. Implications for Native Metal int2 Compatibility (§9 Policy)

A naive Metal `int2` (or `uint2`) tensor would represent raw 2-bit integers with
no metadata. Q2_K requires:

1. **Per-block metadata** (4 bytes: `d` + `dmin`) — not representable in a raw int2 tensor
2. **Per-group metadata** (16 bytes: `scales[]`) — requires auxiliary tensor or custom decode
3. **Asymmetric quantization** (`q * scale - min`) — not a simple int2 × scale pattern
4. **Non-power-of-2 block size** (84 bytes) — complicates tensor stride calculations

**Conclusion:** Native Metal `int2` tensors **cannot** represent Q2_K directly.
Any TensorOps acceleration must use the cooperative custom dequant path
(stage → threadgroup → `matmul2d`), which is exactly what `kernel_mul_mm_id_mpp`
already implements.

The existing MPP kernel provides the baseline for task 9.4 benchmarking.
