_Requirements: R11_

Source: `ds4.c`, `ds4_metal.m`, `ds4_tp.h`, `ds4_cli.c`, `gguf-tools/deepseek4-quantize.c`

## 1. DSpark / Speculative Verify Depth

DS4 has two speculative decoding paths that produce verification batches:

### 1.1 MTP (Multi-Token Prediction)

- Configured via `--mtp-draft N` (field `mtp_draft_tokens`).
- **Default: 1** (no speculation — single-token decode).
- Test harness uses `mtp_draft_tokens = 4`.
- The verify forward pass calls `metal_graph_verify_suffix_tops` with `n_tokens = draft_depth`.
- Typical N for MTP verification: **2–4 tokens**.

### 1.2 DSpark (Speculative Model)

- Configured via `--dspark` with a separate support GGUF.
- **Block size default: 5** (`DSPARK_DEFAULT_BLOCK_SIZE = 5`).
- **Maximum block size: 16** (`DS4_DSPARK_MAX_BLOCK_SIZE = 16`).
- The verification forward pass runs with `n_tokens = draft_n` where `draft_n` is the block size.
- Typical N for DSpark verification: **5 tokens** (the default block).
- Upper bound enforced by TP: `DS4_TP_BATCH_MAX_ROWS = 8` (comment: "speculative blocks are <=5").

### 1.3 Split-KV Speculative Verify

- Fixed N=2 batch: calls `metal_graph_verify_suffix_tops(..., 2, ...)`.
- Used in the cuda split-KV speculative path.

### 1.4 Summary of Verification Batch N Values

| Path | Typical N | Max N | Notes |
|------|-----------|-------|-------|
| MTP verify | 2–4 | mtp_draft_tokens | Per-config |
| DSpark verify | 5 | 16 | Default block_size=5 |
| Split-KV spec | 2 | 2 | Fixed |
| TP batch gate | 1–8 | DS4_TP_BATCH_MAX_ROWS=8 | TP verify exchange |

**The verification forward pass runs the entire model (all layers) at the draft block width.**
It uses the same batch layer kernels as prefill, but at these tiny N values.

## 2. Session Batching

DS4 supports multi-session decode batching where multiple concurrent generation sessions are
batched into a single GPU command submission.

### 2.1 Metal Session Batch

- Controlled by `DS4_METAL_SESSION_BATCH_SHARED` and `DS4_METAL_SESSION_BATCH_QKV` env vars.
- `ds4_sessions_eval_batch(items, count, ...)` dispatches N decode tokens as one batch.
- Test harness: `MAX_SESSION_COUNT = 16`, `DECODE_STEPS = 6`, default `session_count = 2`.
- Production use in `ds4-server` batches multiple concurrent requests.

### 2.2 CUDA Session Batch

- `DEFAULT_SESSION_COUNT = 8`, `MAX_SESSION_COUNT = 16`.
- `DECODE_STEPS = 24`.
- Alternates batch sizes: 8, 4, and 2 in tests.

### 2.3 Mixed Batch (Prefill + Decode)

- `ds4_sessions_eval_batch_with_prefill` combines one prefill session with multiple decode sessions.
- Produces a batch where one session contributes a suffix (8 tokens in test: `MIXED_SUFFIX_TOKENS = 8`)
  and the remaining sessions each contribute 1 decode token.
- Total N = prefill_suffix_tokens + decode_session_count.

### 2.4 Session Batch N Distribution

| Configuration | Batch N | Notes |
|---------------|---------|-------|
| 2 sessions decode | 2 | Minimum useful batch |
| 4 sessions decode | 4 | Common server config |
| 8 sessions decode | 8 | CUDA default test |
| 16 sessions decode | 16 | Maximum tested |
| Mixed: 8 suffix + 2 decode | 10 | Prefill overlapping decode |
| Mixed: 8 suffix + 8 decode | 16 | Higher concurrency |

**Session batching produces N = session_count for pure-decode batches.** The practical range
is **2–16** tokens per batch submission during generation.

## 3. Prompt Tail Batches

After the main prefill processes large chunks, a tail remains when the prompt length is not
a multiple of the prefill chunk size.

### 3.1 Chunked Prefill Behavior

- Default prefill_cap (Metal): **4096 tokens** (long prompts), or **prompt length** for short prompts.
- PRO variant: 8192 tokens for long prompts.
- CUDA TP: 2048 tokens.
- Configurable via `--prefill-chunk N` or `DS4_METAL_PREFILL_CHUNK`.
- The tail is: `prompt_length % chunk_cap` if prompt > chunk_cap, otherwise the entire prompt.

### 3.2 Q8 Stripe Tail Trimming

For GLM Q8 prefill paths, there's explicit tail-trimming logic:

```c
if (chunk >= 256u && chunk == n_tokens - done) {
    const uint32_t tail = chunk & 31u;
    if (tail != 0u && tail <= 16u) chunk -= tail;
}
```

This means the last chunk is trimmed to 32-alignment if the tail is ≤16 tokens,
leaving a second "micro-tail" of 1–16 tokens to be handled by a small-batch kernel.

### 3.3 Typical Tail N Values

| Prompt Length | Chunk Cap | Tail N | Notes |
|---------------|-----------|--------|-------|
| 500 | 500 (= prompt) | 500 | No tail; single chunk |
| 2000 | 2000 | 2000 | Single chunk |
| 5000 | 4096 | 904 | Residual chunk |
| 8191 | 4096 | 4095 | Almost-full residual |
| 8192 | 4096 | 4096 | Perfect split |
| 10000 | 4096 | 1808 | Typical residual |
| Q8 tail after trimming | — | 1–16 | Micro-tail |

**Prompt tails in the "gap zone" are 1–4095 tokens**, but the operationally interesting
case for TensorOps crossover is the micro-tail of **1–31 tokens** that falls below the
`n_tokens >= 32` matmul dispatch threshold.

## 4. Current Dispatch Thresholds

### 4.1 MoE Expert Projection

| N Range | Dispatch Path | Kernel Family |
|---------|---------------|---------------|
| N = 1 | Standard decode matvec | `kernel_mul_mv_id_*` |
| N ≤ 5 | Tiny pair (matvec iterated) | `mul_mv_id_*_pair_swiglu` |
| N = 6–31 | Standard matvec (no pair opt) | `kernel_mul_mv_id_*` |
| N ≥ 32 | Expert-major grouped matmul | `kernel_mul_mm_id_*` |

The boundary is explicit in `ds4_metal.m`:
```c
const bool use_mm_id = ... && n_tokens >= 32u && ...;
const bool use_tiny_pair_mv = ... && n_tokens <= 5u && ...;
```

**Gap zone: N = 6–31** — neither tiny-pair-optimized nor large-batch matmul.
These fall through to per-token matvec dispatch, which is suboptimal for this range.

### 4.2 Dense Attention Output (MPP/TensorOps)

| Condition | Path |
|-----------|------|
| N ≥ 32 AND N % 64 == 0 | TensorOps MPP (strict) |
| N ≥ 256 AND padding allowed | TensorOps MPP with padding to 64-alignment |
| N < 32 or non-aligned | Legacy kernel |

Tile size: `DS4_METAL_ATTN_OUT_MPP_TILE_N = 64`.

### 4.3 Indexer TensorOps (NAX)

| Condition | Path |
|-----------|------|
| N ≥ 16 AND mpp_available AND head_dim == 128 | TensorOps NAX |
| N < 16 | Legacy tiled kernel (shape too small) |

### 4.4 MoE Specialized Paths

| Condition | Path | Notes |
|-----------|------|-------|
| N ≥ 2048 (pre-M5) | MXFP4 compact tail cull | Pre-M5 optimization |
| N ≥ 2048 (pre-M5) | MXFP4 map scatter | Work compaction |
| N ≥ 2048 (pre-M5) | MXFP4 down half-LUT | Scale optimization |

## 5. Crossover Implications for TensorOps

### 5.1 The Interesting Batch Ranges

From the observed generation shapes:

| Batch Range | Source | Current Path | TensorOps Opportunity |
|-------------|--------|--------------|----------------------|
| N = 1 | Decode | Fused matvec | None (bandwidth-bound) |
| N = 2–5 | DSpark verify / MTP | Tiny pair matvec | Marginal — too small for tile efficiency |
| N = 6–16 | Session batch / tails | Per-token matvec | **Potential crossover zone** |
| N = 17–31 | Session batch / tails | Per-token matvec | **Strong TensorOps candidate** |
| N ≥ 32 | Prefill chunks | Expert-major matmul | Already using matmul; TensorOps lift target |

### 5.2 Key Findings

1. **DSpark verification (N=5) sits at the boundary.** The `use_tiny_pair_mv` path handles
   this specifically with a fused gate/up pair dispatch. TensorOps at N=5 is unlikely to
   beat the hand-tuned pair kernel, but this should be benchmarked.

2. **Session batching (N=2–16) is the most natural TensorOps small-batch target.** At N=8+
   the arithmetic intensity begins to justify a matmul dispatch over iterated matvec.

3. **The N=6–31 gap zone currently falls through to unoptimized matvec.** This is where a
   TensorOps crossover measurement (task 10.2) would find the biggest potential uplift.

4. **Prompt tail micro-batches (1–16 tokens after Q8 alignment trimming)** hit the same
   gap zone. These are less frequent but occur at the end of every chunked prefill.

5. **The current threshold N≥32 for `use_mm_id`** is a conservative boundary inherited
   from the simdgroup-matrix kernel's tile efficiency. TensorOps `matmul2d` may have
   a lower crossover point due to the Neural Accelerator's instruction-level parallelism.

### 5.3 Recommended Benchmark Matrix for Task 10.2

| N | Source scenario | Dense quants | MoE quants |
|---|-----------------|--------------|------------|
| 2 | MTP verify | Q8_0, Q4_K | MXFP4, Q4_K |
| 4 | MTP/DSpark verify | Q8_0, Q4_K | MXFP4, Q4_K |
| 5 | DSpark default | Q8_0, Q4_K | MXFP4, Q4_K |
| 8 | Session batch | Q8_0, Q4_K | MXFP4, Q4_K |
| 12 | Session batch | Q8_0, Q4_K | MXFP4, Q4_K |
| 16 | Max session batch / indexer threshold | Q8_0, Q4_K | MXFP4, Q4_K |
| 24 | Large session batch | Q8_0, Q4_K | MXFP4, Q4_K |
| 32 | Current mm_id threshold | Q8_0, Q4_K | MXFP4, Q4_K |
| 48 | Above threshold reference | Q8_0, Q4_K | MXFP4, Q4_K |

Compare: existing kernel (tiny_pair / matvec / mm_id) vs TensorOps candidate at each N.

## 6. Summary

| Shape Category | N Range | Frequency | Current Handling | TensorOps Crossover Interest |
|----------------|---------|-----------|------------------|------------------------------|
| Batch-1 decode | 1 | Every generated token | Fused matvec | None — bandwidth-bound |
| DSpark verify | 2–5 (default 5) | Every speculative block | Tiny pair matvec | Low — specialized path exists |
| Session batch decode | 2–16 | Server batched generation | Matvec (gap zone) | **Medium–High** for N≥8 |
| Prompt micro-tail | 1–31 | End of chunked prefill | Matvec fallback | Medium for N≥16 |
| Prefill chunk | 32–8192 | Every prefill iteration | mm_id matmul | Already addressed by MoE TensorOps lift |

The primary targets for task 10.2 benchmarking are:
- **Session batch at N=8–16**: most likely TensorOps crossover zone
- **N=16–31 gap**: currently has no specialized path between matvec and grouped matmul
- **DSpark verify at N=5**: validate that the tiny_pair path remains fastest
