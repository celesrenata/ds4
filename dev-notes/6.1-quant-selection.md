# 6.1 — First Prototype Quant Selection: Q8_0

## Decision

**Q8_0** is selected as the first format for the custom-dequant-to-cooperative-tensor prototype.

## Rationale

The goal of task 6 is to validate the *mechanism* — proving that custom dequantization
can feed a cooperative tensor input to `matmul2d` without a threadgroup-memory round trip.
The dequant format itself should be the simplest possible variable so that any issues
encountered are attributable to the cooperative-input plumbing, not to decode complexity.

Q8_0 satisfies this because:

1. **Simplest block structure in DS4's quant inventory.** No nibble packing, no sub-byte
   extraction, no codebooks, no grouped scales/mins, no lookup tables.

2. **Already proven in the TensorOps dense path.** `kernel_mul_mm_mpp_direct_rhs` in
   `metal/dense.metal` already has a production Q8_0 variant using double-buffered staging.
   The decode arithmetic is known correct and the shapes are exercised.

3. **Isolates the mechanism.** If the cooperative-input path works for Q8_0, the pattern
   generalizes to more complex formats (Q4_0, Q4_K, MXFP4). If it fails, we know the
   failure is in the cooperative-input mechanism itself, not in a complex decoder.

4. **Minimal register pressure from dequant.** The trivial multiply means we test
   cooperative-tensor register/occupancy constraints without the dequant itself competing
   for registers.

## Q8_0 Block Structure (reference)

```
struct block_q8_0 {
    half   d;           // 2 bytes — f16 scale factor
    int8_t qs[32];      // 32 bytes — quantized values
};
// Total: 34 bytes per 32 elements
```

### Dequant arithmetic

```metal
float value = (float)d * (float)qs[i];
```

That's it. One f16→f32 promotion of the scale (shared across 32 values), one int8→f32
cast per element, one multiply. No bit shifting, no nibble masking, no codebook lookup,
no min/max reconstruction.

### Memory layout

- Blocks are contiguous along K (the reduction dimension).
- Each block covers 32 consecutive K elements.
- Row stride = `(K / 32) * 34` bytes.
- Alignment: 2-byte aligned (from the f16 scale).

## What comes next

Once the cooperative-input mechanism is validated with Q8_0 (tasks 6.2–6.5), the pattern
extends to production-priority formats:

1. **MXFP4** — the ultimate MoE target, either through native-MX tensors (task 5) or
   through cooperative custom dequant if native proves layout-incompatible.
2. **Q4_0 / Q4_K** — nibble unpacking adds moderate complexity but the mechanism is the same.
3. **Q2_K** — grouped scales/mins add significant decode work; evaluate whether the
   cooperative path still wins over threadgroup staging at that complexity level.
4. **IQ2_XXS** — codebook decoding; explicitly deferred per spec. Only attempted after
   simpler formats prove the mechanism and if profiling shows it matters.

## Explicitly avoided

- **IQ2_XXS as first prototype** — codebook/lookup decoding would conflate mechanism
  validation with decoder correctness and register-pressure issues.
- **MXFP4 as first prototype** — nibble packing + E8M0 scale semantics + potential layout
  incompatibility with cooperative-tensor planes would obscure mechanism-level bugs.
- **Q2_K as first prototype** — complex scale/min encoding with sub-byte packing adds
  unnecessary variables to the initial experiment.

## Requirement traceability

- **R7** (Quantization compatibility research): This selection begins the research by
  choosing the simplest format to validate custom-dequant-to-cooperative-tensor feasibility.
