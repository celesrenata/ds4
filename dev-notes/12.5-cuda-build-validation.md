### Link: ENVIRONMENT ISSUE (not a code defect)

Link failed due to Nix packaging mismatch: CUDA 12 headers (only version in
Nix store) generate calls to `cudaGetDeviceProperties_v2`, but the CUDA 13.2
runtime exports `cudaGetDeviceProperties` (no `_v2` suffix). This is a
header/runtime version skew in the Nix environment, not a DS4 code issue.

On gremlin-1 (10.1.1.12) with consistent CUDA toolchain, this would link
cleanly. The `make cuda CUDA_ARCH=sm_120` target is the correct invocation.

### nvcc Nix-specific notes

- Requires `--allow-unsupported-compiler` (GCC 15 > CUDA 13.2's max of 14)
- Requires explicit `-I` for CUDA headers (Nix store path not propagated)
- `CUDA_HOME` resolves to `/run/current-system/sw` (non-standard layout)
- Lib path: `/run/current-system/sw/lib` (not `lib64` or `targets/sbsa-linux/lib`)

## Conclusion

**Shared interface changes from the TensorOps lift compile cleanly for CUDA.**

The `ds4_gpu.h` TensorOps additions (tasks 2.1–2.4: capability detection,
diagnostics, counters, rollback control) are properly guarded with
`#ifdef __APPLE__` / `#else` no-op stubs. The `ds4_gpu_mgpu.h` and
`ds4_gpu_args.h` shared types are unchanged and compile as before.

No DS4 code changes are required for CUDA compatibility. Full link validation
should be performed on gremlin-1 where the CUDA toolchain is self-consistent.
