## 12.8 — Exercise SSD Streaming

### Status: PENDING HARDWARE EXECUTION (macOS + Metal + model files required)

### Background

Per the production dispatch policy (dev-notes/12.1):
- SSD streaming mode uses address-table or slot-based access patterns
- TensorOps is **structurally excluded** during streaming via the `use_mm_id` gate:
  - `use_iq2_batch_selected_addr` → blocks `use_mm_id` → addr-based kernels
  - `use_q4_batch_expert_table` → blocks `use_mm_id` → table-based kernels
  - MXFP4 streaming → `ds4_gpu_wrap_model_range()` returns nil → graceful 0 return
  - Decode (N=1) streaming → slot-based matvec (`_slots6_*`)
- Dense TensorOps is unaffected by SSD streaming (contiguous weight buffers always)
- Confirmed structurally in task 7.6 (TP/streaming preservation)

### Test Scenarios

#### Cold Expert Cache (first prompt)

```bash
# Forces SSD streaming mode — first prompt fills expert cache from disk
DS4_SSD_STREAMING=1 ./ds4 -m /path/to/model.gguf -p "The quick brown fox" --n-predict 32
```

Expected behavior:
- Expert weights loaded from SSD on demand
- All MoE projections use addr/slot/table fallback kernels (NOT TensorOps)
- `g_ctr_fallback_streaming` increments on every MoE dispatch
- `g_ctr_moe_gate_up_tensorops` = 0, `g_ctr_moe_down_tensorops` = 0
- Dense TensorOps counters may be non-zero (dense is unaffected)
- No crash, no assertion failure

#### Warm Expert Cache (subsequent prompts)

```bash
# Same session, second prompt — experts now cached in resident memory
DS4_SSD_STREAMING=1 ./ds4 -m /path/to/model.gguf -p "The quick brown fox" --n-predict 32 \
  --interactive  # then type a second prompt
```

Expected behavior:
- Cached experts serve from resident memory
- Same fallback path used (streaming flag persists per-session)
- No TensorOps for MoE even with warm cache (the streaming mode flag
  controls dispatch, not the cache state)
- Decode still uses slot-based matvec

#### Verify: No Full-Model Copy

```bash
# Monitor memory during SSD streaming
DS4_SSD_STREAMING=1 DS4_METAL_DIAGNOSTICS=1 ./ds4 -m /path/to/model.gguf \
  -p "Hello" --n-predict 16
```

Expected behavior:
- TensorOps uses contiguous resident buffers for dense projections only
- MoE experts in streaming mode are NOT replicated into contiguous TensorOps buffers
- Total GPU memory usage should NOT equal full model size
- Diagnostics should show TensorOps active only for dense (non-MoE) operations

#### Diagnostics Counter Verification

With `DS4_METAL_DIAGNOSTICS=1`, after a streaming session:

| Counter | Expected |
|---------|----------|
| `g_ctr_dense_tensorops` | > 0 (dense is unaffected by streaming) |
| `g_ctr_indexer_tensorops` | > 0 (indexer is unaffected) |
| `g_ctr_moe_gate_up_tensorops` | 0 (excluded by streaming) |
| `g_ctr_moe_down_tensorops` | 0 (excluded by streaming) |
| `g_ctr_fallback_streaming` | > 0 (streaming fallback triggered) |

### Pass Criteria

- No crash or assertion failure in either cold or warm scenarios
- MoE TensorOps counters remain zero while streaming is active
- Streaming fallback counter increments appropriately
- Memory usage consistent with partial model (not full-model expanded copy)
- Dense TensorOps continues functioning normally alongside streaming MoE

## 12.9 — Exercise Pre-M5 Apple Silicon

### Status: NOT AVAILABLE (no pre-M5 Apple Silicon hardware)

### Background

Per the production dispatch policy (dev-notes/12.1, §1.3):
- Pre-M5 detection: device name does NOT match "M5", "M6", "A19", "A20"
- Result: `g_metal4_tensor_api_enabled = 0` → `ds4_gpu_mpp_available() = false`
- All TensorOps paths fall through to legacy simdgroup kernels
- No TensorOps is auto-enabled without device-specific evidence (R17)

### Key Invariant Chain

```
ds4_gpu_device_is_pre_m5_apple_silicon() == true
  → g_metal4_tensor_api_enabled = 0
    → ds4_gpu_mpp_available() = false
      → ds4_gpu_routed_mm_mpp_mask() = 0
        → ALL TensorOps dispatch checks fail
          → ALL operations route to legacy kernels
```

This is enforced at init time (`ds4_gpu_detect_capabilities()`) — there is no
runtime path that can enable TensorOps on pre-M5 hardware without the init-time
device name match succeeding.

### Validation Plan (requires M1/M2/M3/M4 hardware)

#### Performance Regression Check

```bash
# On each available pre-M5 device:
./ds4-bench -m /path/to/model.gguf -n 128 -p 512 -r 3
# Compare against pre-TensorOps baseline CSV from task 1.1
```

Expected: No material regression (< 2% decode, < 5% prefill) since the code
changes do not alter any legacy kernel execution path.

#### Behavioral Verification

```bash
DS4_METAL_DIAGNOSTICS=1 ./ds4 -m /path/to/model.gguf -p "Hello" --n-predict 32
```

Expected diagnostics output on pre-M5:
```
Metal TensorOps:
  compiled                  no
  runtime                   no
  M5 neural accelerator     no
  ...
  mpp_mask                  0
```

All TensorOps dispatch counters should remain at 0. All fallback counters
should show `fallback_os` incrementing (capability not available).

#### Correctness Check

```bash
# Run standard ds4_test on pre-M5
make test
```

All existing tests should pass unchanged — the TensorOps code paths are
never entered, so pre-M5 behavior is identical to the pre-change codebase.

### Risk Assessment

**LOW RISK.** The TensorOps changes are gated behind:
1. Compile-time: `DS4_METAL_HAS_TENSOR` (only injected when `g_metal4_tensor_api_enabled`)
2. Runtime: `ds4_gpu_mpp_available()` (returns false on pre-M5)
3. Per-operation: `mpp_mask` (zero on pre-M5)

No new code paths execute on pre-M5 hardware. The only risk is if a shared
code change (outside the TensorOps guards) introduced a regression in legacy
kernel selection or buffer management — which is covered by the existing test
suite running on pre-M5.
