## 2. Cooperative-Input Experiment (`DS4_EXPERIMENT_COOP_INPUT_SINGLE_SG`)

### Location
- `metal/moe.metal` lines ~9128–9353: `kernel_mul_mm_id_q8_0_coop_input_candidate`
- `ds4_metal.m` lines ~30089–30140: Commented documentation block (host dispatch reference)

### Decision: RETAIN

Rationale:
- The kernel is behind a compile guard (`DS4_EXPERIMENT_COOP_INPUT_SINGLE_SG`) that is **never defined** in any build configuration.
- It does not compile in normal builds — zero compilation overhead.
- It does not appear in any dispatch path — zero runtime overhead.
- The 6.3 dev-note explicitly states: "retained as documentation of the approach and could be revived if future Apple hardware/SDK lifts the single-simdgroup restriction."
- The `ds4_metal.m` block is a comment only — no dead code, no stale pipeline registration.

This is not dead code in the traditional sense. It is a guarded reference implementation
for a future platform capability. It costs nothing and has clear documentary value.

## 5. Force-Enable Flags Audit

Searched all source files for `DS4_METAL_FORCE` pattern:

- **In design.md:** `DS4_METAL_FORCE_TENSOROPS_DENSE`, `DS4_METAL_FORCE_TENSOROPS_MOE`,
  `DS4_METAL_FORCE_TENSOROPS_NATIVE_MX` are listed as "optional research-only" env vars.
- **In source code (`ds4_metal.m`, `*.metal`):** Zero matches.

**These force flags were never implemented.** The design doc proposed them but the
actual implementation uses only `DS4_METAL_DISABLE_*` rollback controls, which is
cleaner (auto-enable the fastest proven path; disable only for debugging/regression
hunting).

### Decision: NO STALE FORCE FLAGS TO REMOVE

The design doc's mention of force flags is aspirational documentation, not dead code.
No source references exist.

All comments referencing experiments are either (a) accurate history documenting design
decisions, (b) inside the retained guarded region, or (c) describing the current
