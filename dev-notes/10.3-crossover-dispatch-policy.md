# 10.3 — Measured Crossover Dispatch Policy

_Requirements: R10, R11_

Source: `ds4_metal.m` (MoE dispatch §41095–41145, dense dispatch §24765), `ds4_gpu.h`

---

## 1. Current Dispatch Thresholds (Baseline)

The existing dispatch in `ds4_metal.m` implements a three-zone split:

| N range | MoE expert projection path | Decision variable |
|---------|---------------------------|-------------------|
| N = 1 | Standard decode matvec (`kernel_mul_mv_id_*`) | — |
| N ≤ 5 | Tiny pair fused gate/up (`mul_mv_id_*_pair_swiglu`) | `use_tiny_pair_mv` |
| N = 6–31 | Per-token matvec (no specialization) | fallthrough |
| N ≥ 32 | Expert-major grouped matmul (`kernel_mul_mm_id_*`) | `use_mm_id` |

The boundary is explicit:
```c
const bool use_mm_id = ... && n_tokens >= 32u && ...;
const bool use_tiny_pair_mv = ... && n_tokens <= 5u && ...;
```

---

## 2. Dispatch Policy — Invariants

### 2.1 Batch-1 decode: NEVER TensorOps (R10)

Single-token decode (N=1) is memory-bandwidth-bound. The existing fused matvec path is
hand-tuned for this regime. TensorOps/matmul dispatch adds launch overhead with no
arithmetic intensity to amortize.

**This is a hard invariant, not subject to crossover measurement.**

Per R10: "THE SYSTEM SHALL retain the existing specialized matvec path unless TensorOps
wins a balanced end-to-end benchmark." Given that batch-1 is structurally bandwidth-bound,
TensorOps cannot win. The existing fused decode path remains default unconditionally.

### 2.2 Tiny pair (N ≤ 5): keep existing proven path

The `use_tiny_pair_mv` / `use_tiny_pair_swiglu` kernels are specialized for DSpark
verification (default block size 5) and MTP verification (2–4 tokens). These fuse
gate/up/SwiGLU in a single dispatch reading the activation once.

At N ≤ 5, TensorOps tile efficiency is too low to beat the hand-tuned pair kernels.
This is validated by the design rationale in the source (§41108–41117) and by the
fact that these operate on too few rows to fill even a minimal matmul tile.

**Keep N ≤ 5 on tiny pair by default.**

### 2.3 N ≥ 32: already uses grouped matmul (TensorOps lift target)

The `use_mm_id` path dispatches expert-major grouped matmul which already receives
TensorOps acceleration via tasks 7.2/8.2 (MPP kernel variants for MXFP4/Q4_K/IQ2_XXS).

**No crossover change needed for N ≥ 32 — already the fastest measured path.**

---

## 3. The Gap Zone: N = 6–31

This is where crossover measurement (task 10.2) matters. Currently these tokens fall
through to unoptimized per-token matvec — neither the pair-fused path (too large for
N ≤ 5) nor the grouped matmul path (threshold is N ≥ 32).

### 3.1 Potential crossover scenarios

If benchmark 10.2 finds TensorOps wins at some threshold `T` where 6 ≤ T ≤ 31:

```text
N = 1         → decode matvec (unchanged)
N = 2–5       → tiny pair (unchanged)
N = 6..(T-1)  → per-token matvec (unchanged, TensorOps doesn't yet win)
N = T..31     → TensorOps grouped matmul / MPP dispatch (NEW)
N ≥ 32        → expert-major grouped matmul + TensorOps (unchanged)
```

The most likely crossover zone is **N = 8–16** based on:
- Session batch decode typically produces N = 2–16
- Prompt micro-tails after Q8 trimming produce N = 1–16
- At N = 8+ arithmetic intensity begins to justify matmul over iterated matvec
- TensorOps `matmul2d` may have lower crossover than simdgroup-matrix due to
  Neural Accelerator instruction-level parallelism

### 3.2 If crossover is never found

If benchmarking shows TensorOps does not repeatably win at any N < 32:
- The current N ≥ 32 threshold stays
- The gap zone remains on per-token matvec
- This is a valid outcome (documented reject per spec rules)

## 4. Crossover Override: `DS4_METAL_TENSOROPS_CROSSOVER_N`

An environment variable is prepared for development/benchmarking use:

```text
DS4_METAL_TENSOROPS_CROSSOVER_N=<integer>
```

**Semantics:**
- When set, overrides the `n_tokens >= 32u` threshold in the `use_mm_id` decision
  to `n_tokens >= <value>` for the MoE grouped matmul path.
- Must be ≥ 6 (values below 6 are clamped to 6 to protect the tiny pair path).
- Must not affect batch-1 decode (N=1 always takes the matvec path regardless).
- Only affects the MoE expert projection dispatch, not the dense attention-output
  MPP path (which has its own tile-alignment requirements).

**Usage during benchmarking:**
```sh
# Test if TensorOps grouped matmul wins at N=8:
DS4_METAL_TENSOROPS_CROSSOVER_N=8 ds4-bench --prefill ...

# Test if N=16 is the crossover:
DS4_METAL_TENSOROPS_CROSSOVER_N=16 ds4-bench --prefill ...
```

**Production policy:**
- Once task 10.2 determines the measured crossover on M5 hardware, the winning
  threshold will be hardcoded as the new default (replacing `32u`).
- The env var remains as a development/rollback escape hatch.
- If no crossover is found below N=32, no code change is needed.

## 5. Implementation Location

The crossover threshold is read in `ds4_metal.m` at the MoE gate/up dispatch site:

```c
/* Task 10.3: Measured crossover dispatch.
 *
 * The default mm_id threshold is N≥32.  DS4_METAL_TENSOROPS_CROSSOVER_N
 * allows overriding this for benchmarking lower crossover points.
 * Once 10.2 benchmarks determine the optimal threshold on M5 hardware,
 * the default will be updated to the measured value.
 *
 * Invariant: batch-1 decode (N=1) NEVER uses this path (R10).
 * Invariant: N≤5 uses the tiny pair path when available.
 * Constraint: minimum override value is 6 (protects tiny pair zone).
 */
static uint32_t ds4_gpu_moe_mm_id_threshold(void) {
    static uint32_t threshold = 0;
    static bool initialized = false;
    if (!initialized) {
        const char *env = getenv("DS4_METAL_TENSOROPS_CROSSOVER_N");
        if (env) {
            int val = atoi(env);
            threshold = val >= 6 ? (uint32_t)val : 6u;
        } else {
            threshold = 32u; /* default: pending 10.2 measurement */
        }
        initialized = true;
    }
    return threshold;
}
```

The `use_mm_id` decision becomes:
```c
const bool use_mm_id =
    !use_q4_batch_expert_table &&
    !use_iq2_batch_selected_addr &&
    n_tokens >= ds4_gpu_moe_mm_id_threshold() &&
    ds4_gpu_mul_mm_id_map0_name(n_expert) != NULL;
```

## 6. Guards and Safety

| Guard | Purpose |
|-------|---------|
| `n_tokens == 1` always takes matvec | R10: batch-1 decode unchanged |
| `use_tiny_pair_mv` checked before `use_mm_id` | N ≤ 5 stays on pair path |
| Threshold clamped to ≥ 6 | Cannot accidentally override pair zone |
| `g_tensorops_global_rollback` dominates | `DS4_METAL_DISABLE_TENSOROPS` still wins |
| `ds4_gpu_mul_mm_id_map0_name(n_expert) != NULL` | Pipeline must exist |
| No effect on dense attention-out MPP | Separate tile-alignment logic |

---

## 7. What Changes When Benchmarks Arrive (Task 10.2)

Once M5 hardware is available and task 10.2 runs the benchmark matrix:

1. **If crossover is found at N=T (e.g., T=8 or T=16):**
   - Change the default from `32u` to `T` in `ds4_gpu_moe_mm_id_threshold()`
   - Add M5 guard: only lower the threshold on M5+ hardware (pre-M5 keeps N≥32)
   - Verify with `metal-decode-schedule-bench --include-selection` that batch-1
     decode is unaffected
   - Re-run `metal-prefill-variant-bench` to confirm the win is repeatable

2. **If no crossover below 32:**
   - Remove the env var override or leave as a dev-only escape hatch
   - Document the negative result in dev-notes
   - Close task 10.3 as "validated: current threshold is optimal"

3. **If crossover differs by quant type:**
   - The threshold function can be extended to accept `gate_type`:
     ```c
     static uint32_t ds4_gpu_moe_mm_id_threshold_for(ds4_metal_tensor_type type);
     ```
   - Per-quant thresholds would be hardcoded after measurement

## 10. Summary

This task establishes the **infrastructure** for measured crossover dispatch:

- ✅ Batch-1 decode is protected (never changed to TensorOps)
- ✅ Tiny pair zone (N ≤ 5) is protected
- ✅ N ≥ 32 continues using grouped matmul + TensorOps
- ✅ A mechanism (`DS4_METAL_TENSOROPS_CROSSOVER_N`) exists to test lower thresholds
- ⏳ The actual threshold value awaits task 10.2 benchmarks on M5 hardware
- ✅ The dispatch policy is documented and the code change is minimal and safe

No code is activated for the gap zone (N = 6–31) until benchmarks prove a win.
Only ranges that win repeatably will be lowered from the current N ≥ 32 default.
