# Task 8.1 — Down-Projection Accumulation Order

_Requirements: R6, R12_
_Commit: 84cc882352757baf628a1776badf7cc54d584e28_

---

## 1. Summary

The MoE down projection produces a per-token output by summing the individual
expert down-projection dot products across all selected experts (typically 6).
DS4 implements this accumulation in two distinct patterns depending on phase and
dispatch path:

| Phase | Path | Accumulation method | Output destination |
|-------|------|--------------------|--------------------|
| Decode (1 token) | Fused `sum6` kernels | Sequential loop over expert slots, inline register sum | `dst` (final output buffer) |
| Decode (1 token) | Non-fused legacy | Per-expert writes to scratch, separate `kernel_dsv4_moe_sum6_f32` | `down_dst` → `outbuf` |
| Prefill (N tokens) | `kernel_mul_mm_id` / `kernel_mul_mm_id_mpp` | Per-expert writes to scratch per (token,slot), separate sum kernel | `down_dst` → `outbuf` |
| Prefill (N tokens) | Fused `sum6` matvec (tiny batch ≤5) | Same as decode fused | `outbuf` |
| GLM grouped | `kernel_glm_q4_K_down_f32` etc. | Sequential loop over slots, threadgroup reduction | `out` (final) |

---

## 2. Decode Fused Path (`direct_down_sum`)

### Activation conditions

```c
const bool direct_down_sum =
    !g_quality_mode &&
    (n_expert == 6 || (n_expert == 8 && g_tp_split_world == 2)) &&
    n_tokens == 1 &&
    down_sum6_pipeline != nil;
```

When active, a single kernel (e.g. `kernel_mul_mv_id_mxfp4_sum6_f32`) performs
both the per-expert dot products and the cross-expert sum.

### Accumulation order (MXFP4 example)

```metal
float2 sumf = 0.0f;
for (int slot = 0; slot < args.nei0; slot++) {       // slot 0,1,2,...,5
    const int32_t expert = token_ids[slot];
    // ... skip if not TP-owned ...
    sumf += ds4_mxfp4_accumulate_rows(expert_base, ...);
}
// simd_sum(sumf[row]) then write to dst
```

Key properties:
- **Sequential slot order (0→5)**: experts are accumulated in the order they
  appear in the `token_ids` (routing decision) array.
- **Register accumulation**: the running sum is held in per-thread `float`
  registers — no intermediate device-memory writes between experts.
- **`simd_sum` at the end**: the final horizontal reduction across SIMD lanes
  happens once after all experts are summed.
- **Single write**: output goes directly to `dst` (the layer output buffer).
  No intermediate buffer is used.

The Q4_K, Q2_K, and IQ2_XXS `sum6` kernels follow the same pattern: a `for
(expert_slot = 0; expert_slot < args.nei0; ...)` loop accumulating into a
`float sumf[nr0]` array, with a final `simd_sum` and a single write to `dst`.

## 3. Decode Non-Fused Path

When `direct_down_sum` is false (e.g. `g_quality_mode` or unsupported shape),
the dispatch is:

1. **Per-expert matvec** (`ds4_gpu_encode_mul_mv_id`) — writes each expert's
   contribution to a contiguous region in `down_dst` (scratch buffer).
   Layout: `[token][slot][out_dim]` where slot stride = `out_dim × sizeof(float)`.

2. **Separate sum kernel** (`kernel_dsv4_moe_sum6_f32`) — reads 6 consecutive
   expert rows per token and accumulates sequentially:

```metal
for (uint col = tid; col < args.width; col += ntg) {
    float v = s[col];           // slot 0
    v += s[width + col];        // slot 1
    v += s[2*width + col];      // slot 2
    v += s[3*width + col];      // slot 3
    v += s[4*width + col];      // slot 4
    v += s[5*width + col];      // slot 5
    d[col] = v;
}
```

The `src_token_stride` passed from the host is `6 × out_dim × sizeof(float)`,
and `dst_token_stride` is `out_dim × sizeof(float)`.

## 4. Prefill Path (`kernel_mul_mm_id` / `kernel_mul_mm_id_mpp`)

### Write pattern

The simdgroup-matmul prefill kernel writes **per-expert-per-token** into the
output buffer. The addressing is:

```metal
device float *D = (device float *)dst + r0 + ide*args.ne0 + idt*args.ne1*args.ne0;
```

Where:
- `ide = idj % args.ne20` — expert slot index within this token (0–5)
- `idt = idj / args.ne20` — token index
- `args.ne0` — output dimension (e.g. 4096)
- `args.ne1` — number of expert slots (e.g. 6)

This produces a layout:
```
dst[token][slot][out_dim]  (F32)
```

Each expert tile writes independently to its own slot. There is no atomic; each
(token, slot) position is written by exactly one expert tile.

The MPP (TensorOps) path `kernel_mul_mm_id_mpp` uses the identical output
layout and write pattern.

### Subsequent sum dispatch

After the prefill down kernel completes:

```objc
if (ok && n_expert > 1 && !direct_down_sum && ...) {
    ok = ds4_gpu_encode_moe_sum_experts(cb, down_dst, ..., outbuf, ...,
                                        out_dim, n_expert, n_tokens);
}
```

`ds4_gpu_encode_moe_sum_experts` dispatches:
- `kernel_dsv4_moe_sum6_f32` if n_expert == 6
- `kernel_dsv4_moe_sum8_f32` if n_expert == 8
- Iterative pairwise `g_add_pipeline` otherwise

## 5. GLM Path

The GLM down kernels (`kernel_glm_q4_K_down_f32`, `kernel_glm_q4_K_down_simd_f32`,
etc.) use a single-kernel approach where each threadgroup handles one output
row for one token:

```metal
float acc = 0.0f;
for (uint slot = 0; slot < args.n_expert_used; slot++) {
    // dot product of down_row[expert] · mid[slot]
    acc += ...;
}
// threadgroup reduction
out[token * out_dim + row] = scratch[0];
```

This is a fused in-kernel accumulation over all selected experts, writing
directly to the final output. The order is sequential over slots (0→5).

## 6. Exact-Order Dependency Analysis

### Is the accumulation order correctness-sensitive?

**Strictly speaking, yes — for floating-point bit-identity. Practically, no —
for inference correctness.**

Evidence:

1. **`g_quality_mode` disables the fused path.** When `--quality` is set, DS4
   falls back to the non-fused per-expert-then-sum path. The design comment
   does not explicitly state this is for accumulation order, but the quality
   mode broadly disables fusions that may change FP reduction order (it also
   disables the parallel attention path comment: "restores the sorted order for
   stricter reproducibility").

2. **Both paths use the same logical order.** The fused decode kernels iterate
   `slot = 0..nei0-1`. The separate `kernel_dsv4_moe_sum6_f32` sums
   `slot[0] + slot[1] + slot[2] + slot[3] + slot[4] + slot[5]` in that fixed
   order. The inner per-expert products use the same lane decomposition. So both
   paths produce the same FP result for the same input.

3. **No atomics.** No path uses atomic adds or unordered parallel writes to the
   same output location. The fused kernels accumulate in registers; the split
   path writes non-overlapping slots then sums sequentially.

4. **No test enforces a specific expert ordering** beyond what the router
   produces. The speed-bench validates full-vocabulary logits, which implicitly
   validates the sum result but does not isolate accumulation order from other
   numerical differences.

5. **TensorOps (MPP) path uses the same layout.** `kernel_mul_mm_id_mpp` writes
   per-expert identically to the simdgroup path and relies on the same subsequent
   sum kernel. No different reduction strategy.

### What would break if order changed?

- If experts were summed in a different permutation (e.g. reverse or unordered),
  the final float result may differ by a few ULP due to FP non-associativity.
- This would cause the speed-bench logit check to fail (detects any logit
  change).
- It would NOT cause incorrect model behavior in practice (the difference is
  rounding noise, not a logic error).

### Conclusion

The current accumulation order is **fixed-sequential-by-slot** in all paths.
Any new TensorOps down kernel must either:

1. **Preserve slot-sequential order** (preferred for bit-reproducibility with
   existing paths), or
2. **Accept per-ULP divergence** and validate via `--quality` fallback
   comparison, documenting the difference.

## 7. Output Destination Summary

| Path | Intermediate buffer | Final buffer | Layout |
|------|--------------------:|:-------------|--------|
| Decode fused sum6 | None | `outbuf` (`dst`) | `[out_dim]` per token |
| Decode non-fused | `g_moe_down_scratch_buffer` or `expertsbuf` | `outbuf` | Scratch: `[token][6][out_dim]`; Final: `[out_dim]` per token |
| Prefill mm_id | `g_moe_down_scratch_buffer` or `expertsbuf` | `outbuf` | Scratch: `[token][slot][out_dim]`; Final: `[out_dim]` per token |
| Prefill fused sum6 (tiny batch) | None | `outbuf` | `[out_dim]` per token |
| GLM down | None | `out` | `[token][out_dim]` |

---

## 8. Implications for TensorOps Down Kernel Design

1. **Can fuse without changing reduction order**: A TensorOps kernel that
   processes all 6 experts per output tile and accumulates in slot order would
   produce bit-identical results to the current fused decode path.

2. **Per-expert GEMM + later sum is safe**: Writing per-expert tiles then
   summing with the existing `kernel_dsv4_moe_sum6_f32` preserves the current
   non-fused accumulation order exactly.

3. **Reordering experts for better memory layout** (e.g. grouping tokens by
   expert for coalescing) is acceptable provided the final column-wise sum
   still adds slots in the same order. The key constraint is the reduction
   order of the final sum across expert contributions, not the dispatch order
   of tiles.

4. **`g_quality_mode` serves as the correctness oracle**: any new TensorOps
   path should compare against the quality fallback to validate numerical
   equivalence within acceptable bounds.
