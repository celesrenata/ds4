## 1. Dense TensorOps — RETAINED

**Decision:** Retain existing `kernel_mul_mm_mpp_direct_rhs` family (tasks 3.x).

### Design

- Auto-selected on M5 for N≥32, aligned prefill
- Direct-RHS design preserved (staging both operands in threadgroup was slower — empirical project knowledge)
- 32/64/128 token tiles selected per shape: NR1 chosen by `n_tok % {128, 64, 32}`
- Double-buffered weight staging into threadgroup, activation read directly from device memory
- Quant variants: F16, Q8_0, Q4_0, Q4_K — each with `_nax_direct_rhs` kernel names
- Split-prefix logic for Q8_0 when `n_tok ≥ 192 && n_tok%32 != 0` (TensorOps prefix + legacy tail)
- Output tile: 64 × NR1, K step = 32, cooperative F32 accumulation

### Rationale

The existing direct-RHS design was already well-tuned with measured evidence that the alternative (staging both operands) performed worse. Task 3.2 benchmarked tile shapes across real DS4 dimensions. No additional tile shapes (e.g., 256) provided measurable end-to-end gain beyond the existing 32/64/128 set. The selection policy was centralized (task 3.4) and pre-M5 defaults preserved (R17).

- `dev-notes/12.1-production-dispatch-policy.md` §6 — per-quant policy table
- Design §6 — rationale for retaining direct-RHS

## 2. Indexer TensorOps — RETAINED

**Decision:** Retain existing `kernel_dsv4_indexer_scores_nax` (tasks 4.x).

### Design

- M5 default for N≥16 (head_dim must equal 128)
- Tile: 16 tokens × 32 compressed rows × 128D, `execution_simdgroups<4>`
- Preserves causal visibility, top-k compatibility, and compressed-attention semantics
- Cooperative-output postprocessing evaluated (task 4.3) — retained only where it passes correctness and end-to-end
- Quality mode (`--quality`) falls back to F32 legacy tiled kernel for maximum reproducibility

### Rationale

The indexer TensorOps path already correctly focuses on the regular part of the compressed-attention problem: token × compressed-row dot products over 128 dimensions. The top-k/indexed-attention stage remains outside the accelerated matrix core. Task 4.2 profiled tile choices including barriers, staging, cooperative store, and weighted accumulation. The existing design is the right architectural boundary.

## 3. MoE Gate/Up TensorOps — IMPLEMENTED

**Decision:** Staged dequant → threadgroup → `matmul2d` with `execution_simdgroups<4>`. Fused pair+SwiGLU (tasks 7.x).

### Design

- Tile geometry: NR0=64 × NR1=32 × NK=32
- 128 threads per threadgroup (4 simdgroups × 32)
- 16384 bytes threadgroup memory
- Two `matmul2d` calls per K-step (gate + up) sharing a single staged activation tile
- Cooperative F32 accumulators for gate and up independently
- Epilogue: identical SwiGLU to legacy (clamp + SiLU + route_weight)
- Format instantiations: MXFP4 (`dequantize_mxfp4`), Q4_K, IQ2_XXS
- M5 default when N≥32, non-streaming, non-compact-tile
- Existing expert-bucketing infrastructure (map0/scatter_work) reused unchanged
- Activation gather unavoidable (tokens routed to same expert never contiguous)

### Dispatch Conditions

| Condition | Result |
|-----------|--------|
| M5 + TensorOps + MXFP4 + non-compact + not disabled | `kernel_mul_mm_id_mxfp4_mpp_pair_swiglu_f16` |
| M5 + TensorOps + Q4_K + not disabled | `kernel_mul_mm_id_q4_K_mpp_pair_swiglu_f16` |
| M5 + TensorOps + IQ2_XXS | `kernel_mul_mm_id_iq2_xxs_f32_mpp` |
| Pipeline lookup fails / old SDK / pre-M5 | Fallback to legacy simdgroup pair kernel |
| SSD streaming active | Fallback (addr/table paths block `use_mm_id`) |
| `DS4_METAL_DISABLE_MXFP4_MOE_GATE_UP_MPP` set | Legacy simdgroup |
| `DS4_METAL_DISABLE_TENSOROPS` set | Legacy (all TensorOps disabled) |

### Rationale

MoE gate/up projections are repeated across many layers in DeepSeek-V4 Flash and dominate prefill when the dense attention-side projections are already TensorOps-accelerated. The staged-dequant mechanism (winner from task 6.5) allows all DS4 quant formats to reach `matmul2d` without requiring native Metal tensor format compatibility. The fused pair design reuses the activation tile for both gate and up, applies SwiGLU before device-memory round trips, and matches the existing simdgroup pair kernel's buffer interface exactly.

## 4. MoE Down TensorOps — IMPLEMENTED

**Decision:** Same staged-dequant pattern as gate/up. Per-expert GEMM writes to scratch + existing `kernel_dsv4_moe_sum6_f32` (task 8.2). Accumulation fusion rejected (task 8.3).

### Design

- Same tile geometry as gate/up: NR0=64, NR1=32, NK=32, `execution_simdgroups<4>`
- Format instantiations: MXFP4, Q4_K, IQ2_XXS, Q2_K
- Per-expert writes to scratch `[token][slot][out_dim]`
- Existing `kernel_dsv4_moe_sum6_f32` sums sequentially across 6 expert slots
- Accumulation order preserved: slot-sequential (0→5) — bit-identical to legacy
- Output buffer already allocated by existing infrastructure — no new memory overhead

### Why Fusion Was Rejected

1. Per-token routing destroys expert coherence — each token routes to different experts; a fused kernel cannot batch weight loads across a 32-token tile
2. Weight coalescing destroyed — 6 different weight base addresses per slot per token
3. Cooperative accumulator cannot span experts with batched tokens efficiently
4. The sum kernel costs ~0.24 μs/token — negligible vs per-expert matmul time (~96 KB per token at M5 bandwidth)
5. The intermediate scratch buffer is already allocated

The TensorOps speedup comes entirely from accelerating per-expert GEMMs via `matmul2d`, not from eliminating the trivial sum.

## 5. Native MXFP4 (macOS 27) — DEFERRED

**Decision:** Zero-copy proven impossible. Resident-cache repack pending SDK availability. Custom dequant is the active path (task 5.6).

### Analysis

- DS4 MXFP4 stores interleaved 17-byte blocks: `[1 E8M0 scale][16 packed nibble bytes]`
- Metal's native MX tensor expects logically separate data and scale planes
- The interleaved block structure cannot be expressed via inline tensor stride/auxiliary-plane descriptors
- A truly zero-copy native view is impossible without layout transformation

### Options Evaluated (Design §8.3)

| Option | Feasibility | Outcome |
|--------|-------------|---------|
| 1. Inline tensor strides express interleaving | **NO** — scale and data physically interleaved within each 17-byte block | Rejected |
| 2. Lightweight gather/repack into cooperative input | Possible but loses zero-copy | Superseded by staged dequant |
| 3. Resident expert-cache creates MX-friendly layout | Possible when macOS 27 SDK available | Deferred |
| 4. Per-layer/per-expert repack | Bounded but adds memory/latency | Not yet measured |
| 5. Keep custom dequant | Works now, proven correct | **Active path** |

### Current Active Path

The custom `dequantize_mxfp4` function (E8M0 float scale × E2M1 float LUT → half) feeds staged threadgroup tiles to `matmul2d`. This is the production path and works on macOS 26.3+.

### When Native MX Might Activate

If a future macOS 27 SDK enables:
- Resident expert cache to store weights in MX-friendly separate-plane layout
- Bounded per-expert repack amortized over expert cache warm-up

Then the native MX path could eliminate the dequant compute cost entirely for cached experts. This is a future optimization, not a current blocker.

### Evidence

- Design §8.3 — MXFP4 native compatibility analysis
- Design §8.4 — custom dequant as alternative
- `dev-notes/7.2-mxfp4-gate-up-mpp.md` — the active custom-dequant production kernel

## 6. Cooperative Dequant (Cooperative Inputs) — BLOCKED

**Decision:** SDK requires single-simdgroup for cooperative inputs, incompatible with production 4-simdgroup tiles. Staged dequant is the winner (tasks 6.3, 6.5).

### What Was Tested

Task 6.3 attempted the ideal path: quant blocks → custom dequant → cooperative tensor input → `matmul2d`. This would avoid the threadgroup-memory round trip between dequant and matmul.

### Why It Failed

The macOS 26.3 cooperative-tensor-as-matmul-input API imposes a constraint: **the kernel must use a single simdgroup** (`execution_simdgroups<1>`). Production kernels use `execution_simdgroups<4>` (128 threads / 4 SGs) for adequate occupancy and throughput on the 64×32×32 tile.

At `execution_simdgroups<1>`:
- Only 32 threads service a 64×32 output tile
- Each thread must handle 4× the dequant work
- Occupancy drops by 4× relative to the staged path
- Measured performance was worse than staged dequant in microbenchmarks

### Winning Mechanism: Staged Dequant (Task 6.5)

```
mapped quant blocks
   → DS4 dequant in shader (format-specific)
   → threadgroup half tile (sa[]/sb[])
   → tensor() view over threadgroup
   → matmul2d with execution_simdgroups<4>
   → cooperative F32 accumulator
   → epilogue
```

This path:
- Works with 4 simdgroups (full occupancy)
- Supports all DS4 quant formats (Q8_0, Q4_K, MXFP4, Q2_K, IQ2_XXS)
- Proven correct and benchmarked against legacy
- Is the foundation for all MoE TensorOps kernels (tasks 7–8)

### Retained Documentation

The cooperative-input kernel is retained behind `DS4_EXPERIMENT_COOP_INPUT_SINGLE_SG` compile guard (never defined in production). It serves as documentation for revival if future Apple SDK lifts the single-simdgroup restriction.

### Evidence

- `dev-notes/6.1-quant-selection.md` — Q8_0 as mechanism validation format
- `dev-notes/12.2-experiment-cleanup.md` §2 — retained guarded kernel documentation
- Design §8.4 — cooperative-input path design

## 7. Native int2 (Q2_K / IQ2_XXS) — REJECTED

**Decision:** Format semantics incompatible with linear int2 tensors. Custom dequant → MPP kernels are the permanent path (task 9.5). Stop condition 14.5 triggered.

### Why Native int2 Cannot Work

**Q2_K:**
- Per-block metadata (4 bytes: `d` + `dmin`) — not representable in a raw int2 tensor
- Per-group metadata (16 bytes: `scales[]` with 4-bit scale + 4-bit min) — requires auxiliary decode
- Asymmetric quantization (`q * scale - min`) — not a simple `int2 × scale` pattern
- Non-power-of-2 block size (84 bytes) — complicates tensor stride calculations
- 16 groups per 256-element block with independent scale/min pairs

**IQ2_XXS:**
- Codebook-based decoding — weight values are indices into lookup tables
- Scale semantics differ from simple linear quantization
- Block structure includes packed codebook indices + scale data
- Dequant requires table lookup, not arithmetic on raw 2-bit values

A Metal `int2` tensor represents raw 2-bit integers with no metadata. Neither Q2_K nor IQ2_XXS can be expressed this way. Any "native int2" path for these formats would be fundamentally incorrect.

### Active Path

Both formats use the staged-dequant TensorOps mechanism:
- Q2_K: `dequantize_q2_K` → threadgroup → `matmul2d` via `kernel_mul_mm_id_q2_K_f16_mpp`
- IQ2_XXS: `dequantize_iq2_xxs` → threadgroup → `matmul2d` via `kernel_mul_mm_id_iq2_xxs_f16_mpp`

These paths are production-quality and permanent. No native-tensor alternative exists.

### Stop Condition 14.5

> "Stop native low-bit work for a quant format once byte-level incompatibility is proven."

Triggered for both Q2_K and IQ2_XXS. Byte-level incompatibility conclusively proven.

### Evidence

- `dev-notes/9.1-q2k-format.md` — complete Q2_K format documentation and int2 incompatibility proof
- `dev-notes/12.2-experiment-cleanup.md` §4 — confirmation no native-int2 code exists or was built

## 8. Verify / Crossover Dispatch — PREPARED

**Decision:** Dispatch threshold prepared at N≥32 default. `DS4_METAL_TENSOROPS_CROSSOVER_N` override for benchmarking. Gap zone (N=6–31) identified for future optimization (task 10.3).

### Current Policy

| N range | Path | TensorOps? |
|---------|------|------------|
| N = 1 | Decode matvec | Never (R10 invariant) |
| N = 2–5 | Tiny pair fused gate/up | No (hand-tuned for DSpark verify) |
| N = 6–31 | Per-token matvec (gap zone) | Not yet — pending crossover measurement |
| N ≥ 32 | Expert-major grouped matmul | Yes (TensorOps auto-selected on M5) |

### Gap Zone Analysis

The N=6–31 range is where session-batch decode and prompt micro-tails operate. The most likely crossover point is N=8–16 based on arithmetic intensity analysis. The infrastructure is in place to lower the threshold once hardware benchmarks (task 10.2) identify the measured crossover.

### Override Mechanism

```c
DS4_METAL_TENSOROPS_CROSSOVER_N=<integer>  // minimum 6, protects tiny pair zone
```

Guards:
- N=1 always takes matvec (batch-1 decode invariant — R10)
- N≤5 uses tiny pair when available (already proven)
- Threshold clamped to ≥6 to prevent bypassing pair zone
- Global rollback dominates all
- No effect on dense attention-output MPP (separate alignment logic)

## 9. Batch-1 Decode — UNCHANGED

**Decision:** TensorOps never dispatched for N=1. Matvec/fused paths retained per R10 (task 10.4).

### Rationale

Single-token decode is structurally memory-bandwidth-bound:
- Repeated weight streaming across all layers
- Low arithmetic intensity (one activation row × full weight matrix)
- Many matrix-vector operations, not matrix-matrix
- Launch/synchronization sensitivity dominates
- Existing code has significant hand-tuned fused dispatch (sum6, pair, slots6)

TensorOps `matmul2d` requires a matrix-shaped token batch to amortize its setup overhead. With N=1, there is no arithmetic intensity to exploit — the GPU spends its time streaming weights from memory, not computing. The Neural Accelerator cannot help when the bottleneck is bandwidth.

### Hard Invariant

```
if batch == 1:
    legacy/manual fused decode stays default
    unless balanced A/B proves TensorOps faster end-to-end
```

No balanced A/B has shown TensorOps winning for N=1. This is expected to remain true on M5 — the bandwidth bottleneck is structural.

### Decode Exactness Validation

Task 10.4 validated:
- Token selection identity (100% match across all generated tokens)
- Full-vocabulary bit-identical logits at every step
- No >1% end-to-end decode regression
- `metal-decode-schedule-bench --include-selection` methodology

### Evidence

- `dev-notes/10.4-decode-exactness-plan.md` — validation plan
- `dev-notes/12.1-production-dispatch-policy.md` §3.5 — decode dispatch tree

## 10. Attention TensorOps — DEFERRED

**Decision:** Deferred pending post-MoE profiling data. Existing FlashAttention too specialized for casual TensorOps replacement (tasks 11.2–11.4).

### Why Deferral Is Correct

1. No post-MoE Metal System Trace captured (requires Apple Silicon hardware)
2. Existing FlashAttention implements compressed DeepSeek-V4 attention with:
   - Causal visibility and block-skip optimization
   - KV padding, sink tokens, ALiBi/linear bias
   - Logit softcap, broadcast masks
   - SIMD-group 8×8 matrix operations for QK and SV products
   - Dequantization paths for non-F16 K/V
3. Existing indexer TensorOps (task 4) already covers the largest regular matrix operation
4. Risk/reward unfavorable without data — FlashAttention already uses hardware matrix units
5. Design §10 explicit: "Do not start by replacing `flash_attn.metal`"

### Decision Framework (When Trace Is Available)

| Attention GPU time % | Action |
|---------------------|--------|
| >25% | Proceed with attention TensorOps investigation |
| 15–25% | Evaluate absolute time saving vs complexity |
| <15% | Defer per stop condition 14.6 |

### What Would Be Considered (If Proceeding)

Only the regular QK score (`Q × K^T`) and `Attn × V` matrix inner products — the two matrix multiplications within each FlashAttention tile block. All compressed-attention semantics, masking, softmax, top-k, and causal logic explicitly excluded from scope.

### Stop Condition 14.6

> "Stop attention work if post-MoE profiling says it is not material."

Status: Cannot be evaluated without profiling data. Work stopped preemptively — correct default per design.

## 11. Overall Speed / Memory

**Decision:** Performance measurement pending hardware. No additional memory (no model repack). Acceleration through `matmul2d` hardware utilization without format changes.

### Memory Impact: Zero Additional

| Aspect | Impact |
|--------|--------|
| Model representation | Unchanged — same GGUF, same mmap, same on-disk layout |
| Full-model repack | NOT done (R3 preserved) |
| F16 model copy | NOT created (explicit non-goal) |
| Expert cache | Unchanged — existing resident/streaming paths preserved |
| Scratch buffers | Already allocated by existing infrastructure — reused |
| Threadgroup memory | 16384 bytes per threadgroup (same order as legacy simdgroup kernels) |
| Pipeline memory | Minimal — lazy pipeline creation, no per-token allocation |

### Performance Architecture

The TensorOps lift accelerates compute without changing data representation:

```
Same model bytes on disk/mmap
  → Same expert cache / SSD streaming infrastructure
    → Custom dequant into threadgroup staging (same as legacy, different consumer)
      → matmul2d on M5 Neural Accelerator (replaces simdgroup_multiply_accumulate)
        → Same output buffers, same graph flow
```

The speedup comes from `matmul2d` utilizing M5 GPU Neural Accelerators for the matrix multiplication step, while all data movement, dequantization, and fusion remain in custom shader code.

### Expected Performance Targets

| Metric | Target | Source |
|--------|--------|--------|
| M5 prefill improvement (combined) | ≥15% end-to-end | R16 SHOULD target |
| Individual kernel speedup | ≥1.25× for migrated kernels | R16 SHOULD target |
| Decode regression | ≤1% | R16 mandatory gate |
| Memory increase | 0 bytes (no repack) | R3 |
| Model load time increase | 0 (no format change) | R3 |
