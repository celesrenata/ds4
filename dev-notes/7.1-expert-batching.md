# 7.1 — Expert Batching Map for TensorOps Tile Consumption

_Requirements: R6_

## Summary

**Tokens ARE bucketed by expert** before the prefill matmul. The existing infrastructure
produces expert-major token lists and a compact work-item array that maps directly to
threadgroup grid positions. The activation (RHS) data is **gathered per-token from
scattered device-memory positions** — it is never physically contiguous per expert.

A TensorOps tile can consume:
- **Weights (LHS):** contiguous expert rows — pointer-stable, no gather needed.
- **Activations (RHS):** scattered token positions requiring per-row gather into
  threadgroup or cooperative-tensor staging.

---

## 1. Expert Bucketing: Two Mapping Kernels

### 1.1 `kernel_mul_mm_id_map0<ne20>`

**Sequential per-expert scan.** One thread per expert. Each thread scans all `ne21` tokens
linearly, checks if its expert id appears in the token's top-k selection list (stored in
`src2`), and appends the token index to a per-expert dense array.

**Output layout** (in `g_moe_id_map_buffer`):

| Region | Offset | Size | Content |
|--------|--------|------|---------|
| `htpe` (tokens-per-expert) | 0 | `ne02 × 4` bytes | `uint32_t tpe[expert]` — count of tokens assigned to each expert |
| `hids` (expert-local id list) | `ne02 × 4` | `ne02 × ne21 × 4` bytes | `int32_t ids[expert][row]` — packed token indices for each expert |
| `work` (tile work items) | aligned after hids | `8 + work_cap × 8` bytes | `uint32_t count` + `uint2 items[](expert_id, tile_row_offset)` |

**Packed id encoding:** `ids[expert][row] = token_index * ne20 + slot_within_topk`

This encodes both the token position (for activation gather) and the slot index (for
route-weight lookup and output scatter).

**Work items:** After counting tokens per expert, the kernel divides each expert's token
count into 32-row tiles and emits a compact `uint2(expert_id, row_offset)` for each tile.
This is the **direct launch grid** — each threadgroup processes exactly one work item.

**Dispatch:** Single threadgroup, `ne02` threads (one per expert). Sequential but fast
since `ne02` ≈ 256 and `ne21` ≤ prompt length.

### 1.2 `kernel_mul_mm_id_map_scatter_work<ne20>`

**Parallel token-centric scatter.** Multiple threads process tokens in parallel. For each
token, each selected expert gets an atomic-appended row in that expert's id list.

Same output format as map0 (same `htpe` / `hids` / `work` layout), but:
- Uses `atomic_fetch_add` per expert for parallel assignment
- Token-within-expert order is unspecified (tokens may land in different order than map0)
- Specialized for the common 6-expert MXFP4 case (`ne20=6`)
- Used on pre-M5 for ≥2048 tokens with compact tail tile

Both produce the **identical work-item trailer** consumed by all downstream matmul kernels.

## 2. Data Layout at Matmul Time

### 2.1 Weights (src0 / LHS) — Contiguous

Expert weights are **contiguous** in the model-mapped buffer:

```
weight_addr = base + expert * nb02 + output_row * nb01
```

For a given expert tile, the kernel reads `NR0` consecutive output rows × `NK` K-elements
per step. This is a **dense, aligned, sequential read** — ideal for TensorOps `tensor()`
views or direct staging.

For SSD-streaming (`kernel_mul_mm_id_addr`), the address table provides per-expert GPU
virtual addresses that point to the same dense row layout within cached buffers.

### 2.2 Activations (src1 / RHS) — Scattered by Token

The activation tensor is laid out as `src1[token][slot][K]`:

```metal
device const T1 * y = (device const T1 *)(src1
    + nb13*i13        // always 0
    + nb12*i12        // token index (id / ne20)
    + nb11*i11        // slot index (id % ne20) % ne11
    + nb10*iy);       // K offset
```

The `id` value from `hids[expert][row]` encodes the (token, slot) pair. Tokens assigned to
the same expert are **not** contiguous in `src1` — they're at arbitrary token positions
determined by the router output.

**Current staging approach:** Each thread in the matmul kernel independently reads its
assigned activation row from device memory and stages it into threadgroup memory `sb[]`.
This is a **gather** operation — `NR1` (32) scattered device-memory reads per K-step.

### 2.3 Output (dst) — Token-Major Scatter-Back

Results are written back to token-major layout:

```metal
device float *D = (device float *)dst + r0 + ide*ne0 + idt*ne1*ne0;
```

Each expert's output row scatters to a unique `(token, slot)` position. This is also
non-contiguous from the expert tile's perspective.

## 3. How the Existing Simdgroup Kernel Consumes the Map

`kernel_mul_mm_id_pair_swiglu_f16_impl` (the production MXFP4/Q4_K/IQ2 prefill kernel):

1. **Grid dispatch:** `tgpig.x` indexes into `work_items[]`, `tgpig.y` tiles across output
   rows (NR0=64). Each threadgroup handles one (expert, 32-token-tile) pair.

2. **Early exit:** If `work_index >= work_count[0]` or `r1 >= neh1`, return.

3. **Activation staging:** Each thread resolves `ids_i32[expert*ne21 + r1 + lr1]` → token
   index → device pointer into `src1`. The 4 threads assigned to each activation row read
   8 values each (NK=32 per step) into threadgroup `sb[]`.

4. **Weight staging:** Each thread dequantizes from `src0 + expert*nb02 + row*nb01` and
   writes 16 values into threadgroup `sa_gate[]` and `sa_up[]`.

5. **MMA:** 4 simdgroups perform 8×8 multiply-accumulate from threadgroup tiles.

6. **Epilogue:** SwiGLU + route-weight → write to scattered `dst_mid` positions.

### 3.1 The Existing MPP/TensorOps Kernel (`kernel_mul_mm_id_mpp`)

The Q2_K/IQ2_XXS TensorOps path uses the **identical dispatch and gather pattern**:

1. Same `work_items[]` indexing from map0 output
2. Same scattered activation gather into threadgroup `sb[]`
3. Same weight dequant into threadgroup `sa[]`
4. **`matmul2d` on threadgroup tiles** instead of explicit simdgroup MMA
5. **`cooperative_tensor` store** to threadgroup for output scatter

## 4. Where TensorOps Can Consume Rows

### 4.1 Weight Tiles (LHS) — Pointer-Stable, Contiguous

Expert weight data is:
- Contiguous per expert in GPU memory (mmap or resident cache)
- Row-major within each expert
- Aligned to block boundaries (34B for Q8_0, 18B for MXFP4, etc.)

**TensorOps integration point:** A `tensor()` view can be constructed over threadgroup-
staged dequantized weight data (current pattern) OR potentially over device-memory directly
if the format is compatible with native tensor types.

### 4.2 Activation Tiles (RHS) — Requires Gather

Activation data for a 32-token expert tile:
- Lives at 32 **arbitrary** positions in the `src1` buffer
- Each position determined by `ids_i32[expert*ne21 + r1 + row]`
- Row stride in `src1` is regular (`nb12` per token), but token indices are non-sequential

**TensorOps integration point:** The activation must be staged into a contiguous tile
(threadgroup or cooperative-input tensor) before `matmul2d` can consume it. This is the
existing pattern and remains necessary.

**Key insight:** The existing code already stages `sb[]` as a dense `[NR1 × NK]` tile in
threadgroup memory with layout `sb[NK*(8*sy + ly) + 8*sx + lx]`. A TensorOps `tensor()`
view over this staged tile is the natural entry point. The gather cost is fixed regardless
of whether simdgroup MMA or `matmul2d` consumes the result.

### 4.3 The Exact TensorOps Consumption Point

```
[map0 / scatter_work]          → work_items[], htpe[], hids[]
                                     ↓
[per threadgroup]              → resolve work_item → (expert, row_offset)
                                     ↓
[weight staging, per K-step]   → dequant from contiguous expert rows → threadgroup sa[]
                                     ↓
[activation staging, per K-step] → gather from scattered src1 → threadgroup sb[]
                                     ↓
[matmul2d consumption]         → tensor(sa, ...) × tensor(sb, ...) → cooperative output
                                     ↓
[epilogue]                     → SwiGLU + route weight → scatter to dst_mid
```

**The TensorOps tile consumes rows from threadgroup staging, not directly from device
memory.** Both operands are staged into threadgroup regardless of whether simdgroup MMA
or `matmul2d` is used. The existing MPP kernel already proves this pattern works for
routed MoE.

## 5. Implications for the MXFP4 TensorOps Lift

1. **No new bucketing infrastructure needed.** The existing map0/scatter_work output is
   directly consumed by both simdgroup and TensorOps kernels. The MXFP4 TensorOps gate/up
   kernel can use the identical work-item dispatch.

2. **Activation gather is unavoidable.** Tokens routed to the same expert are never
   contiguous in memory. The staging cost is a fixed overhead paid by both simdgroup and
   TensorOps paths.

3. **Weight staging may be avoidable for native-MX formats.** If MXFP4 proves layout-
   compatible with native Metal MX tensor types (task 5 result), the weight tensor could
   potentially be consumed directly from device memory via native tensor views. Otherwise,
   the custom-dequant-to-cooperative-tensor path (task 6 mechanism) feeds the matmul.

4. **Tile shape is compatible.** The existing 64×32×32 (NR0×NR1×NK) and 32×32×32 (compact)
   tiles match the TensorOps tile shapes used in `kernel_mul_mm_id_mpp`. The dispatch grid
   (one threadgroup per work item) maps naturally.

5. **Fused pair+SwiGLU preserves.** The paired kernel runs gate and up projections sharing
   the same staged activation tile. A TensorOps version can do the same — two `matmul2d`
   calls per K-step sharing one `tensor(sb, ...)` operand.

6. **Tail handling is orthogonal.** Expert tiles with fewer than 32 tokens use existing
   nr1 clamping, tail-cull, or compact-tile strategies. These work the same whether the
   inner matmul is simdgroup or TensorOps.

## 6. Buffer Binding Summary (for TensorOps kernel development)

| Index | Buffer | Content | Access Pattern |
|-------|--------|---------|----------------|
| 0 | args | `ds4_metal_args_mul_mm_id` struct | Constant |
| 1 | act_args | `ds4_metal_dsv4_moe_swiglu_weight_args` | Constant (pair+SwiGLU only) |
| 2 | src0_gate | Expert gate weights (contiguous per expert) | Sequential read |
| 3 | src0_up | Expert up weights (contiguous per expert) | Sequential read |
| 4 | src1 | Token activations (token-major, scattered) | Gathered read |
| 5 | htpe | Tokens-per-expert counts | Random read (one per expert) |
| 6 | hids | Expert-local token id lists | Sequential read within tile |
| 7 | dst_mid | SwiGLU intermediate output | Scattered write |
| 8 | weights | Route weights per (token, slot) | Gathered read |
| 9 | work | Work item array (expert_id, row_offset) | Indexed by tgpig.x |

## 7. Requirement Traceability

- **R6** (Routed-MoE TensorOps lift): This analysis confirms that expert bucketing exists
  and identifies the exact consumption point where `matmul2d` replaces simdgroup MMA.
  The work-item dispatch, activation gather, and output scatter patterns are shared
  infrastructure that a TensorOps kernel inherits unchanged.
