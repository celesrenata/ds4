This workspace is **esnixi** (NixOS x86_64 workstation). The `metal-prefill-variant-bench`
harness requires:
- macOS with Metal GPU access
- Apple Silicon (M5-family for TensorOps dispatch)
- A loaded DS4 GGUF model file

The benchmark plan is documented here for execution on the macOS development machine.

## 2. Binary

Single binary: `speed-bench/metal_prefill_variant_bench`

Build:
```bash
make metal-prefill-variant-bench
```

Same binary is used for both control and candidate runs — the harness toggles behavior via
environment variables at runtime using `setenv`/`unsetenv` between runs within the same
Metal engine instance.

## 5. Harness Methodology (built into the binary)

The `metal_prefill_variant_bench` harness enforces:

| Property | Implementation |
|----------|---------------|
| Same binary | Single Metal engine instance, variant selected by env var |
| Fresh sessions | New `ds4_session` created for every timed run |
| Alternating order | ABBA block (repeats 1, 3, 5…) + BAAB block (repeats 2, 4, 6…) |
| Warmup | ≥32 tokens untimed per variant before measurement |
| Bit-identical logits | Full vocabulary `memcmp` after each run; abort on mismatch |
| Logit buffer poisoning | Host buffer filled with alternating 0xa5/0x5a before copy |
| Default prefix | 8192 tokens |
| Default repeats | 2 (= 8 timed runs total: 4 control + 4 candidate) |

## 6. Acceptance Criteria (from R16)

### 6.1 Combined TensorOps prefill improvement target

> THE PROJECT SHOULD TARGET at least a **15% end-to-end M5 prefill improvement** on
> representative DeepSeek-V4 prompts after all enabled TensorOps work is combined.

This is measured by the global rollback A/B (§4.2): TensorOps-default vs `DS4_METAL_DISABLE_TENSOROPS`.

### 6.2 Individual kernel speedup target

> THE PROJECT SHOULD TARGET at least a **1.25× speedup** in the individual compute-dense
> kernels migrated to TensorOps, unless end-to-end profiling shows the kernel is no longer
> material.

This is measured by the per-quant A/Bs (§4.1, §4.3, §4.4). The gate/up kernels are
compute-dense MoE projections and are expected to be material in the prefill profile.

### 6.3 Decode regression gate

> THE SYSTEM SHALL have no statistically significant regression greater than **1%** in the
> established end-to-end decode benchmark.

This is verified separately via `metal-decode-schedule-bench --include-selection` (task scope
extends beyond this document but must pass before TensorOps becomes default).

### 6.4 Bit-identical correctness

The harness aborts if any control/candidate logit row differs. This is a binary pass/fail
built into every measurement run.

## 7. Expected Output Format

The harness prints per-run lines:
```
run=1 repeat=1 pattern=ABBA slot=1 variant=control tokens=8192 seconds=0.543210 tokens_per_second=15081.1234 exact=yes
run=2 repeat=1 pattern=ABBA slot=2 variant=candidate tokens=8192 seconds=0.612345 tokens_per_second=13381.5678 exact=yes
...
```

Followed by aggregates:
```
aggregate variant=control runs=4 tokens=32768 seconds=2.172840 tokens_per_second=15081.1234
aggregate variant=candidate runs=4 tokens=32768 seconds=2.449380 tokens_per_second=13381.5678
candidate_delta_percent=-11.2600 exact_runs=8 exact_floats=1048576 vocab=131072
```

A **negative** `candidate_delta_percent` means the candidate (legacy/rollback) is slower —
i.e., TensorOps (control) wins.

## 9. Decision Criteria

| Result | Action |
|--------|--------|
| TensorOps control wins ≥15% combined | Accept as default; proceed to task 8 (down projection) |
| TensorOps control wins 5–15% combined | Accept as default; note gap to target |
| TensorOps control wins <5% combined | Investigate; may need down-projection (task 8) to reach target |
| TensorOps control neutral or loses | **Reject** — disable gate/up TensorOps, document finding |
| Logit mismatch (bit-identity failure) | **Block** — fix correctness before retrying |

Per-quant results may differ. A quant-specific path can be rejected independently while
others are retained.

## 11. Requirement Traceability

### R13 (Benchmark methodology)

> WHEN comparing a candidate against control  
> THE SYSTEM SHALL use the same engine, warmed sessions, alternating run order, and
> fresh-session discipline already used by DS4's Metal A/B harnesses.

**Satisfied.** The `metal_prefill_variant_bench` harness implements all of these properties
(same engine, `setenv`/`unsetenv` toggle, ABBA/BAAB ordering, fresh sessions, warmup).

> WHEN an optimization is retained  
> THE SYSTEM SHALL show repeatable benefit across more than one prompt/batch shape.

**Plan:** Commands in §4 cover 512, 2048, 8192, and 32768 token prefills.

### R16 (Performance acceptance)

> THE PROJECT SHOULD TARGET at least a 15% end-to-end M5 prefill improvement.

**Plan:** Measured by the combined TensorOps A/B (§4.2).

> THE PROJECT SHOULD TARGET at least a 1.25× speedup in individual compute-dense kernels.

**Plan:** Measured by per-quant A/Bs (§4.1, §4.3, §4.4).

> A production TensorOps path that improves a microbenchmark but regresses total prefill,
> TTFT, memory pressure, or load time SHALL NOT become default.

**Plan:** End-to-end prefill t/s is the primary metric, not kernel microbenchmarks.
